# استاندارد و قوانین مستندسازی

این سند قانون مشترک تمام مستندات پروژه است و باید در زمان ایجاد یا تکمیل هر فرم، موضوع و workflow رعایت شود.

## ۱. تفکیک واقعیت از پیشنهاد

هر سند باید اطلاعات را در یکی از این چهار دسته قرار دهد:

| برچسب | مفهوم |
|---|---|
| رفتار فعلی | مستقیماً از کد، Designer، API یا رفتار قابل مشاهده استخراج شده است |
| برداشت تحلیلی | نتیجه‌گیری منطقی از چند بخش کد است، اما مستقیماً به‌عنوان قرارداد اعلام نشده است |
| ناقص/نیازمند تأیید | اطلاعاتی که در کد ناقص، مبهم، متناقض یا بدون مسیر مشخص است |
| پیشنهاد نسخه‌ی وب | تصمیم پیشنهادی برای React/API جدید، نه توصیف رفتار فعلی |

نباید پیشنهاد نسخه‌ی وب به‌عنوان رفتار فعلی برنامه نوشته شود.

## ۲. قانون کامل‌بودن API

برای هر فرم باید مشخص شود APIها در چه سطحی مستند شده‌اند:

- **کامل**: مسیر، HTTP method، ورودی، خروجی، خطا و اثر UI بررسی شده است.
- **نام endpoint مشخص**: مسیر از کد کلاینت پیدا شده، اما قرارداد کامل یا کنترلر بررسی نشده است.
- **ناقص**: بخشی از APIهای مورد نیاز فرم پیدا نشده یا اطلاعات ورودی/خروجی آن‌ها مشخص نیست.
- **نامشخص**: رفتار UI وجود دارد، اما endpoint یا منبع داده‌ی آن هنوز مشخص نیست.

هر سند فرم باید بخش `وضعیت پوشش API` داشته باشد و موارد ناقص را با جدول پیگیری ثبت کند.

## ۳. قالب اجباری مستندات فرم

هر سند فرم باید تا حد امکان این بخش‌ها را داشته باشد:

1. هدف فرم
2. مسیر دسترسی و نقش‌های مجاز
3. ساختار و اجزای UI
4. حالت‌های صفحه
5. جریان‌های اصلی کاربر
6. فیلدها و اعتبارسنجی‌ها
7. عملیات ایجاد، ویرایش، حذف و لغو
8. وابستگی به فرم‌ها و داده‌های دیگر
9. APIهای مورد نیاز و وضعیت پوشش آن‌ها
10. مدل‌های ورودی و خروجی
11. خطاها و وضعیت‌های empty/loading/unauthorized
12. رفتار فعلی که نباید مستقیماً به وب منتقل شود
13. پیشنهادها و نیازمندی‌های نسخه‌ی وب
14. موارد باز و نیازمند تصمیم

## ۴. ثبت منبع و میزان اطمینان

برای جزئیات حساس باید منبع مشخص باشد: فایل فرم، Designer، `ApiAddress`، Controller، DTO/Entity یا component مشترک. اگر فقط از روی نام کنترل یا endpoint نتیجه‌گیری شده باشد، باید با برچسب «برداشت تحلیلی» یا «نیازمند تأیید» ثبت شود.

## قرارداد مشترک حذف در payload

**تصمیم محصول:** در requestهای UI که فهرست entity را برای API ارسال می‌کنند، `Id < 0` به‌معنای حذف entity با شناسه‌ی `abs(Id)` است. چنین رکوردی نباید ایجاد یا ویرایش شود. مثال: `Id = -42` یعنی حذف entity شماره `42`.

- این قرارداد فقط برای endpointهایی معتبر است که Backend آن را رسماً پشتیبانی و مستند کرده باشد.
- UI باید حذف را پس از تأیید کاربر به payload تبدیل کند و شناسه‌ی منفی را به‌عنوان شناسه‌ی موقت/رکورد جدید تلقی نکند.
- **سیاست پیش‌فرض محصول:** حذف، فیزیکی از دیتابیس (hard delete) است. هر موردی که باید soft delete یا archive شود، استثنا است و باید صریحاً در سند همان entity ثبت شود.
- Backend باید authorization، وجود رکورد، وابستگی‌ها، audit و نتیجه‌ی حذف فیزیکی را کنترل کند.

## ۵. تفکیک رفتار فعلی و طراحی وب

هر جا رفتار نسخه‌ی ویندوزی با استاندارد یا معماری وب تفاوت دارد، دو بخش جدا نوشته شود: «رفتار فعلی برنامه» و «پیشنهاد یا نیازمندی نسخه‌ی وب».

مواردی مانند ذخیره‌ی محلی credential، کدهای عددی مجوز، پیش‌بارگذاری داده و endpoint نامتناسب با REST نباید بدون ارزیابی به React منتقل شوند.

## ۶. ثبت ابهام و وضعیت تکمیل

برای خلأ اطلاعات حدس قطعی نوشته نشود. وضعیت‌هایی مانند «endpoint پیدا نشد»، «مدل request/response نامشخص»، «خطاها مشخص نیستند» و «رفتار UI و API سازگار نیستند» باید صریحاً ثبت شوند.

وضعیت سند می‌تواند یکی از این موارد باشد: تحلیل اولیه، در حال تکمیل، API ناقص، نیازمند تأیید محصول، یا آماده‌ی مبنای طراحی وب.

## ۷. کامل‌بودن اجباری هر بخش

هر بخش، فرم، صفحه یا workflow باید به‌صورت کامل و بدون کاستی مستند شود. مستندسازی ناقص یک بخش نباید به‌عنوان مستندات تکمیل‌شده ارائه شود.

کامل‌بودن هر بخش حداقل شامل این موارد است:

- هدف، نقش و جایگاه بخش در workflow
- مسیر ورود، خروج و بازگشت
- نقش‌ها و سطح دسترسی
- ساختار کامل UI، فیلدها، جدول‌ها، دکمه‌ها و حالت‌های صفحه
- جریان‌های اصلی و حالت‌های جایگزین کاربر
- اعتبارسنجی‌ها، وابستگی‌ها و اثر هر عملیات
- حالت‌های loading، empty، error، unauthorized و تغییر ذخیره‌نشده
- عملیات ایجاد، مشاهده، ویرایش، حذف، لغو، جستجو، فیلتر و صفحه‌بندی در صورت وجود
- APIها، method، مسیر، request، response، خطا، status code و اثر API بر UI
- مدل‌های داده و نگاشت فیلدهای UI به مدل API
- تفاوت رفتار فعلی با نیازمندی نسخه وب
- موارد باز، تصمیم‌های لازم و منبع هر ادعا

اگر هر یک از این موارد از کد یا منابع موجود قابل استخراج نیست، باید همان مورد صریحاً با یکی از برچسب‌های «ناقص/نیازمند تأیید»، «پیشنهاد نسخه وب» یا «نامشخص» ثبت شود؛ حذف‌کردن خلأ اطلاعات مجاز نیست.

## ۸. آماده‌بودن برای طراحی اولیه و پیاده‌سازی وب

هر بخش باید به‌گونه‌ای مستند شود که هم برای طراحی اولیه UI وب کافی باشد و هم مبنای آماده‌سازی پیاده‌سازی قرار گیرد. سند باید بتواند بدون مراجعه‌ی دوباره به کد قدیمی، موارد زیر را برای تیم طراحی و توسعه مشخص کند:

- صفحه‌ها، routeها، layout و ارتباط بین viewها
- componentهای اصلی و الگوی تعامل کاربر
- فیلدها، نوع کنترل، مقدار پیش‌فرض، اجباری‌بودن و پیام اعتبارسنجی
- جدول‌ها، ستون‌ها، فیلترها، sort، pagination و عملیات هر ردیف
- قرارداد loading، empty، error، unauthorized و success state
- request/response رسمی API و نحوه‌ی مدیریت خطا و retry
- مجوزهای مورد نیاز در frontend و backend
- رفتار responsive، دسترسی‌پذیری و متن‌های قابل نمایش در UI
- نیازمندی‌های امنیت، audit، تراکنش و حفاظت از داده‌های حساس در صورت وجود

وضعیت «آماده‌ی مبنای طراحی وب» فقط زمانی مجاز است که طراحی اولیه UI بتواند بر اساس همان سند انجام شود. وضعیت «آماده‌ی پیاده‌سازی وب» فقط زمانی مجاز است که علاوه بر UI، قرارداد API، مدل داده، خطاها، مجوزها و workflowهای اصلی نیز تعیین شده باشند. در غیر این صورت وضعیت باید «API ناقص»، «نیازمند تأیید محصول» یا وضعیت دقیق‌تر دیگری ثبت شود.

## ۹. اصل هم‌ارزی قابلیت با Windows

**تصمیم محصول:** نسخه وب باید تا حد امکان تمام قابلیت‌های محصول Windows را پوشش دهد. دسته‌بندی حوزه‌ها و فرم‌ها باید برای کاربران محصول Windows قابل تشخیص بماند، ولی layout و interaction باید بر مبنای استانداردهای وب، responsive design و accessibility طراحی شود و کپی ظاهری WinForms لازم نیست.

اگر قابلیتی به‌دلیل محدودیت Browser مستقیماً قابل پیاده‌سازی نیست، سند آن قابلیت باید شامل این سه مورد باشد:

1. رفتار Windows که باید حفظ شود؛
2. راهکار جایگزین وب؛
3. مالک و وابستگی اجرا، مانند UI، Backend، Windows Service/Agent یا عملیات اپراتور.

حذف قابلیت بدون ثبت این جایگزین مجاز نیست.

## ۱۰. قواعد الزام‌آور طراحی و پیاده‌سازی React

این بخش مرجع واحد قواعد طراحی UI/UX و کدنویسی React پروژه است. همهٔ طراحی‌ها،
تغییرات کد و بازبینی‌ها باید با آن سنجیده شوند. این پروژه یک **مصرف‌کنندهٔ API**
است؛ قرارداد و پیاده‌سازی Backend در scope آن نیست.

### ۱۰.۱. هدف و زبان طراحی

- رابط باید یک نرم‌افزار عملیاتی/سازمانی حرفه‌ای، دقیق، سریع، متراکم و قابل فهم
  باشد؛ نه داشبورد عمومی SaaS یا صفحهٔ تبلیغاتی.
- زبان بصری باید منسجم و مبتنی بر مینیمالیسم دقیق، سبک بین‌المللی/Swiss، صنعتی،
  editorial و human-centered باشد؛ ترکیب تصادفی سبک‌ها مجاز نیست.
- از glassmorphism، گرادیان‌های تزئینی، کارت‌های شناور و گردِ فراوان، سایه‌های
  سنگین، تیترهای بزرگ، فضای خالی بی‌دلیل، چیدمان کارت سه‌ستونهٔ تکراری، آیکن‌های
  دکوراتیو بزرگ و motion غیرضروری پرهیز شود.
- در تعارض میان زیبایی و usability، میان تزئین و وضوح اطلاعات، یا میان animation و
  سرعت ادراک‌شده، به‌ترتیب usability، وضوح و سرعت اولویت دارند.

### ۱۰.۲. پوسته، سلسله‌مراتب و الگوهای صفحه

- پوستهٔ اصلی باید navigation فشرده و قابل پیش‌بینی، header صفحه، toolbar/filter و
  محتوای عملیاتی را با بیشترین فضای مفید نمایش دهد. منوها منطقی گروه‌بندی شوند و
  بی‌دلیل عمق نگیرند.
- هر صفحه باید فوراً محل فعلی کاربر، اطلاعات نمایش‌داده‌شده، عمل اصلی و عمل‌های
  ثانویه را روشن کند. ترتیب ترجیحی: صفحه، header، عمل اصلی، کنترل‌ها/فیلترها،
  اطلاعات اصلی، اطلاعات ثانویه.
- برای فهرست‌ها از الگوی title، عمل اصلی، فیلتر، نتیجه، data grid و حالت‌های
  loading/empty/error استفاده شود. صفحهٔ جزئیات باید هویت رکورد، عمل‌های context و
  مسیر بازگشت روشن داشته باشد.
- فرم create/edit باید کوتاه، گروه‌بندی‌شده و دارای validation نزدیک به field باشد.
  dialog فقط برای عملیات کوتاه و متمرکز است؛ workflowهای پیچیده باید صفحه یا drawer
  اختصاصی داشته باشند.
- عمل destructive باید رکورد و اثر آن را روشن کند، تأیید صریح بگیرد و ظاهر متمایز
  داشته باشد. عمل‌های مهم تنها در overflow menu پنهان نشوند.

### ۱۰.۳. typography، spacing و tokenها

- خوانایی و تراکم اطلاعات بر typography نمایشی مقدم است. فونت مرجع فارسی برنامه
  `VazirFD` با fallback `Vazir, Tahoma, Arial, sans-serif` است؛ این انتخاب برای
  حفظ نمایش صحیح اعداد فارسی و سازگاری با UI فعلی قطعی است. `Vazirmatn` در این
  پروژه مرجع فونت فارسی محسوب نمی‌شود.
- spacing سفارشی مستقلی در `src/theme.ts` تعریف نشده است؛ مبنای spacing در MUI همان
  واحد پیش‌فرض `8px` است و مقادیر مشترک فعلی در `src/theme.ts` و `src/styles.css`
  نگهداری می‌شوند. بنابراین سند نباید یک مقیاس مستقل مانند `4/8/12/16/20/24/32`
  یا `4/8/12/16/24/32/48` را به‌عنوان token تثبیت‌شده ادعا کند.
- مقادیر فعلی shape در `defaultThemeShape` مرجع هستند: `controlRadius=4px`،
  `buttonRadius=3px` و `popupRadius=5px`. radius عمومی دیگری، از جمله بازه‌ی
  `6 تا 10px` برای کارت‌های عملیاتی، جزو قرارداد فعلی نیست.
- MUI theme و قراردادهای مشترک CSS مرجع tokenهای رنگ، font، border، radius، elevation،
  transition و ابعاد component هستند. مقدار جدید در feature فقط با reuse مقدار مشترک
  موجود مجاز است؛ اگر token spacing یا shape جدید لازم شد، ابتدا باید در Theme تعریف
  و در همین سند ثبت شود.
- فقط از palette معنایی موجود (`primary`، `secondary`، `success`، `warning`،
  `error`، `info`، `background`، `text` و `divider`) استفاده شود. رنگ برای انتقال
  معنی است، نه تزئین.

### ۱۰.۴. اجزا، جدول‌ها، فرم‌ها و بازخورد

- componentهای پایهٔ مشترک (button، input، select، checkbox، dialog، drawer، tabs،
  table، pagination، alert، toast، skeleton و status) باید reuse شوند و منطق کسب‌وکار
  در component عمومی قرار نگیرد.
- tableها باید متراکم، خوانا، قابل اسکن و keyboard-friendly باشند و در صورت نیاز
  sorting، filtering، pagination، انتخاب ردیف، bulk action، sticky header، actionها
  و حالت‌های loading/empty/error را داشته باشند. برای دادهٔ بزرگ، عملیات سمت API و
  virtualization فقط با نیاز مشخص به‌کار رود.
- همهٔ Gridهای قابل فیلتر باید از قرارداد مشترک فیلتر ستونی استفاده کنند: منوی سه‌نقطه
  در هر سرستون، بازشدن گزینه‌ها در یک منوی شناور متصل به همان ستون و ورودی جستجو داخل
  همان سرستون و زیر عنوان. ورودی جستجو در حالت پیش‌فرض مخفی است و از منوی همان ستون
  فعال می‌شود؛ ردیف جداگانه یا نوار ابزار جداگانه برای فیلتر و گزینه‌های آن مجاز نیست.
  فیلترها در حالت معمول روی رکوردهای موجود در UI با منطق AND بین ستون‌ها
  اعمال می‌شوند و باید گزینه‌های `contains`، `startsWith`، `equals`، حساسیت به حروف و
  پاک‌کردن همهٔ فیلترها را ارائه کنند. فرم‌هایی که نیاز عملیاتی به نمایش فوری فیلتر
  دارند می‌توانند `defaultFilterOpen` را فعال کنند؛ پیاده‌سازی جداگانهٔ فیلتر در
  featureها مجاز نیست.
- buttonها hierarchy روشن داشته باشند: فقط عمل اصلی dominant است و destructive styling
  متمایز باشد. در toolbar بالای هر Grid، همهٔ دکمه‌های عملیاتی و CRUD الزاماً
  icon-only هستند؛ متن داخل دکمه نمایش داده نمی‌شود و نام عمل باید هم‌زمان با
  `Tooltip` و `aria-label` ارائه شود. ترتیب CRUD مرجع `جدید`، `ویرایش`، `حذف` است؛
  ایجاد/جدید با رنگ primary، ویرایش خنثی و حذف با رنگ error نمایش داده می‌شود.
  دکمهٔ ویرایش فقط با انتخاب دقیقاً یک ردیف و دکمهٔ حذف فقط با انتخاب ردیف فعال
  می‌شوند. دکمهٔ icon-only باید از component مشترک و اندازه/spacing مشترک toolbar
  استفاده کند و برای Tooltip در حالت disabled داخل wrapper مناسب قرار بگیرد.
  این الزام فقط برای toolbar بالای Grid است؛ دکمه‌های فرم و Dialog می‌توانند label
  متنی داشته باشند.
- فرم‌ها label روشن، گروه‌بندی منطقی، required field مشخص، input type مناسب و خطای
  نزدیک به field داشته باشند. validation باید صریح و متمرکز باشد.
- از toast، alert، inline validation، confirmation و progress به‌صورت فوری و
  context-aware استفاده شود؛ feedback نباید بی‌دلیل کاربر را متوقف کند.
- هر داده یا عملیات async باید حالت pending/loading، success، error و no-data مناسب
  با scope خود داشته باشد؛ برای محتوای اصلی skeleton بر متن سادهٔ Loading ترجیح دارد.

### ۱۰.۵. RTL، زبان و responsive

- محصول فارسی‌محور است، ولی RTL و LTR باید هر دو درست کار کنند. `dir` سند، MUI theme
  و cache RTL از زبان فعال گرفته شوند.
- در CSS از logical propertyهای `margin-inline`، `padding-inline`، `inset-inline` و
  `text-align: start/end` استفاده شود، نه left/right. آیکن‌ها فقط وقتی معنایشان به
  جهت وابسته است mirror شوند.
- مقدارهای فنی مانند code، identifier، URL، password و plate number در RTL باید با
  direction مناسب و خوانا نمایش داده شوند.
- همهٔ متن‌های قابل مشاهده باید از لایهٔ ترجمه بیایند. date، time، currency، count و
  تبدیل ارقام فارسی/لاتین نیز باید formatter مشترک داشته باشند، نه پیاده‌سازی موردی
  در component.
- تنها منبع مجاز برای ترجمهٔ متن UI در React، `i18next` به‌همراه
  `react-i18next` است. منابع هر زبان باید در فایل مستقل داخل `src/locales/` نگهداری
  شوند و instance مشترک i18next در `src/i18n/` پیکربندی شود. در componentها از
  `useTranslation()` و `t()` استفاده شود؛ کدهای خارج از component می‌توانند از
  instance مشترک `i18n.t()` استفاده کنند.
- استفاده از روش‌های موازی یا جایگزین برای متن UI ممنوع است؛ از جمله
  `language === 'fa' ? '...' : '...'`، الگوی `text(fa, en)`، helper ترجمهٔ سفارشی،
  مقدار پیش‌فرض inline برای پنهان‌کردن کلید مفقود و هر متن قابل مشاهدهٔ hard-code
  داخل JSX، hook، handler یا مدل view. شرط زبان فقط برای direction، formatter و
  منطق فنی مجاز است، نه برای انتخاب متن نمایشی.
- کلیدهای ترجمه باید معنادار و مشترک بین منابع زبان باشند. اضافه‌کردن زبان جدید
  مستلزم ساخت resource مستقل با همان قرارداد کلیدها، ثبت زبان در `supportedLngs`
  و تعیین fallback رسمی است؛ ترجمهٔ زبان جدید نباید با fallback یا ternary جایگزین
  شود.
- وجود یکی از الگوهای ممنوع، کلید مفقود، resource ناقص یا استفاده از سیستم ترجمهٔ
  دوم، blocker تحویل است. بازبینی باید با جست‌وجوی الگوهای ممنوع، type-check منابع
  و تست missing-key انجام شود و مورد استثنا فقط با ثبت دلیل، مالک، ریسک و برنامهٔ
  حذف/جایگزینی پذیرفته شود.
- برای عملیات مخرب، به‌خصوص حذف، استفاده از `window.confirm` و هر دیالوگ native
  مرورگر ممنوع است. تمام تأییدهای حذف باید با `ConfirmDialog` مشترک انجام شوند؛
  اجرای API حذف فقط در `onConfirm` مجاز است و در زمان درخواست async باید dialog با
  `busy` قفل شود. این قاعده شامل حذف تکی و گروهی و همهٔ workspaceهاست.
- responsive صرفاً کوچک‌کردن desktop نیست: در صفحهٔ باریک فرم‌ها stack، کنترل‌های
  ثانویهٔ toolbar جمع و navigation به drawer تبدیل شوند. tableها با scroll محصور،
  اولویت ستون یا detail فشرده خوانا بمانند و page-level overflow ایجاد نکنند.
- dark mode، در صورت وجود، با surfaceهای معنایی و contrast مناسب پیاده شود، نه invert
  سادهٔ رنگ‌ها.

### ۱۰.۶. accessibility

- semantic HTML، keyboard navigation، focus state واضح، label مناسب، ARIA فقط در
  جای لازم، contrast کافی و dialog/form قابل دسترس الزامی است.
- هر کنترل آیکنی باید accessible name داشته باشد. dialog باید focus را در زمان بازشدن
  مدیریت، داخل خود نگه‌داری و پس از بسته‌شدن به کنترل آغازکننده برگرداند.
- status و validation فقط با رنگ منتقل نشوند. motion غیرضروری باید
  `prefers-reduced-motion` را رعایت کند.

### ۱۰.۷. اصول کدنویسی و معماری

- React با TypeScript strict الزامی است. کد باید production-ready، ساده، صریح، قابل
  نگهداری و قابل توسعه باشد. از `any` اجتناب و برای دادهٔ واقعاً ناشناخته از `unknown`
  استفاده شود.
- معماری feature-based مرجع است: کد مخصوص هر دامنه در feature خودش و componentهای
  reusable بدون منطق business در shared area قرار می‌گیرند. پیش از ساخت، component،
  hook، utility و منطق موجود جست‌وجو و در صورت مناسب بودن extend شود.
- هر component و hook یک مسئولیت روشن داشته باشد. componentهای بزرگ به بخش‌های
  معنی‌دار و منطق پیچیده به hookهای اختصاصی شکسته شوند؛ اما splitting صرفاً برای
  کم‌کردن تعداد خطوط مجاز نیست.
- نام‌ها توصیفی و ثابت باشند. booleanها با `is`/`has`/`can`/`should`، handlerها با
  `handle…` و callback propها با `on…` نام‌گذاری شوند. از نام‌های مبهم و barrelهایی
  که dependency cycle یا مالکیت نامشخص ایجاد می‌کنند پرهیز شود.
- پشتهٔ فعلی مبنا است: React، TypeScript strict، Vite، MUI/Emotion/stylis RTL، React
  Router، fetch client مشترک، Zod، Vitest، Testing Library و Playwright. وابستگی جدید
  فقط با نیاز مستند و برتری روشن بر platform/MUI/shared code اضافه می‌شود.
- TanStack Query، Zustand و React Hook Form اکنون dependency پروژه نیستند و افزودن
  آن‌ها صرفاً برای پیروی از الگو مجاز نیست. برای formهای غیرساده از MUI و Zod استفاده
  شود؛ dependency جدید باید نیاز واقعی و تصمیم صریح داشته باشد.

### ۱۰.۸. state، API و امنیت

- state محلی در React، state اشتراکی application در Context یا راهکار سبکِ واقعاً
  لازم، و data API در hook اختصاصی نگه‌داری شود. server data بی‌دلیل duplicate یا
  global نشود.
- API call مستقیم در page/UI ممنوع است. زنجیرهٔ مرجع: `UI → custom hook → feature
  service → src/api/client.ts → External Backend API`.
- همهٔ requestها از client مشترک و cookie/timeout/cancellation آن عبور کنند؛ ارسال
  token از UI در header یا query string برای قابلیت‌های جدید ممنوع است.
  endpoint، request، schema پاسخ و mapping به domain/UI کنار feature یا در `src/api`
  قرار بگیرند و در UI پراکنده نشوند.
- پاسخ API untrusted است و هرجا shape آن بر رفتار UI اثر دارد با Zod در boundary
  اعتبارسنجی شود. UI می‌تواند response را به domain model تبدیل کند، اما نباید payload
  یا semantics API را حدس بزند یا تغییر دهد.
- خطاهای 400، 401، 403، 404، 409، 422، 500، network و timeout به پیام کاربری مفید و
  state مناسب تبدیل شوند؛ raw response یا exception فنی نمایش داده نشود.
- retry، polling، optimistic update، caching و virtualization پیش‌فرض نیستند؛ فقط با
  نیاز UX روشن و تعریف cancellation، stale-data و error فعال شوند. submit pending
  باید disabled/idempotent باشد و request قدیمی در unmount یا تغییر filter نادیده یا
  cancel شود.
- هیچ secret، private key، token یا password جدیدی در source، URL، log یا browser
  storage ذخیره نشود. token نشست باید توسط Backend در cookie `HttpOnly`، با
  `SameSite=Lax`، `Path=/` و در production با `Secure` روی HTTPS صادر شود؛ UI نباید
  token را بخواند، در `localStorage`/`sessionStorage` بنویسد یا در header/query
  بفرستد. سازگاری legacy موجود باید isolate، دلیل‌دار و test‌شده باشد و
  نباید الگوی featureهای جدید شود.
- validation سمت client امنیت نیست؛ Backend مرجع authorization است. permission check
  سمت UI فقط UX را کنترل می‌کند و UI همچنان 401/403 را به‌درستی مدیریت می‌کند.

### ۱۰.۹. route، تست، کیفیت و تحویل

- routeها با React Router و به‌شکل مرکزی تعریف شوند؛ routeهای authenticated guard
  داشته باشند و not-found، access-denied، expired-session و unavailable-service حالت
  ثابت داشته باشند.
- ESLint، Prettier و TypeScript strict باید پیکربندی و اعمال شوند. از شرط‌های عمیق و
  one-linerهای پیچیده اجتناب شود. comment فقط دلیل تصمیم غیر بدیهی، قاعدهٔ business،
  محدودیت یا workaround را توضیح دهد.
- تست unit/component کنار واحد با `*.test.ts(x)` قرار گیرد. Vitest و Testing Library
  outcome قابل مشاهدهٔ کاربر را بسنجند و boundary شبکه mock شود. Playwright برای ورود،
  navigation دارای permission و workflowهای حیاتی است.
- پیش از تحویل، testهای مرتبط، `npm run typecheck` و در تغییر مؤثر بر build،
  `npm run build` اجرا شوند. feature کامل است که type، lint، test، accessibility،
  جداسازی API از UI و حالت‌های loading/error/empty آن تأیید شده باشد.
- `console.log`، debug UI، credential mock و endpoint موقت در production code باقی
  نماند. دادهٔ حساس هرگز log نشود؛ diagnostics در utility متمرکز و قابل غیرفعال‌سازی
  قرار گیرد.

### ۱۰.۱۰. خطوط قرمزِ اجباری در React و مدیریت state

موارد این بخش الزام مطلق هستند و رعایت کامل آن‌ها در تمام کدهای جدید و تغییرات
اجباری است. هیچ feature، component، hook یا workaround نباید بدون بررسی صریح این
قواعد وارد کد production شود.

- **JavaScript خام بدون اجازه ممنوع است.** کد منبع پروژه باید TypeScript/TSX و تا
  حد امکان مبتنی بر React، stateهای React، hookها، Context و componentهای MUI باشد.
  استفاده از فایل یا منطق مستقل JavaScript/JSX، یا افزودن dependency جاوااسکریپتی
  برای کاری که با React، TypeScript، پلتفرم وب یا componentهای مشترک قابل انجام است،
  بدون تصمیم ثبت‌شده و تأیید صریح مجاز نیست. TypeScript پس از build به JavaScript
  تبدیل می‌شود و این تبدیل، مجوز استفاده از JavaScript خام در source نیست.
- **دورزدن React برای مدیریت UI ممنوع است.** تغییر مستقیم DOM، attribute، class،
  style یا state ظاهری برنامه با `document`، `window`، `innerHTML`،
  `dataset`، دستکاری دستی eventها یا الگوهای imperative نباید برای مدیریت theme،
  زبان، layout، navigation، فرم، dialog، loading یا سایر stateهای UI استفاده شود.
  این stateها باید از React state/props/context و ThemeProvider، به‌همراه CSS و
  componentهای مشترک، مدیریت شوند. دسترسی مستقیم به DOM فقط برای نیاز فنی اجتناب‌ناپذیر
  مانند focus/selection یا اتصال کنترل‌شده به API مرورگر مجاز است؛ باید در hook یا
  component ایزوله، با دلیل ثبت‌شده و بدون جایگزین React انجام شود.
- **اصل‌های React نباید نقض شوند.** componentها باید declarative، قابل پیش‌بینی و
  تک‌مسئولیتی باشند؛ state و side effect باید در محل درست React قرار گیرد؛ از
  mutation مستقیم props/state، منطق کسب‌وکار در render، وابستگی پنهان به DOM و
  lifecycleهای خارج از الگوی hookها پرهیز شود.
- **اصول SOLID باید به‌طور کامل رعایت شوند.** هر component، hook، service و utility
  مسئولیت واحد و مرز روشن داشته باشد؛ وابستگی‌ها از abstraction مناسب عبور کنند؛
  coupling و تکرار غیرضروری ایجاد نشود؛ و توسعهٔ feature جدید بدون شکستن قرارداد
  واحدهای موجود ممکن باشد. هر استثنا باید با دلیل و مالک تصمیم مستند شود.
- **ذخیرهٔ password مطلقاً ممنوع است.** password، رمز عبور فعلی/جدید، PIN، secret
  معادل یا هر مقدار قابل‌بازسازی آن نباید در `localStorage` یا `sessionStorage`،
  cookie، URL، source، log، cache یا state ماندگار مرورگر ذخیره شود. این ممنوعیت
  شامل remember-me و refresh نیز است. نگهداری snapshot غیرحساس کاربر برای بازسازی
  پوسته مجاز است، اما جایگزین اعتبارسنجی cookie نیست. password باید فقط در حافظهٔ
  کوتاه‌عمر فرم و تا زمان ارسال امن باقی بماند
  و پس از submit، success، خطا یا unmount پاک شود.
- **کنترل تحویل:** هر Pull Request یا تغییر feature باید صریحاً بررسی کند که هیچ
  JavaScript خام بدون مجوز، دستکاری imperative رابط، ذخیرهٔ password یا نقض اصول
  React/SOLID ندارد. وجود هر مورد، حتی اگر عملکردی باشد، مانع تأیید و تحویل feature
  است تا اصلاح یا استثنای رسمی ثبت شود.
