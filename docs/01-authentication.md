# راه‌اندازی، اتصال و ورود

## فرم‌ها

- `Splash`
- `LoginForm`

## هدف

برنامه قبل از نمایش فرم ورود، تنظیمات محلی، فونت‌های مورد نیاز، وضعیت قفل/مجوز اجرای سیستم و دسترسی به سرویس پارکینگ را بررسی می‌کند. `Splash` فرم عملیاتی یا تعاملی نیست و کاربر در آن ورودی وارد نمی‌کند.

## جریان کار

```text
اجرای برنامه
  ↓
Splash: آماده‌سازی و بررسی‌های اولیه
  ↓
LoginForm
  ↓
احراز هویت
  ↓
تصمیم‌گیری مسیر: Dashboard یا MainForm
```

## Splash

### مسئولیت‌ها

- نمایش لوگو/تصویر برنامه و شماره نسخه
- نمایش وضعیت مرحله‌ی جاری به کاربر
- بررسی و نصب فونت‌های مورد نیاز برنامه
- بارگذاری تنظیمات محلی برنامه، از جمله آدرس سرور و تنظیمات اجرایی
- شروع بررسی قفل یا مجوز اجرای سیستم
- بررسی دسترسی به سرویس پارکینگ
- انتقال به فرم ورود در صورت موفقیت

### ترتیب مراحل داخلی

1. نمایش Splash و اجرای افکت ورود فرم
2. بررسی فونت‌های مورد نیاز و تلاش برای نصب فونت‌های موجود در پوشه‌ی برنامه
3. دریافت تنظیمات اولیه از فایل پیکربندی
4. بررسی قفل/مجوز اجرای سیستم
5. بررسی اتصال به سرویس با درخواست health check
6. پایان Splash با نتیجه‌ی موفق و نمایش `LoginForm`

### پیش‌بارگذاری داده‌های خودرو در پیاده‌سازی فعلی

پس از بررسی اتصال، برنامه‌ی فعلی دریافت مدل‌ها و رنگ‌های خودرو را آغاز می‌کند و نتیجه را در حافظه‌ی عمومی برنامه قرار می‌دهد. این داده‌ها برای خود Splash کاربردی ندارند و صرفاً برای کاهش زمان انتظار فرم‌های بعدی پیش‌بارگذاری می‌شوند.

این رفتار یک تصمیم پیاده‌سازی در نسخه‌ی ویندوزی است و الزام محصول یا معماری نسخه‌ی وب محسوب نمی‌شود. در نسخه‌ی React می‌توان این داده‌ها را بر اساس نیاز صفحه، هنگام ورود به فرم مربوطه، یا با یک cache و query مشترک دریافت کرد.

### اجزای قابل مشاهده

- تصویر یا لوگوی برنامه
- شماره نسخه با قالب «نسخه ...»
- متن ثابت راهنما مانند «لطفا چند لحظه صبر کنید ...»
- برچسب وضعیت مرحله‌ی جاری، مانند «بررسی فونت‌های برنامه» یا «درحال اتصال به سرور»
- نوار/پنل انتظار تصویری

### وضعیت‌ها

| وضعیت | رفتار UI |
|---|---|
| در حال بررسی | نمایش متن مرحله‌ی جاری و پنل انتظار |
| فونت ناقص | تلاش برای نصب فونت‌های همراه برنامه؛ در صورت شکست کلی، اجرای بررسی ادامه پیدا می‌کند |
| تنظیمات نادرست | نمایش خطای تنظیمات اولیه و خروج از برنامه |
| قفل/مجوز نامعتبر | نمایش پیام خطا و توقف ادامه‌ی اجرا |
| سرویس در دسترس نیست | نمایش پیام «اتصال با سرویس پارکینگ برقرار نشد» و خروج از برنامه |
| بررسی موفق | پایان Splash با `DialogResult.OK` و نمایش `LoginForm` |

## LoginForm

## ظاهر و اجزای فرم

فرم فعلی یک پنجره‌ی کوچک و بدون نوار عنوان است و شامل این اجزا است:

- عنوان «سیستم مدیریت پارکینگ»
- تصویر یا لوگوی برنامه
- کنترل مشترک `EosLogin`
- دکمه‌ی تأیید ورود
- دکمه‌ی لغو یا بستن فرم
- دکمه/گزینه‌ی عدم تأیید در پوسته‌ی فرم پایه، در صورت نمایش توسط layout مشترک

کنترل `EosLogin` شامل نام کاربری، رمز عبور، گزینه‌ی «کلمه عبور ذخیره شود» و بخش کپچا است. کپچا در شروع مخفی است و فقط در صورتی که پاسخ ناموفق API تصویر کپچا داشته باشد نمایش داده می‌شود.

### ورودی‌ها

- نام کاربری
- رمز عبور
- کد امنیتی/کپچا در UI، فقط در صورت درخواست سرویس

### اعتبارسنجی سمت UI

- نام کاربری نباید خالی باشد.
- رمز عبور نباید خالی باشد.
- در پیاده‌سازی فعلی، کپچا در `IsValid` کنترل مشترک جزو شروط اعتبارسنجی نیست.
- در صورت نامعتبر بودن ورودی، درخواست به API ارسال نمی‌شود و پیام اعتبارسنجی نمایش داده می‌شود.
- فشردن `Enter` در نام کاربری، فوکوس را به رمز عبور منتقل می‌کند.
- فشردن `Enter` در ورودی کپچا، عملیات ورود را اجرا می‌کند.

### رفتار دکمه‌ها

| عملیات | رفتار |
|---|---|
| تأیید/ورود | اعتبارسنجی، ارسال درخواست login و نمایش وضعیت انتظار |
| لغو | بستن فرم ورود و پایان اجرای برنامه |
| ورود موفق | مخفی‌شدن Login، ذخیره‌ی context کاربر و بازشدن مسیر بعدی |
| بازگشت با وضعیت Retry | نمایش دوباره‌ی Login برای ورود مجدد |

### خروجی موفق

- اطلاعات کاربر جاری
- token احراز هویت
- فهرست یا دسترسی پارکینگ‌ها
- سطح دسترسی کاربر

### آماده‌سازی درخواست

قبل از ارسال، رمز عبور با helper داخلی برنامه رمزنگاری می‌شود و همراه flag مربوط به رمزنگاری‌شدن مقدار ارسال می‌شود. پاسخ موفق به `UserDto` تبدیل می‌شود و موارد زیر در context برنامه قرار می‌گیرند:

در کد فعلی، مقدار فیلد کپچا هنگام ساخت `UserDto` در `LoginForm` به‌صورت صریح تنظیم نشده است. بنابراین باید در بررسی قرارداد API مشخص شود که کپچا در این سناریو چگونه و در کدام property یا مکانیزم منتقل می‌شود؛ مستندات نسخه‌ی وب نباید تا قبل از این تأیید، رفتار کپچا را قطعی فرض کند.

- `CurrentUser`
- `UserToken`
- نام کاربری ذخیره‌شده برای پیشنهاد ورود بعدی

### ذخیره‌ی اطلاعات ورود در نسخه‌ی فعلی

- نام کاربری در تنظیمات محلی برنامه ذخیره می‌شود و هنگام بازشدن Login دوباره در فیلد نام کاربری قرار می‌گیرد.
- کنترل Login فهرست کاربران قبلی را از فایل محلی مخصوص رمزها می‌خواند.
- پس از ورود موفق، رمز عبور در فایل محلی مخصوص ذخیره می‌شود؛ علامت گزینه‌ی «کلمه عبور ذخیره شود» تعیین می‌کند که رمز ذخیره‌شده در ورود بعدی قابل بازیابی خودکار باشد یا نه.
- این جزئیات، رفتار فعلی برنامه‌ی ویندوزی هستند و نباید مستقیماً به طراحی امنیتی نسخه‌ی وب منتقل شوند.

### تطبیق رفتار username با استاندارد وب

#### رفتار فعلی برنامه

آخرین نام کاربریِ ورود موفق در تنظیمات محلی با کلید `UserLogin` ذخیره می‌شود. هنگام بازشدن `LoginForm`، همین مقدار دوباره در فیلد username قرار می‌گیرد؛ بنابراین username به‌صورت پیش‌فرض پر است، اما کاربر می‌تواند آن را تغییر دهد.

#### ارزیابی برای نسخه‌ی وب

این رفتار از نظر تجربه‌ی کاربری قابل قبول است، اما در وب بهتر است با قابلیت‌های استاندارد مرورگر و password manager پیاده‌سازی شود، نه با ذخیره‌ی دستی credential در local storage یا cookie قابل دسترسی برای JavaScript.

| موضوع | پیشنهاد نسخه‌ی وب |
|---|---|
| username | استفاده از `autocomplete="username"` |
| رمز عبور فعلی | استفاده از `type="password"` و `autocomplete="current-password"` |
| پیش‌پرکردن username | اجازه‌ی استفاده از autofill مرورگر یا password manager؛ در صورت نیاز می‌توان آخرین username غیرحساس را جداگانه نگهداری کرد |
| ذخیره‌ی رمز عبور | ذخیره‌سازی دستی رمز در local storage، session storage یا cookie ممنوع؛ استفاده از password manager مرورگر یا سازوکار امن سمت سرور |
| گزینه‌ی «مرا به خاطر بسپار» | باید از ذخیره‌ی رمز جدا باشد و با session/refresh-token امن، انقضا و امکان لغو نشست طراحی شود |
| ارتباط | صفحه‌ی ورود و endpoint احراز هویت باید فقط روی HTTPS باشند |
| کپچا یا کد یک‌بارمصرف | در صورت استفاده، با `autocomplete="one-time-code"` و قرارداد مشخص API طراحی شود |

در نتیجه، نیازمندی محصول برای نسخه‌ی وب این است: «در صورت ورود موفق، امکان پیشنهاد یا تکمیل خودکار آخرین username وجود داشته باشد؛ نحوه‌ی ذخیره و تکمیل باید با password manager و سیاست امنیتی وب سازگار باشد.» الزام به کپی‌کردن فایل‌ها و رفتار ذخیره‌سازی نسخه‌ی ویندوز وجود ندارد.

مرجع استاندارد فیلدهای autofill: [WHATWG HTML Standard](https://html.spec.whatwg.org/dev/form-control-infrastructure.html). راهنمای کاربردی فیلدهای login: [MDN Passwords](https://developer.mozilla.org/en-US/docs/Web/Security/Authentication/Passwords).

## تصمیم‌گیری بعد از ورود

پس از ورود موفق، برنامه بر اساس نوع کاربر، پارکینگ جاری و مجوزهای دسترسی مسیر بعدی را تعیین می‌کند:

```text
کاربر وارد شد
  ├── مجوز مدیریت سطح سیستم و فهرست پارکینگ‌ها دارد
  │     └── نمایش DashboardForm و فهرست پارکینگ‌ها
  └── فقط به یک پارکینگ دسترسی دارد
        └── بازکردن مستقیم MainForm همان پارکینگ
```

در پیاده‌سازی فعلی، `DashboardForm` ابتدا ساخته می‌شود؛ اما برای کاربری که `CurrentParking` دارد و مجوز `DashbordManaging` را ندارد، پارکینگ جاری پیدا شده و `MainForm` مستقیماً باز می‌شود. بنابراین داشبورد در این حالت عملاً به کاربر نمایش داده نمی‌شود.

### حالت‌های کاربری ویژه

- کاربر دارای مجوز مدیریت سطح سیستم و فهرست پارکینگ‌ها: منوی همبرگری «پارکینگ‌ها» را می‌بیند و یکی از رکوردها را انتخاب می‌کند.
- کاربر محدود به یک پارکینگ: مستقیماً وارد محیط همان پارکینگ می‌شود.
- کاربران محصول دو گروه اصلی دارند: اپراتورها که با برنامه ویندوزی کار می‌کنند، و پارکبان‌ها که از نرم‌افزار اندرویدی استفاده می‌کنند. در برنامه ویندوزی، نوع کاربری `Parkban` برای گروه پارکبان‌هاست؛ بنابراین برخی قابلیت‌های مدیریتی ویندوز برای آن‌ها محدود یا پنهان می‌شود.
- کاربر با نوع `ExitPermissionManager`: مسیر و گزینه‌های مرتبط با مجوز خروج برای او نمایش داده می‌شود.

### خطاها

- نام کاربری یا رمز عبور نادرست
- قطع ارتباط با API
- در دسترس نبودن سرویس یا gateway
- پاسخ خطادار همراه با پیام سرویس
- پاسخ خطادار همراه با تصویر کپچا
- کاربر بدون دسترسی به پارکینگ
- خطای اعتبارسنجی ورودی

در خطای عمومی، پیام سرویس در صورت وجود نمایش داده می‌شود؛ اگر پیام قابل استفاده‌ای وجود نداشته باشد، پیام پیش‌فرض نمایش داده می‌شود. در خطاهای مرتبط با سرویس، فرم Login باقی می‌ماند تا کاربر بتواند دوباره تلاش کند.

## APIها و سرویس‌های مشاهده‌شده

- `Utils/hi?key=asd` برای health check سرویس
- `ParkingApi.GetCarModelsAndColors` برای پیش‌بارگذاری مدل‌ها و رنگ‌های خودرو در پیاده‌سازی فعلی؛ این درخواست بخشی از نیازمندی خود Splash نیست.

بررسی احراز هویت کاربر در `LoginForm` و با endpoint زیر انجام می‌شود:

- `UserApi.Login`

## مسیر بعد از Login

پس از پاسخ موفق، Login مخفی می‌شود و `DashboardForm` باز می‌شود. Dashboard بر اساس سطح دسترسی و پارکینگ جاری، یا فهرست پارکینگ‌ها را نشان می‌دهد یا کاربر را مستقیماً به `MainForm` پارکینگ جاری می‌فرستد. اگر Dashboard با وضعیت `Retry` بسته شود، Login دوباره نمایش داده می‌شود؛ در غیر این صورت فرم Login بسته می‌شود.

> این توصیف مربوط به جریان برنامه‌ی Windows است. در نسخه وب، route مقصد `Home` است، Dashboard مستقل وجود ندارد، و امکانات سطح سیستم زیر بخش «مدیریت سامانه» برای مدیر سیستم قرار می‌گیرند. آیتم «پارکینگ‌ها» در این بخش فقط به فهرست رکوردهای پارکینگ و فرم ایجاد/ویرایش آن‌ها اشاره دارد.

## نیازمندی نسخه‌ی وب

- صفحه‌ی login مستقل
- نگهداری امن session/token
- guard برای مسیرهای محافظت‌شده
- نمایش پارکینگ‌های قابل دسترسی پس از ورود
- امکان خروج و تعویض کاربر
- نمایش خطای قابل فهم بدون افشای جزئیات داخلی
- طراحی آگاهانه‌ی قابلیت «مرا به خاطر بسپار» با storage امن؛ ذخیره‌ی رمز به شکل فعلی نباید کپی شود

## مسیرها و ارتباط صفحه‌ها

| مسیر | صفحه | جایگاه و رفتار |
|---|---|---|
| `/` | `Login2Page` | صفحه‌ی اصلی ورود با طراحی جدید و فرم احراز هویت عادی |
| `/login` | `Login2Page` | مسیر نام‌گذاری‌شده‌ی همان صفحه‌ی اصلی ورود |
| `/login2` | `LoginPage` | صفحه‌ی ورود کلاسیک شامل پنل معرفی، دیاگرام پارکینگ و فرم ورود |
| `/sso/callback` | `SsoCallbackPage` | دریافت callback ورود یکپارچه و تکمیل احراز هویت |
| `/home/*` | `Home` | محیط محافظت‌شده پس از احراز هویت |

کاربر احرازنشده‌ای که به `/home/*` برسد با `Navigate` به `/` هدایت می‌شود. پس از
ورود موفق از هر یک از دو صفحه، `App.authenticate` نشست غیرحساس کاربر را ثبت می‌کند
و مسیر را با جایگزینی history به `/home` می‌برد. در صورت نامعتبر شدن نشست نیز
اطلاعات نشست پاک و کاربر به `/` بازگردانده می‌شود.

## صفحه‌ی اصلی ورود (`Login2Page`)

### هدف و ساختار UI

صفحه‌ی اصلی ورود یک صفحه‌ی عملیاتی با ظاهر شیشه‌ای و تم‌محور است که علاوه بر فرم
احراز هویت، هویت سامانه و مفاهیم امنیت، سرعت و مدیریت پارکینگ را نمایش می‌دهد.

- پس‌زمینه با grid، orbit و رنگ‌های semantic تم ساخته می‌شود و بخشی از اطلاعات عملیاتی
  واقعی پارکینگ نیست.
- در بخش معرفی، عنوان فارسی «پارکینگ مدیریت هوشمند تردد» و زیرعنوان «شرکت علم و صنعت»
  نمایش داده می‌شود؛ «پارکینگ» بخش اصلی و «مدیریت هوشمند تردد» بخش کوچک‌تر عنوان است.
- سه شاخص معرفی همراه آیکن نمایش داده می‌شود: «امنیت و دسترسی»، «دقت و سرعت» و
  «مدیریت و یکپارچگی». این شاخص‌ها متن معرفی هستند و مقدار عددی یا داده‌ی زنده ندارند.
- visual پارکینگ یک نقشه‌ی شماتیک ثابت و تزئینی است و شامل نوار وضعیت، مسیر ورود،
  گیت، خانه‌های پارکینگ `A1` تا `B3`، sensorها و برچسب `ZONE A / LEVEL 01` است.
  این visual به API ظرفیت، گیت، sensor یا جای پارک متصل نیست.
- کارت ورود ظاهر glass و border دارد و عنوان آن «مرکز کنترل پارکینگ» است. لوگوی
  برنامه از `public/eos-parking-logo.png` بارگذاری می‌شود و filterهای CSS آن را با
  حالت روشن/تیره و paletteهای green و slate هماهنگ می‌کنند.
- در کارت ورود، متن راهنما، نام کاربری، رمز عبور، گزینه‌ی «مرا به خاطر بسپار»،
  کنترل نمایش/پنهان‌سازی رمز و دکمه‌ی «ورود به سیستم» قرار دارد.
- دکمه‌ی تغییر زبان در topbar قرار دارد و direction صفحه از زبان فعال تعیین می‌شود.

### فیلدها و اعتبارسنجی

| فیلد/کنترل | رفتار فعلی |
|---|---|
| نام کاربری | اجباری؛ مقدار trim‌شده برای login ارسال می‌شود؛ `autocomplete="username"` و direction لاتین دارد |
| رمز عبور | اجباری؛ به‌صورت password نمایش داده می‌شود؛ با آیکن قابل نمایش/پنهان‌سازی است؛ `autocomplete="current-password"` دارد |
| «مرا به خاطر بسپار» | فقط username غیرحساس را در کلید `eos-parking-remembered-username` در localStorage ذخیره یا حذف می‌کند؛ رمز عبور ذخیره نمی‌شود |
| «ورود به سیستم» | در زمان درخواست غیرفعال می‌شود و spinner جای متن دکمه را می‌گیرد |
| تغییر زبان | زبان بین فارسی و انگلیسی تغییر می‌کند و متن‌ها، جهت و locale رابط را تغییر می‌دهد |

اگر username خالی باشد پیام `usernameRequired` و اگر password خالی باشد پیام
`passwordRequired` نمایش داده می‌شود و API فراخوانی نمی‌شود. خطای 401 به پیام
ورود نامعتبر و سایر خطاهای درخواست به پیام خطای درخواست تبدیل می‌شوند. خطای API
در بالای فرم با `Alert` نمایش داده می‌شود.

### حالت SSO در صفحه‌ی اصلی

اگر `appConfig.ssoUiBaseUrl` مقدار داشته باشد، فرم عادی نمایش داده نمی‌شود. صفحه یک
کارت وضعیت شامل لوگو/عنوان، spinner و متن «در حال آماده‌سازی ورود یکپارچه…» نشان
می‌دهد و `beginSsoLogin` را یک‌بار اجرا می‌کند. خطای شروع SSO با پیام خطا در همان
کارت نمایش داده می‌شود. ادامه‌ی callback در `/sso/callback` انجام می‌شود.

در شروع ورود، UI ابتدا `POST api/user/SsoPkce` را صدا می‌زند. در پیاده‌سازی فعلی،
تولید `code_verifier` و `code_challenge` در Backend انجام می‌شود؛ Backend با ۳۲ بایت
تصادفی verifier را می‌سازد و challenge را از SHA-256 و Base64Url آن تولید می‌کند.
UI جفت دریافت‌شده را همراه `clientId`، `redirectUri`، `state` و زمان ایجاد درخواست
در `sessionStorage` با کلید `eos-parking-pending-sso` نگه می‌دارد. این درخواست پس از
۱۰ دقیقه منقضی می‌شود.

سامانه SSO می‌تواند callback را با `authorizationCode` یا نام قدیمی‌تر `code` برگرداند.
اگر `error` برگردد، UI مقدار `error_description` را برای نمایش استفاده می‌کند. در
نسخه فعلی Provider معمولاً `state` را برنمی‌گرداند؛ اگر state برگشت داده شود، UI آن
را با مقدار ذخیره‌شده مقایسه می‌کند. پس از خطای موقت Backend، verifier تا موفقیت
`SsoLogin` پاک نمی‌شود تا retry امکان‌پذیر باشد.

### تنظیمات قابل تغییر پس از Build

رابط کاربری در شروع، تنظیمات عمومی قابل نمایش را از endpoint زیر دریافت می‌کند:

```text
GET /api/Utils/GetClientConfig
```

این endpoint بدون نیاز به ورود قابل فراخوانی است، چون قبل از احراز هویت برای تصمیم‌گیری درباره‌ی SSO استفاده می‌شود. در وضعیت فعلی فقط بخش SSO برگردانده می‌شود و ساختار پاسخ برای اضافه‌شدن بخش‌های عمومی دیگر قابل توسعه است:

```json
{
  "Values": {
    "Sso": {
      "Enabled": true,
      "SsoUiBaseUrl": "https://etspanel.elmosanat.com/",
      "ClientId": "Hsh123456"
    }
  }
}
```

مقادیر SSO از تنظیمات سرویس API خوانده می‌شوند:

```text
Services/EosParkingApiWindowsService/App.config
```

کلیدهای فعلی `SsoEnabled`، `SsoUiBaseUrl`، `SsoBaseUrl`، `SsoClientId`،
`SsoTokenPath` و `SsoLogoutPath` هستند. `SsoUiBaseUrl` آدرس عمومی صفحه‌ی authorization
است و `SsoBaseUrl` آدرس Backend SSO برای تبادل کد و خروج است؛ این دو ممکن است دامنه‌های
متفاوتی داشته باشند. اگر `SsoEnabled` وجود نداشته باشد، Backend برای سازگاری با نصب‌های
قدیمی، وجود `SsoBaseUrl` و `SsoClientId` را ملاک فعال‌بودن قرار می‌دهد. همچنین اگر
`SsoUiBaseUrl` تنظیم نشده باشد، مقدار `SsoBaseUrl` به‌عنوان fallback استفاده می‌شود.
در UI، SSO فقط زمانی فعال می‌شود که مقدار Enabled، آدرس عمومی و Client ID معتبر باشند.
در صورت خطا یا در دسترس نبودن API تنظیمات، UI به‌صورت fail-closed فرم ورود معمولی را
نمایش می‌دهد.

برای تعیین آدرس اولیه‌ی API، فایل bootstrap زیر همچنان کنار خروجی Frontend قابل تنظیم است:

```text
<web-root>/config.json
```

این فایل همراه Build در پوشه‌ی `dist` قرار می‌گیرد و مشتری می‌تواند پس از انتشار،
بدون Build مجدد، مقدار `apiBaseUrl` را تغییر دهد. نمونه:

```json
{
  "apiBaseUrl": "/backend"
}
```

در محیط توسعه، Vite مسیر `/backend` را به API محلی روی پورت `3001` proxy می‌کند. در
محیط مشتری، همین مقدار را می‌توان به آدرس واقعی API تغییر داد؛ برای نمونه
`http://server:3001/` یا آدرس عمومی API.

در صورت نیاز، endpoint API می‌تواند در آینده فیلدهای عمومی دیگری مانند
`parkingServiceUrl`، `anprSignalRUrl` و Feature Flagها را نیز در همین پاسخ برگرداند.
اطلاعات حساس مانند Secret SSO، رمز دیتابیس و کلیدهای داخلی نباید در پاسخ این
endpoint یا فایل `config.json` قرار بگیرند.

برنامه ابتدا فایل bootstrap و سپس endpoint API را با `cache: no-store` و قبل از
Mount شدن React دریافت می‌کند. اگر API تنظیمات در دسترس نباشد، SSO فعال نمی‌شود
و فرم ورود معمولی نمایش داده می‌شود.

Redirect URI همچنان به‌صورت runtime از دامنه‌ی جاری ساخته می‌شود:

```text
https://<customer-host>/sso/callback
```

این URI باید در سامانه‌ی SSO ثبت شود. وب‌سرور نیز باید درخواست مستقیم به مسیر
`/sso/callback` را به `index.html` برگرداند تا React Router callback را پردازش
کند. فایل `config.json` باید از همان origin وب و با دسترسی خواندن عمومی سرو شود.

## صفحه‌ی ورود کلاسیک (`LoginPage`)

این صفحه در مسیر `/login2` در دسترس است و فرم احراز هویت آن از همان `useLogin` و
سرویس مشترک `authService.login` استفاده می‌کند.

- پنل معرفی شامل لوگوی EOS، عنوان سامانه، متن معرفی، دیاگرام شماتیک پارکینگ،
  سه ویژگی «امنیت و دسترسی کنترل‌شده»، «تصمیم‌گیری سریع در عملیات» و «اتصال زنده
  به تجهیزات» و footer سامانه است.
- دیاگرام شامل خانه‌های پارکینگ، دو مسیر، گیت، دو تصویر شماتیک خودرو و nodeهای
  تصویری است؛ این دیاگرام داده‌ی زنده از API دریافت نمی‌کند.
- کارت فرم شامل عنوان، subtitle، نام کاربری، رمز عبور، گزینه‌ی یادآوری username،
  دکمه‌ی ورود و footer نسخه است.
- در حالت SSO، به‌جای پنل و فرم، کارت وضعیت SSO نمایش داده می‌شود و خطا با `Alert`
  ارائه می‌گردد.
- اعتبارسنجی، نمایش/پنهان‌سازی رمز، loading، ذخیره‌ی username و مسیر موفق ورود
  با صفحه‌ی اصلی ورود هم‌رفتار است؛ تفاوت آن در layout و اجزای معرفی است.

## جریان ورود مشترک دو صفحه

```text
نمایش Login2Page در / یا /login، یا LoginPage در /login2
  ↓
اعتبارسنجی username و password در UI
  ↓
useLogin.submit
  ↓
authService.login → apiRequest('api/user/Login', POST)
  ↓
اعتبارسنجی و نگاشت پاسخ در contracts.ts
  ↓
App.authenticate
  ↓
ثبت snapshot غیرحساس کاربر و انتقال به /home
```

## وضعیت پوشش API در React

**وضعیت:** نام endpoint مشخص؛ قرارداد پاسخ در boundary کلاینت با Zod بررسی می‌شود،
اما قرارداد رسمی Backend و Controller در این workspace بررسی نشده است.

| API | method | request فعلی | response/اثر UI | وضعیت |
|---|---|---|---|---|
| `api/user/SsoPkce` | `POST` | بدون payload | Backend یک `CodeVerifier` و `CodeVerifierChallenge` برمی‌گرداند؛ UI آن‌ها را برای callback موقتاً نگه می‌دارد | پیاده‌سازی‌شده |
| `api/user/Login` | `POST` | `{ UserName, UserPass, UserPassEncrypted }`؛ مقدار `UserPass` بر اساس تنظیم legacy ممکن است رمزنگاری شود | پاسخ با `ResponseResultType`، کاربر در `Values/values`، token احتمالی، permissionها و پیام خطا خوانده می‌شود؛ پاسخ موفق به `HomeUser` نگاشت و کاربر به `/home` هدایت می‌شود | نام endpoint مشخص؛ قرارداد رسمی نیازمند تأیید Backend |
| `api/user/SsoLogin` | `POST` | `authorizationCode`, `ClientId`, `RedirectUri`, `CodeVerifier` | Backend ClientId را بررسی، کد را با `OAuthToken` تعویض، کاربر فعال محلی را تطبیق و cookie `EosSession` را صادر می‌کند؛ خطاهای کاربردی معمولاً داخل wrapper و با HTTP 200 برمی‌گردند | پیاده‌سازی‌شده |
| `api/user/Logout` | `POST` | بدون payload | Backend نشست داخلی و cookie را پاک و در صورت وجود mapping، logout مرکزی را اجرا می‌کند؛ UI در هر حالت وضعیت محلی را پاک و به `/` برمی‌گردد | پیاده‌سازی‌شده |

`useLogin` وضعیت pending را نگه می‌دارد و خطای HTTP 401 را از خطاهای عمومی جدا
می‌کند. پاسخ login از شکل‌های legacy شامل `ResponseResultType`، `Values/values`،
نام‌های PascalCase/camelCase و token در wrapper یا user پشتیبانی می‌کند. پاسخ SSO
همچنین wrapperهای `Data/data` و فیلدهای `Token`، `UserName`، `error` و
`error_description` را از Provider پشتیبانی می‌کند. `PreferencesJson` در صورت معتبر
بودن برای تنظیم زبان، حالت نمایش و رنگ‌های SSO پردازش می‌شود.

## حالت‌های صفحه و محدودیت‌های فعلی

| حالت | رفتار |
|---|---|
| initial | فرم ورود و visual ثابت صفحه نمایش داده می‌شوند؛ username ممکن است از localStorage بازیابی شود |
| validation error | خطای نزدیک فیلد نمایش داده می‌شود و request ارسال نمی‌شود |
| loading | submit غیرفعال و spinner نمایش داده می‌شود |
| API error | پیام خطای قابل نمایش در `Alert` قرار می‌گیرد و فرم باقی می‌ماند |
| SSO starting | spinner و پیام آماده‌سازی SSO نمایش داده می‌شود |
| SSO error | پیام خطای شروع SSO در کارت وضعیت نمایش داده می‌شود |
| success | snapshot غیرحساس user ذخیره و `/home` باز می‌شود |
| expired/invalid session | session پاک و `/` باز می‌شود |
| responsive | layout در viewport باریک stack می‌شود؛ visual تزئینی کوچک‌تر می‌شود و فرم قابل استفاده باقی می‌ماند |

دو visual پارکینگ صرفاً بخشی از presentation هستند و نباید به‌عنوان وضعیت ظرفیت،
درب، sensor، خودرو یا تجهیزات در مستندات محصول یا تصمیم‌گیری عملیاتی تفسیر شوند.
متن‌های اختصاصی `Login2Page` در حال حاضر در constant محلی `copy` قرار دارند؛ برای
انطباق کامل با قاعده‌ی ترجمه‌ی مشترک پروژه، انتقال این متن‌ها به resourceهای مستقل
`src/locales/` یک مورد باز فنی است.

### ماندگاری نشست در refresh

پس از ورود موفق، Backend token را در cookie امن و `HttpOnly` صادر می‌کند؛ UI حق
خواندن یا ذخیره‌کردن token در `localStorage`/`sessionStorage` و ارسال آن در header
یا query string را ندارد. UI فقط snapshot غیرحساس کاربر را برای بازسازی پوسته پس از
refresh نگه می‌دارد و تمام requestها را با `credentials: include` می‌فرستد. Logout
باید endpoint Backend را صدا بزند تا token سمت سرور باطل و cookie پاک شود، سپس
snapshot محلی حذف و کاربر به Login برگردانده شود.

در Backend، طول عمر پیش‌فرض token داخلی ۳۶۰ دقیقه است. cookie با نام `EosSession`،
`HttpOnly` و `SameSite=Lax` است و ویژگی `Secure` بر اساس `AuthCookieSecure` تنظیم
می‌شود. Backend برای سازگاری با کلاینت‌های قدیمی Header `UserToken` را نیز می‌پذیرد،
اما UI جدید از آن استفاده نمی‌کند. توکن SSO مرکزی پس از ورود در حافظه‌ی فرآیند Backend
و به‌ازای token داخلی نگه‌داری می‌شود تا هنگام Logout برای خروج مرکزی استفاده شود.
