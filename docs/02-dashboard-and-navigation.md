# DashboardForm؛ مدیریت سطح بالای سیستم

**وضعیت سند:** رفتار UI گزارشات کلی مستند شده؛ قرارداد API ناقص

## هدف فرم

`DashboardForm` صفحه‌ی مرکزی پس از ورود کاربر است. این فرم برای انتخاب پارکینگ، دسترسی به امکانات مدیریتی در سطح کل سیستم، گزارش‌های چندپارکینگی و بعضی عملیات ویژه استفاده می‌شود.

`DashboardForm` با `MainForm` تفاوت دارد:

- `DashboardForm`: مدیریت و مشاهده‌ی چندپارکینگ یا امکانات سراسری سیستم
- `MainForm`: مدیریت جزئیات یک پارکینگ مشخص

## تصمیم محصول برای نسخه وب

در نسخه وب، `DashboardForm` به‌عنوان صفحه یا منوی مستقل نمایش داده نمی‌شود. محتوای اولیه‌ی آن در route `Home` قرار می‌گیرد و امکانات مدیریتی سطح سیستم زیر منوی «مدیریت پارکینگ‌ها» سازمان‌دهی می‌شوند.

- `Home` صفحه‌ی اولیه‌ی مشترک پس از ورود است.
- منوی «مدیریت پارکینگ‌ها» فقط برای مدیر سیستم یا کاربری که مجوز مدیریت داشبورد/پارکینگ‌ها را دارد نمایش داده می‌شود.
- تفاوت کاربرها در این سطح فقط تعداد منوهای قابل مشاهده و دسترسی آن‌هاست؛ کاربر معمولی/پارکبان منوی مدیریت پارکینگ‌ها را نمی‌بیند.
- در صورت وجود فهرست پارکینگ، اولین پارکینگ به‌صورت پیش‌فرض انتخاب می‌شود و اطلاعات آن در `Home` نمایش داده می‌شود.
- مدیر سیستم می‌تواند از `Home` بین پارکینگ‌های مجاز جابه‌جا شود؛ انتخاب پارکینگ برای ورود به `MainForm` نیز از منوی مدیریت پارکینگ‌ها در دسترس است.
- قابلیت‌های سیستم مانند کاربران، سطوح دسترسی، گزارش‌های کلی، مجوز خروج و ایجاد پارکینگ به‌صورت زیرمنوی مدیریت پارکینگ‌ها قرار می‌گیرند؛ این قابلیت‌ها جزو یک داشبورد مستقل نیستند.
- شاخص‌های عملیاتی مانند ظرفیت، ورود، خروج و فعالیت‌های یک پارکینگ به `MainForm`/مدیریت پارکینگ جاری تعلق دارند، نه بخش مدیریت سطح سیستم.

## مسیر ورود و خروج

```text
LoginForm
  ↓
DashboardForm
  ├── کاربر مدیریتی → مشاهده‌ی داشبورد و انتخاب پارکینگ
  ├── کاربر محدود → انتقال مستقیم به MainForm پارکینگ جاری
  └── کاربر ویژه → نمایش امکانات مجاز همان نوع کاربر
```

در پیاده‌سازی فعلی، Dashboard بعد از ورود ساخته می‌شود. اگر کاربر `CurrentParking` معتبر داشته باشد و مجوز `DashbordManaging` را نداشته باشد، پس از دریافت فهرست پارکینگ‌ها، `MainForm` همان پارکینگ مستقیماً باز می‌شود و Dashboard به کاربر نمایش داده نمی‌شود. از نظر محصول، کاربران دو گروه اصلی دارند: اپراتورها که با برنامه ویندوزی کار می‌کنند و پارکبان‌ها که از نرم‌افزار اندرویدی استفاده می‌کنند. در این برنامه، `Parkban` نوع کاربری گروه دوم است.

## ساختار کلی UI

- عنوان سیستم
- عنوان بخش‌ها: «سیستم» و «پارکینگ ها»
- ناحیه‌ی Tile برای امکانات سیستم
- ناحیه‌ی Tile برای فهرست پارکینگ‌ها
- گزینه‌ی ایجاد پارکینگ جدید
- آیکون بالای صفحه (`simpleButton2`)
- نام شرکت در پایین صفحه
- پنل گزارش‌های کلی، که در ابتدا مخفی است
- پنل انتخاب فیلتر گزارش
- دکمه‌ی نمایش گزارش
- دکمه‌ی بازگشت از گزارش

## چرخه‌ی عمر صفحه

1. Dashboard ساخته می‌شود.
2. بر اساس نوع کاربر، Tileها نمایش یا مخفی می‌شوند.
3. فهرست پارکینگ‌ها از API دریافت می‌شود؛ مگر در مسیرهای ویژه‌ای که نیاز به آن وجود ندارد.
4. اگر کاربر محدود باشد، انتقال مستقیم به پارکینگ جاری انجام می‌شود.
5. در غیر این صورت، Tileهای پارکینگ در صفحه نمایش داده می‌شوند.
6. پس از بازگشت از `MainForm`، فهرست پارکینگ‌ها دوباره دریافت می‌شود.

## ۱. امکانات مدیریتی سیستم

این بخش امکاناتی را دربرمی‌گیرد که به یک پارکینگ خاص محدود نیستند.

### گزینه‌ها

| گزینه | فرم مقصد | رفتار کلی |
|---|---|---|
| کاربران | `UsersForm` | مدیریت کاربران سیستم |
| سطوح دسترسی | `AccessLevelForm` | تعریف و مدیریت مجوزها |

### کنترل دسترسی

- پیش از بازکردن `UsersForm`، مجوز `ParkingUsers` بررسی می‌شود.
- پیش از بازکردن `AccessLevelForm`، مجوز `ParkingAccessLevels` بررسی می‌شود.
- در صورت نداشتن مجوز، فرم مقصد باز نمی‌شود و پیام عدم دسترسی نمایش داده می‌شود.
- علاوه بر مجوز، نوع کاربر نیز می‌تواند باعث مخفی‌شدن Tileها شود.

### رفتار بازگشت

اگر فرم مقصد با نتیجه‌ی `Retry` بسته شود، Dashboard نیز نتیجه‌ی `Retry` را به Login منتقل می‌کند تا مسیر ورود مجدد یا تعویض کاربر انجام شود.

## ۲. گزارش‌های کلی چندپارکینگی

گزارش‌های این بخش در خود Dashboard نمایش داده می‌شوند و به یک پارکینگ انتخاب‌شده در `MainForm` وابسته نیستند.

### ورود به بخش گزارش

```text
انتخاب «گزارشات کلی»
  ↓
نمایش پنل گزارش
  ↓
انتخاب نوع گزارش
  ↓
نمایش Filter Panel
  ↓
انتخاب پارامترها
  ↓
انتخاب «نمایش»
  ↓
تولید گزارش
```

### گزارش‌های موجود

| عنوان | Filter Panel | مفهوم |
|---|---|---|
| مقایسه درآمد ماهانه پارکینگ‌ها | `IncomeFilterPanel` با حالت `0` | مقایسه‌ی درآمد در سطح پارکینگ‌ها |
| مقایسه درآمد پارکینگ‌ها | `IncomeFilterPanel` با حالت `1` | گزارش مقایسه‌ای درآمد |
| مقایسه درآمد سالانه پارکینگ‌ها | `IncomeFilterPanel` با حالت `2` | مقایسه‌ی سالانه |
| عملکرد مالی کاربران | `UserFilterPanel` | بررسی فعالیت مالی کاربران |
| ریز درآمد از پارک آزاد خودروها | `TrafficDetailsFilterPanel` | جزئیات درآمد حاصل از تردد خودروها |

### فیلترهای هر گزارش

#### ۱) مقایسه درآمد ماهانه پارکینگ‌ها

پنل: `IncomeFilterPanel` با `StateValue = 0`

| فیلتر | نوع کنترل | رفتار فعلی |
|---|---|---|
| سال | انتخاب سال شمسی | یک سال انتخاب می‌شود؛ سال جاری در شروع انتخاب شده است |
| انتخاب پارکینگ | انتخاب چندگانه | فهرست از `ParkingApi.Get` می‌آید و در شروع همه پارکینگ‌ها انتخاب می‌شوند |

سال انتخاب‌شده به بازه‌ی اول فروردین تا ۲۹ اسفند همان سال تبدیل می‌شود. درخواست با `TrafficStatisticFilterModel` و endpoint `ReportApi.GetParkingMonthlyIncomingReport` ارسال می‌شود.

#### ۲) مقایسه درآمد پارکینگ‌ها

پنل: `IncomeFilterPanel` با `StateValue = 1`

| فیلتر | نوع کنترل | رفتار فعلی |
|---|---|---|
| سال‌های شمسی | انتخاب چندگانه | سال‌های موجود در کنترل قابل انتخاب‌اند و سال جاری به‌صورت پیش‌فرض انتخاب می‌شود |
| انتخاب پارکینگ | انتخاب چندگانه | فهرست از `ParkingApi.Get` می‌آید و همه در شروع انتخاب می‌شوند |

در کد فعلی برای این گزینه endpoint سالانه (`ReportApi.GetParkingYearIncomingReport`) فراخوانی می‌شود، اما قالب گزارش ماهانه (`ParkingMonthlyIncomingChartReport.mrt`) انتخاب شده است؛ این ناهماهنگی نیازمند تأیید محصول/backend است.

**ثبت رفتار فعلی:** تا زمان تصمیم‌گیری، همین نگاشت به‌عنوان قرارداد مشاهده‌شده‌ی برنامه مستند می‌شود و در این مرحله هیچ اصلاحی در endpoint، فیلتر یا قالب گزارش پیشنهاد یا اعمال نمی‌شود.

#### ۳) مقایسه درآمد سالانه پارکینگ‌ها

پنل: `IncomeFilterPanel` با `StateValue = 2`

| فیلتر | نوع کنترل | رفتار فعلی |
|---|---|---|
| سال‌های شمسی | انتخاب چندگانه | سال‌های انتخاب‌شده در آرایه‌ی `SolarYears` قرار می‌گیرند |
| انتخاب پارکینگ | انتخاب چندگانه | شناسه‌ی پارکینگ‌های انتخاب‌شده در `ParkingIds` قرار می‌گیرد |

برای این گزینه نیز endpoint `ReportApi.GetParkingYearIncomingReport` استفاده می‌شود و خروجی در قالب `ParkingYearlyComparIncomingChartReport.mrt` نمایش داده می‌شود. بازه‌ی تاریخ مستقل از سال انتخابی ارسال نمی‌شود و سال‌ها به‌عنوان فیلتر اصلی گزارش استفاده می‌شوند.

#### ۴) عملکرد مالی کاربران

پنل: `UserFilterPanel`

| فیلتر | نوع کنترل | مقدار پیش‌فرض/اجباری |
|---|---|---|
| تاریخ ورود از | انتخاب تاریخ | یک ماه قبل از تاریخ جاری |
| تا | انتخاب تاریخ | تاریخ جاری |
| نام کاربر | جستجو/انتخاب از فهرست | در مسیر Dashboard نمایش داده می‌شود؛ فهرست کاربران از `UserApi.Get` و بر اساس نام کاربری مرتب می‌شود |

در Dashboard مقدار `userId = 0` است؛ بنابراین انتخاب کاربر در پنل قابل مشاهده است. مقدارهای تاریخ با فرمت میلادی `yyyy/MM/dd` در query قرار می‌گیرند و زمان پایان روز برای تاریخ دوم با `23:59` ارسال می‌شود. endpoint گزارش `ReportApi.GetUserActivity` و پاسخ `List<CashDto>` است.

#### ۵) ریز درآمد از پارک آزاد خودروها

پنل: `TrafficDetailsFilterPanel` با تنظیمات Dashboard زیر:

```text
ShowParkingComboBox = true
ShowJustPresenceCheckBox = false
ShowImageCheckBox = false
```

| فیلتر | نوع کنترل | وضعیت در گزارشات کلی |
|---|---|---|
| تاریخ ورود از / تا | بازه‌ی تاریخ | پیش‌فرض از یک ماه قبل تا امروز |
| انتخاب پارکینگ | انتخاب چندگانه | قابل مشاهده و اجباری؛ در شروع همه انتخاب می‌شوند |
| کد عضویت | متن اختیاری | قابل ورود؛ در payload با `MemberCode` ارسال می‌شود |
| پلاک | کنترل اختصاصی پلاک | اختیاری؛ مقدار پلاک با `Plate` ارسال می‌شود |
| نوع وسیله نقلیه | انتخابی | اختیاری؛ از enum `CarTypes` ساخته می‌شود |
| فقط نمایش حاضرین | checkbox | در این مسیر مخفی است و کاربر Dashboard آن را تغییر نمی‌دهد |
| همراه با تصویر ورود | checkbox | در این مسیر مخفی است و گزارش بدون تصویر تولید می‌شود |

انتخاب حداقل یک پارکینگ اجباری است و در صورت نبود انتخاب، خطای «هیچ پارکینگی انتخاب نشده است» ایجاد می‌شود. درخواست با `ReportDumpParkingsFilterModels` به `ReportApi.GetIncomingDetailsReport` ارسال و خروجی `List<ExitBillDto>` در `TrafficIncomingDetailsReport.mrt` نمایش داده می‌شود.

### قواعد مشترک فیلترها

- انتخاب گزارش، فیلتر قبلی را از `reportFilterPanel` حذف و پنل جدید را جایگزین می‌کند.
- دکمه «نمایش» ابتدا `GetValues()` را اجرا می‌کند؛ فقط در صورت وجود داده، `ShowReport()` فراخوانی می‌شود.
- پاسخ موفق بدون داده به‌صورت پیام «اطلاعاتی یافت نشد» به کاربر اعلام می‌شود.
- خطاهای اعتبارسنجی فیلتر با پیام exception نمایش داده می‌شوند.
- در کد فعلی برای چند فیلتر `GetValuesSync()` پیاده‌سازی نشده است؛ این موضوع نباید بدون تصمیم معماری به نسخه وب منتقل شود.

### کنترل‌های گزارش

- انتخاب گزارش از فهرست یا Accordion
- نمایش فیلتر متناسب با گزارش انتخاب‌شده
- اعتبارسنجی فیلترها قبل از اجرا
- نمایش پیام «اطلاعاتی یافت نشد» در صورت نبود داده
- نمایش خطای اعتبارسنجی در صورت نادرست بودن فیلتر
- بازگشت به نمای اصلی Dashboard

### نکته‌ی معماری

Dashboard نقش هماهنگ‌کننده‌ی فیلتر و نمایش گزارش را دارد؛ منطق فیلتر و تولید خروجی در Filter Panel و قالب گزارش مربوطه قرار دارد. در نسخه‌ی وب بهتر است انتخاب گزارش، فرم فیلتر و viewer/export گزارش از یکدیگر جدا باشند.

### جزئیات رفتار فعلی در کد

با انتخاب Tile «گزارشات کلی»، `reportPanel` نمایش داده می‌شود. این پنل در شروع مخفی است و شامل Accordion گزارش‌ها، عنوان گزارش، پنل فیلتر و دکمه‌های «نمایش» و بازگشت است.

```text
DashboardForm
  ↓ انتخاب «گزارشات کلی»
reportPanel.Show()
  ↓ انتخاب گزارش از Accordion
قرار دادن FilterPanel متناظر در reportFilterPanel
  ↓ «نمایش»
IFilterPanel.GetValues()
  ↓ در صورت داشتن داده
IFilterPanel.ShowReport()
  ↓ بازگشت
reportPanel.Hide()
```

نگاشت واقعی گزینه‌ها به پنل و endpoint به شکل زیر است:

| عنوان UI | پنل | state/تنظیم | endpoint داده | قالب گزارش |
|---|---|---|---|---|
| مقایسه درآمد ماهانه پارکینگ ها | `IncomeFilterPanel` | `0` | `ReportApi.GetParkingMonthlyIncomingReport` | `ParkingMonthlyIncomingChartReport.mrt` |
| مقایسه درآمد پارکینگ ها | `IncomeFilterPanel` | `1` | `ReportApi.GetParkingYearIncomingReport` | در کد فعلی `ParkingMonthlyIncomingChartReport.mrt` |
| مقایسه درآمد سالانه پارکینگ ها | `IncomeFilterPanel` | `2` | `ReportApi.GetParkingYearIncomingReport` | `ParkingYearlyComparIncomingChartReport.mrt` |
| عملکرد مالی کاربران | `UserFilterPanel` | `userId=0` در حالت عمومی | `ReportApi.GetUserActivity` | `UserCashReport.mrt` |
| ریز درآمد از پارک آزاد خودروها | `TrafficDetailsFilterPanel` | انتخاب چند پارکینگ، بدون تصویر/فقط حضور | `ReportApi.GetIncomingDetailsReport` | `TrafficIncomingDetailsReport.mrt` |

در `IncomeFilterPanel` فیلترهای سال شمسی و پارکینگ‌های انتخاب‌شده به `PageFilterModel<TrafficStatisticFilterModel>` تبدیل می‌شوند و اندازه صفحه در کد فعلی `1000000` است. در گزارش عملکرد مالی، بازه تاریخ و کاربر انتخاب می‌شود. در گزارش ریز درآمد، انتخاب حداقل یک پارکینگ الزامی است و در غیر این صورت `EosValidationDataException` نمایش داده می‌شود.

### وضعیت‌های UI و خطا

- قبل از انتخاب گزارش، پنل فیلتر و دکمه نمایش مخفی هستند.
- با انتخاب گزارش، فیلتر جایگزین قبلی می‌شود و دکمه نمایش فعال/قابل مشاهده می‌گردد.
- اگر `GetValues()` مقدار false برگرداند، پیام «اطلاعاتی یافت نشد» نمایش داده می‌شود و viewer باز نمی‌شود.
- خطای اعتبارسنجی فیلتر با پیام exception نمایش داده می‌شود.
- خطای عمومی داخل handler فعلی به‌صورت صریح به کاربر نمایش داده نمی‌شود.
- `GetValuesSync()` در چند FilterPanel پیاده‌سازی نشده و `NotImplementedException` دارد؛ این مورد برای قرارداد وب نیازمند تعیین تکلیف است.

### وضعیت پوشش API گزارشات کلی

وضعیت این بخش **نام endpoint مشخص، اما قرارداد ناقص** است: نام endpointها، نوع request تقریبی، مدل پاسخ و فایل گزارش از کد قابل مشاهده است؛ مسیر HTTP نهایی، method رسمی، schema کامل فیلتر/پاسخ، status codeها، خطاها و مجوز گزارش‌ها از این پروژه به‌صورت کامل تأیید نشده‌اند.

| API | مدل فیلتر/ورودی | پاسخ مصرف‌شده |
|---|---|---|
| `ReportApi.GetParkingMonthlyIncomingReport` | `PageFilterModel<TrafficStatisticFilterModel>` | `List<StatisticsDto>` |
| `ReportApi.GetParkingYearIncomingReport` | `PageFilterModel<TrafficStatisticFilterModel>` | `List<StatisticsDto>` |
| `ReportApi.GetUserActivity` | query شامل تاریخ شروع، پایان و `userId` | `List<CashDto>` |
| `ReportApi.GetIncomingDetailsReport` | `PageFilterModel<ReportDumpParkingsFilterModels>` | `List<ExitBillDto>` |

### رفتار نتیجه، viewer و صفحه‌بندی

پس از دریافت موفق داده، هر FilterPanel نتیجه را در حافظه‌ی فرم (`LatestValues`) نگه می‌دارد و با `ReportsViewer.ShowReportResource` نمایش می‌دهد. قالب‌های گزارش به‌صورت resource داخلی برنامه خوانده می‌شوند؛ بنابراین Dashboard فایل گزارش را از کاربر یا مسیر خارجی دریافت نمی‌کند.

| گزارش | مدل نتیجه | نحوه نمایش فعلی |
|---|---|---|
| مقایسه درآمد ماهانه | `StatisticsDto` | viewer به‌صورت Dialog |
| مقایسه درآمد پارکینگ‌ها | `StatisticsDto` | viewer به‌صورت Dialog |
| مقایسه درآمد سالانه | `StatisticsDto` | viewer به‌صورت Dialog |
| عملکرد مالی کاربران | `CashDto` | viewer پیش‌فرض `ShowReportResource` |
| ریز درآمد پارک آزاد | `ExitBillDto` | viewer پیش‌فرض همراه با پارامتر عنوان بازه تاریخ |

در کد Dashboard برای نمایش گزارش‌های کلی، فراخوانی مستقیمی برای print، export، PDF یا Excel وجود ندارد. وجود یا نبود این امکانات در نوار ابزار viewer از این پروژه قابل تأیید نیست و باید هنگام تست UI یا بررسی کتابخانه‌ی گزارش مشخص شود.

وضعیت صفحه‌بندی فعلی یکسان نیست:

- گزارش‌های درآمدی `PageNumber = 1` و `PageSize = 1000000` ارسال می‌کنند؛ یعنی عملاً انتظار دریافت حجم بسیار بزرگ داده وجود دارد.
- گزارش ریز درآمد `PageNumber = 1` دارد، اما اندازه صفحه در کد فیلتر مشخص نشده است.
- گزارش عملکرد مالی کاربران به‌صورت query string ارسال می‌شود و مدل صفحه‌بندی ندارد.

این رفتار، توصیف برنامه فعلی است؛ برای نسخه وب باید pagination، محدودیت حجم پاسخ، sort و export به‌صورت قرارداد مستقل تعریف شوند.

### کنترل دسترسی گزارشات کلی

در handler انتخاب گزارش، بررسی مستقیمی مانند `CheckUserAccess` وجود ندارد. در `DashboardForm_Shown`، Tile گزارشات کلی برای کاربر نوع `Parkban` مخفی می‌شود؛ برای سایر انواع کاربر، از روی کد موجود مجوز اختصاصی دیگری برای این Tile قابل مشاهده نیست. بنابراین وضعیت فعلی چنین ثبت می‌شود:

| نوع کاربر | وضعیت گزارشات کلی |
|---|---|
| `Parkban` | Tile گزارشات کلی مخفی است |
| `ExitPermissionManager` | در کد نمایش Tile گزارشات کلی صراحتاً غیرفعال نشده است؛ نیازمند تست/تأیید |
| سایر کاربران | Tile قابل نمایش است، مگر منطق بیرونی یا دسترسی سرویس مانع شود |

مخفی‌کردن Tile به‌تنهایی کنترل امنیتی محسوب نمی‌شود؛ API گزارش باید مجوز و محدوده‌ی داده‌ی مجاز کاربر را در سمت سرور بررسی کند.

### وضعیت نهایی پوشش مستندات این بخش

موارد زیر برای رفتار فعلی مستند شده‌اند: مسیر ورود به گزارشات کلی، پنج گزینه گزارش، فیلترهای هر گزینه، endpointهای مشاهده‌شده، مدل‌های نتیجه، قالب‌های `.mrt`، رفتار بدون داده، خطای اعتبارسنجی، viewer و وضعیت صفحه‌بندی. موارد زیر همچنان **نیازمند تأیید بیرونی از کد کلاینت** هستند: مسیر و method رسمی HTTP، schema کامل API، مجوزهای backend، امکانات print/export viewer، timeout/retry و قرارداد pagination.

### ابهام‌ها و موارد نیازمند تأیید

- عنوان «مقایسه درآمد پارکینگ ها» با state `1` به endpoint سالانه متصل است، اما قالب گزارش ماهانه انتخاب می‌شود؛ احتمال ناهماهنگی نام، endpoint یا قالب وجود دارد.
- سطح دسترسی لازم برای Tile گزارشات کلی در handler مستقل بررسی نمی‌شود و بیشتر از منطق visibility نوع کاربر ناشی می‌شود؛ مجوز رسمی باید مشخص شود.
- رفتار صفحه‌بندی، export/print، timeout و retry در viewer و API قرارداد مستقلی ندارد.
- مشخص نیست گزارش عملکرد مالی کاربران در Dashboard باید همه کاربران را نشان دهد یا فقط کاربر انتخاب‌شده را.

## ۳. امکانات ویژه

### استثنا: Tile تنظیمات

در `DashboardForm.Designer.cs` یک Tile با عنوان «تنظیمات» و نام داخلی `tileItem10` تعریف شده است؛ اما این گزینه در اجرای فعلی نمایش داده نمی‌شود:

```csharp
tileItem10.Visible = false;
```

برای این Tile در کد فعلی event کلیک یا فرم مقصدی وجود ندارد. بنابراین «تنظیمات» جزو قابلیت‌های فعال داشبورد محسوب نمی‌شود و فقط به‌عنوان عنصر غیرفعال/استثنا ثبت می‌گردد.

### مجوز خروج

گزینه‌ی «مجوز خروج» برای کاربر نوع `ExitPermissionManager` نمایش داده می‌شود.

```text
DashboardForm
  ↓
انتخاب «مجوز خروج»
  ↓
ExitPermissionForm
```

اگر کاربر نوع مجاز را نداشته باشد، حتی در صورت اجرای event، پیام عدم دسترسی نمایش داده می‌شود و فرم باز نمی‌شود.

### رفتار پارکبان‌ها (`UserTypes.Parkban`)

پارکبان‌ها گروه کاربری محصول هستند که نرم‌افزار اندرویدی دارند؛ موارد زیر محدودیت‌ها و مسیرهای اجرایی آن‌ها در برنامه ویندوزی است:

برای کاربر نوع `Parkban` گزینه‌های زیر در Dashboard مخفی می‌شوند:

- کاربران
- سطوح دسترسی
- گزارش‌های کلی
- مجوز خروج

فهرست پارکینگ‌ها همچنان بارگذاری می‌شود و در صورت داشتن `CurrentParking` و نداشتن مجوز مدیریت داشبورد، ورود مستقیم به `MainForm` انجام می‌شود.

### وضعیت‌های ویژه

| وضعیت | نتیجه |
|---|---|
| کاربر مجاز به مجوز خروج | نمایش Tile مجوز خروج |
| کاربر غیرمجاز | عدم نمایش یا نمایش پیام عدم دسترسی |
| کاربر Parkban | Dashboard محدود و بدون امکانات مدیریتی سراسری |
| کاربر محدود به یک پارکینگ | انتقال مستقیم به MainForm |

## ۴. فهرست و مشاهده/انتخاب پارکینگ‌ها

### هدف

نمایش پارکینگ‌های قابل دسترسی و ورود کاربر به محیط مدیریت هر پارکینگ. هر پارکینگ به‌صورت Tile نمایش داده می‌شود و انتخاب آن، `MainForm` همان پارکینگ را باز می‌کند.

### بارگذاری داده

فهرست پارکینگ‌ها از API زیر دریافت می‌شود:

```text
ParkingApi.Get
```

هر آیتم فهرست شامل موجودیت پارکینگ است و نام پارکینگ به‌عنوان متن Tile نمایش داده می‌شود.

### ایجاد پارکینگ جدید

```text
انتخاب «پارکینگ جدید»
  ↓
ParkingForm
  ↓
ثبت موفق
  ↓
افزودن پارکینگ به فهرست Tileها
```

در صورت لغو یا ثبت ناموفق، آیتم جدیدی به فهرست اضافه نمی‌شود.

در کد فعلی، دکمه‌ی «پارکینگ جدید» فقط برای کاربر نوع `ExitPermissionManager` در `DashboardForm_Shown` مخفی می‌شود. برای سایر نقش‌ها بررسی مجوز مستقیمی در handler ایجاد پارکینگ دیده نمی‌شود؛ مجوز ایجاد باید در `ParkingForm` یا backend کنترل شود.

### انتخاب پارکینگ

```text
انتخاب Tile پارکینگ
  ↓
مخفی‌شدن Dashboard
  ↓
بازشدن MainForm با موجودیت پارکینگ انتخاب‌شده
  ↓
بازگشت به Dashboard یا پایان مسیر
  ↓
بارگذاری دوباره‌ی فهرست پارکینگ‌ها
```

### وضعیت‌های UI

| وضعیت | رفتار پیشنهادی/فعلی |
|---|---|
| در حال بارگذاری | نمایش وضعیت انتظار |
| دریافت موفق | ساخت Tile برای هر پارکینگ |
| فهرست خالی | نمایش empty state مناسب؛ در کد فعلی رفتار صریحی برای آن ثبت نشده است |
| خطای API | نمایش خطای ارتباط یا پیام سرویس؛ در کد فعلی مدیریت این حالت محدود است |
| پارکینگ جدید | افزودن Tile پس از بازگشت موفق از فرم ایجاد |
| بازگشت از MainForm | refresh فهرست پارکینگ‌ها |

### نیازمندی نسخه‌ی وب

- route یا view مستقل برای Dashboard
- نمایش loading، empty و error state
- Tile یا card قابل انتخاب برای هر پارکینگ
- دکمه‌ی ایجاد پارکینگ بر اساس permission
- refresh پس از ایجاد یا ویرایش پارکینگ
- انتقال مستقیم کاربران محدود به route پارکینگ جاری
- عدم نمایش اطلاعات پارکینگ‌هایی که API برای کاربر مجاز نمی‌داند

### عناصر نمایشی بدون workflow فعال

| عنصر | وضعیت فعلی |
|---|---|
| `simpleButton2` در header | در Designer وجود دارد، اما event کلیک یا رفتار اجرایی در `DashboardForm.cs` ندارد؛ عملکرد آن نامشخص/غیرفعال ثبت می‌شود |
| عنوان «سیستم مدیریت پارکینگ» | فقط عنصر نمایشی است |
| عنوان‌های «سیستم» و «پارکینگ ها» | فقط برچسب گروه‌های UI هستند |
| نام شرکت در footer | فقط عنصر نمایشی است |
| Ribbon | در Designer تعریف شده، اما `RibbonVisibility` روی `Hidden` است و مسیر کاربری فعال ندارد |
