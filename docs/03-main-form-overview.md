# MainForm؛ محیط مدیریت پارکینگ جاری

**وضعیت سند:** کلیات و منوها مستند شده؛ جزئیات فرم‌های وابسته جداگانه تکمیل می‌شوند؛ قرارداد API خود فرم ناقص

## شناسنامه فرم

| موضوع | مقدار | وضعیت/منبع |
|---|---|---|
| نام فرم | `MainForm` | رفتار فعلی؛ `EosParkingProfessional/EosForms/MainForm.cs` |
| نوع فرم | فرم اصلی Ribbon برای مدیریت یک پارکینگ | رفتار فعلی؛ ارث‌بری از `EosBaseRibbonForm` |
| ورودی سازنده | `ParkingEntity parking` | رفتار فعلی؛ سازنده‌ی `MainForm` |
| والد منطقی | `DashboardForm` | رفتار فعلی در مسیر انتخاب پارکینگ و انتقال مستقیم کاربر محدود |
| خروجی به مسیر بالادست | `DialogResult.OK`، `DialogResult.Retry` یا `DialogResult.Abort` | رفتار فعلی؛ `MainForm.cs` و متد `ShowForm` |
| محدوده‌ی داده | پارکینگ انتخاب‌شده و قابلیت‌های وابسته به آن | برداشت تحلیلی بر اساس `_parking` و فرم‌های مقصد |
| وضعیت API فرم | ناقص | endpointهای فرم‌های مقصد جدا هستند؛ API وضعیت پارکینگ در ادامه‌ی همین سند ثبت می‌شود |

## هدف و جایگاه

`MainForm` اصلی‌ترین محیط عملیاتی نرم‌افزار است و پس از انتخاب یک پارکینگ از `DashboardForm` باز می‌شود. این فرم context پارکینگ جاری را نگه می‌دارد و منوها، Tileهای دسترسی سریع، گزارش‌ها و فرم‌های وابسته را هماهنگ می‌کند.

```text
DashboardForm
  ↓ انتخاب پارکینگ
MainForm(ParkingEntity)
  ├── تعاریف و پیکربندی پارکینگ
  ├── عملیات ورود، خروج و مانیتورینگ
  ├── گزارش‌های پارکینگ
  ├── ارتباط با سیستم‌های دیگر
  └── ابزار، تغییر کاربر، قفل و خروج
```

این سند فقط قرارداد و رفتار خود `MainForm` را پوشش می‌دهد. جزئیات `ParkingForm`، `MemberForm`، `ManualTrafficControlForm` و سایر فرم‌های مقصد باید در اسناد مستقل نوشته شوند.

### نقش در workflow

`MainForm` مرز ورود کاربر به عملیات یک پارکینگ مشخص است. انتخاب پارکینگ در داشبورد، موجودیت پارکینگ را به این فرم می‌دهد و فرم بر اساس همان موجودیت، منوها و عملیات مربوط به آن را ارائه می‌کند. خود فرم مالک اطلاعات تخصصی اعضا، تردد، تعرفه یا تجهیزات نیست؛ این اطلاعات توسط فرم‌ها و کنترل‌های مقصد مدیریت می‌شوند.

مسیرهای ورود مشاهده‌شده:

1. کاربر پس از ورود، در `DashboardForm` یک Tile پارکینگ را انتخاب می‌کند.
2. کاربری که `CurrentParking` معتبر دارد و مجوز `DashbordManaging` ندارد، پس از منطق تصمیم‌گیری داشبورد مستقیماً به `MainForm` همان پارکینگ منتقل می‌شود.

مسیرهای خروج مشاهده‌شده:

- `OK`: کاربر از گزینه‌ی خروج استفاده می‌کند و فرم بسته می‌شود.
- `Retry`: کاربر «تغییر کاربر» را انتخاب می‌کند؛ نتیجه به مسیر ورود برگردانده می‌شود.
- `Abort`: در خطای بازکردن فرم مقصد، `ShowForm` خطا را نمایش داده و این نتیجه را برمی‌گرداند.

اثر بازگشت از فرم مقصد به `MainForm` به نوع فرم وابسته است. برای نمونه، پس از بازگشت از `ParkingForm` عنوان فرم با `RefreshTitle()` دوباره تنظیم می‌شود. قرارداد عمومی برای refresh داده‌های سایر فرم‌های مقصد در کد فعلی مشخص نشده است.

## context و عنوان صفحه

سازنده‌ی فرم یک `ParkingEntity` دریافت می‌کند. عنوان Ribbon و عنوان پنجره با نام پارکینگ و نام کاربر جاری ساخته می‌شود:

```text
سیستم مدیریت پارکینگ - [نام پارکینگ]     کاربر جاری: [نام کاربری]
```

منبع داده‌ی اصلی فرم:

- پارکینگ جاری: `_parking`
- کاربر جاری: `PublicVariables.CurrentUser`
- token سرویس: `WebHelper.UserToken` که پس از ورود از `CurrentUser.UserToken` مقداردهی می‌شود و برای درخواست‌های بعدی لازم است.
- مجوزهای عملیاتی: `AccessPermissionValuePart1`
- مجوزهای گزارش: `AccessPermissionValuePart2`

### پیش‌شرط‌های context

| context | نیاز فرم | رفتار فعلی در صورت نبودن/ابهام |
|---|---|---|
| `_parking` | نام پارکینگ، شناسه و ارسال به فرم‌های وابسته | سازنده آن را دریافت می‌کند؛ رفتار خطای صریح برای مقدار `null` در مسیر عادی مشخص نشده است؛ نیازمند تأیید |
| `CurrentUser` | نام کاربر، نوع کاربر، پارکینگ جاری و مجوزها | در عنوان و کنترل دسترسی مستقیماً استفاده می‌شود؛ نبودن آن در مسیر عادی پشتیبانی نشده است |
| `UserToken` | درخواست‌های سرویس، از جمله وضعیت پارکینگ | از Login در متغیر عمومی تنظیم می‌شود؛ انقضا، refresh و خطای token در این فرم قرارداد مشخصی ندارد |
| درب/شیفت جاری | برای عملیات ورود و خروج دستی اهمیت دارد | `MainForm` فیلد مستقل برای درب جاری ندارد؛ کنترل شیفت و درب در فرم‌های عملیاتی/داده‌های کاربر انجام می‌شود؛ نیازمند بررسی فرم مقصد |

موارد بالا بین «context لازم برای بازشدن MainForm» و «context لازم برای اجرای یک قابلیت در فرم مقصد» یکسان نیستند. پارکینگ و کاربر برای ایجاد فرم ضروری‌اند؛ درب و شیفت پیش‌شرط بعضی workflowهای عملیاتی هستند، نه ورودی مستقیم سازنده‌ی `MainForm`.

### رفتار فعلی و پیشنهاد نسخه‌ی وب

**رفتار فعلی برنامه:** contextها در متغیرها و کنترل‌های عمومی نگهداری می‌شوند، `MainForm` با یک موجودیت پارکینگ ساخته می‌شود و کنترل دسترسی از مجوزهای عددی کاربر انجام می‌گیرد.

**پیشنهاد نسخه‌ی وب:** `currentUser`، `currentParking`، session/token و در صورت نیاز `currentDoor`/`currentShift` باید در context یا state مشخص و قابل ردیابی قرار گیرند. route پارکینگ باید شناسه‌ی پارکینگ را صریح داشته باشد، اما مجوز و مالکیت آن باید از backend تأیید شود. نگهداری token و refresh آن نباید از الگوی متغیر عمومی نسخه‌ی ویندوزی کپی شود.

## ساختار کامل UI

### نمای کلی layout

ساختار قابل مشاهده‌ی `MainForm` از دو لایه‌ی اصلی تشکیل شده است:

1. `ribbonControl1` در بالای فرم، برای ناوبری و اجرای commandها.
2. `mainTabControl` در بخش محتوای فرم، برای نمایش صفحه‌ی اصلی یا گزارش‌ها.

`mainTabControl` تمام فضای باقی‌مانده‌ی فرم را اشغال می‌کند و دو تب دارد:

| تب داخلی | محتوای فعلی | وضعیت نمایش |
|---|---|---|
| `mainTabPage` | عنوان «دسترسی سریع»، Tileها و کنترل وضعیت پارکینگ | تب پیش‌فرض و نمای عملیاتی اصلی |
| `reportTabPage` | Accordion گزارش‌ها، عنوان گزارش، FilterPanel و دکمه‌ی نمایش | هنگام انتخاب صفحه‌ی Ribbon گزارشات |

در `MainForm_Load`، header تب‌های داخلی مخفی می‌شود (`ShowTabHeader = false`)؛ بنابراین کاربر به‌صورت مستقیم تب‌ها را انتخاب نمی‌کند و جابه‌جایی با Ribbon یا Tile گزارش انجام می‌شود. منبع: `MainForm.cs` و `MainForm.Designer.cs`.

### Ribbon و صفحات آن

Ribbon راست‌به‌چپ است، نوار دسترسی سریع آن مخفی است و چهار صفحه‌ی اصلی دارد:

| صفحه | عنوان نمایشی | محتوای کلی | وضعیت فعلی |
|---|---|---|---|
| `tarrifRibbonPage` | تعاریف | ساختار پارکینگ، اعضا، کارت و تعرفه | visibility بر اساس `AccessPermissionValuePart1` |
| `actionRibbonPage` | عملیات | مانیتورینگ، شیفت، کنترل و مدیریت تردد | visibility بر اساس `AccessPermissionValuePart1` |
| `importRibbonPage` | ارتباط با سایر سیستم ها | تنظیم ارتباط، ETS و Excel | فقط برای username برابر `admin` قابل مشاهده می‌شود؛ نیازمند تأیید محصول برای سیاست نهایی |
| `reportRibbonPage` | گزارشات | فعال‌کردن نمای گزارش و دسترسی به گزارش‌های Accordion | visibility بر اساس `AccessPermissionValuePart2` |

صفحه‌ی `DefinitionsRibbonPageCategory` با عنوان «تعاریف» container مربوط به بخش تعاریف است؛ عنوان صفحه‌ی فعال نیز در Designer «تعاریف» ثبت شده است. بعضی گروه‌ها و BarItemها در Designer وجود دارند اما handler فعال یا عنوان عملیاتی مشخص ندارند؛ این موارد در بخش «عناصر تعریف‌شده ولی بدون workflow فعال» ثبت شده‌اند.

### صفحه‌ی اصلی و دسترسی سریع

در `mainTabPage`، کنترل‌ها به‌ترتیب کاربرد محصولی زیر قرار دارند:

| جزء UI | عنوان/محتوا | عملیات یا رفتار فعلی |
|---|---|---|
| `eosLabel1` | «دسترسی سریع» | عنوان بخش Tileها |
| `tileControl1` | گروه Tileهای عملیاتی | نمایش میانبر قابلیت‌های پرکاربرد |
| `memberShipTileItem` | «عضویت و ثبت نام» | رویداد `ItemPress` به `MemberForm(_parking)` می‌رود؛ handler `ItemClick` خالی است |
| `manualTrafficTileItem` | «ورود و خروج دستی» | همان handler کنترل ورود و خروج دستی را اجرا می‌کند |
| `assignShiftTileItem` | «اختصاص شیفت» | `ParkingUserShiftForm(_parking)` را باز می‌کند |
| `cardManagerTileItem` | «مدیریت کارت ها» | `ParkingCardForm(_parking)` را باز می‌کند |
| `reportTileItem` | «گزارشات» | صفحه‌ی Ribbon گزارشات را انتخاب می‌کند |
| `eosLabel2` | «وضعیت و اطلاعات پارکینگ» | عنوان کنترل خلاصه‌ی پارکینگ |
| `eosParkingInfoControl1` | اطلاعات و وضعیت پارکینگ | با `_parking` و نام شرکت مقداردهی و سپس به‌صورت دوره‌ای به‌روزرسانی می‌شود |
| `eosLabel3` | متن resource داخلی | در Designer مخفی است؛ رفتار محصولی فعالی برای آن ثبت نشده است |

Tileها از نظر visibility و enabled بودن تحت تأثیر کنترل دسترسی عمومی قرار می‌گیرند. نمایش یا فعال‌بودن Tile در UI جایگزین بررسی مجوز در handler و backend نیست.

### نمای گزارش‌ها

`reportTabPage` شامل این نواحی است:

- `accordionControl1` در سمت راست برای انتخاب گروه و نوع گزارش
- `panel1` برای محتوای گزارش
- `panel2` در سمت چپ، ناحیه‌ی نمایش نتیجه/گزارش
- `flowLayoutPanel1` در بالای `panel1` برای عنوان، فیلتر و اجرای گزارش
- `captionReportLabel` برای عنوان گزارش انتخاب‌شده
- `reportFilterPanel` برای قرارگرفتن FilterPanel جاری
- `reportShowButton` با عنوان «نمایش» برای اعتبارسنجی فیلتر و اجرای گزارش
- `eosLabel4` و `pictureBox1` به‌عنوان عناصر نمایشی همراه پنل گزارش؛ رفتار مستقل آن‌ها از کد فرم مشخص نشده است و نیازمند تأیید است.

در شروع، `flowLayoutPanel1` مخفی است. با انتخاب یک گزینه‌ی Accordion، FilterPanel قبلی حذف و پنل جدید در `reportFilterPanel` قرار می‌گیرد، عنوان گزارش تنظیم می‌شود و ناحیه‌ی فیلتر نمایش داده می‌شود. دکمه‌ی «نمایش» ابتدا `GetValues()` و سپس در صورت موفقیت `ShowReport()` را روی FilterPanel جاری اجرا می‌کند. جزئیات نگاشت گزارش‌ها و فیلترها در ادامه‌ی سند آمده است.

### نیازمندی پیشنهادی نسخه‌ی وب

ساختار معادل وب باید یک layout پایدار با header، navigation و ناحیه‌ی محتوای route داشته باشد. صفحه‌ی اصلی پارکینگ، میانبرها و وضعیت پارکینگ را نمایش دهد؛ گزارش‌ها در route یا view مستقل با انتخاب گزارش، schema فیلتر، نتیجه و حالت‌های loading/empty/error پیاده شوند. وضعیت active route نباید به تب‌های پنهان وابسته باشد و هر Tile یا command باید به route/action دارای مجوز نام‌دار متصل شود.

## چرخه‌ی عمر و رفتار عمومی

### مدل lifecycle

چرخه‌ی فعلی فرم بر اساس eventهای WinForms به شکل زیر است:

```text
new MainForm(parking)
  ↓
InitializeComponent و ذخیره‌ی _parking
  ↓
RefreshTitle
  ↓ Load
  ├── اتصال Parking به EosParkingInfoControl
  ├── دریافت اولیه‌ی اطلاعات پارکینگ
  ├── شروع schedule با فاصله‌ی ۱۰ ثانیه
  ├── مخفی‌کردن header تب‌ها
  └── اعمال دسترسی روی UI و Ribbon
  ↓ Shown
  └── محدودسازی مدیریت تردد برای UserTypes.Parkban
  ↓ تعامل کاربر / بازکردن فرم‌های مقصد
  ↓ FormClosing
  └── توقف schedule اطلاعات پارکینگ
  ↓ Dispose فرم و کنترل‌های آن
```

منبع این sequence، سازنده و handlerهای `MainForm` در `EosParkingProfessional/EosForms/MainForm.cs` و eventهای متصل‌شده در `MainForm.Designer.cs` است.

### ایجاد فرم و مقداردهی اولیه

1. `DashboardForm` یا مسیر انتقال مستقیم، یک `ParkingEntity` به سازنده می‌دهد.
2. `InitializeComponent()` کنترل‌های Designer، Ribbon، تب‌ها، Tileها و handlerها را ایجاد و متصل می‌کند.
3. موجودیت ورودی در فیلد خصوصی `_parking` نگهداری می‌شود.
4. `RefreshTitle()` عنوان Ribbon و عنوان پنجره را با `ParkingName` پارکینگ و `CurrentUser.UserName` می‌سازد.

رفتار صریحی برای اعتبارسنجی `parking == null` یا `CurrentUser == null` در سازنده وجود ندارد؛ این مورد **ناقص/نیازمند تأیید** است و در نسخه‌ی وب باید پیش‌شرط route و context باشد.

### مرحله‌ی `Load`

در `MainForm_Load` عملیات زیر به‌ترتیب انجام می‌شود:

1. مقدار `_parking` به `eosParkingInfoControl1.Parking` داده می‌شود.
2. نام شرکت از `LockOprator.CustomerName` در `CopName` کنترل قرار می‌گیرد.
3. دریافت اولیه‌ی اطلاعات از سرور در task جدا آغاز می‌شود و فرم حداکثر ۱۰۰ میلی‌ثانیه برای آن منتظر می‌ماند؛ قرارداد دقیق نتیجه‌ی این انتظار و رفتار خطا در `MainForm` مشخص نیست.
4. schedule کنترل اطلاعات پارکینگ با فاصله‌ی ۱۰٬۰۰۰ میلی‌ثانیه شروع می‌شود.
5. header تب‌های داخلی مخفی می‌شود و `mainTabPage`/`reportTabPage` از طریق Ribbon کنترل می‌شوند.
6. `SetAccess` روی کنترل‌ها و آیتم‌های Ribbon اعمال می‌شود.
7. `SetAccessReport` روی Accordion گزارش‌ها اعمال می‌شود.
8. visibility صفحه‌های Ribbon بر اساس بخش اول یا دوم مجوز تعیین می‌شود و visibility `reportTileItem` با `reportRibbonPage` هماهنگ می‌گردد.
9. صفحه‌ی ارتباط با سایر سیستم‌ها در رفتار فعلی با username برابر `admin` قابل مشاهده می‌شود.

در صورت خطای دریافت اولیه یا schedule، قرارداد عمومی برای نمایش خطا، retry یا قرارگرفتن کنترل در حالت degraded در این فرم ثبت نشده است؛ جزئیات به کنترل مشترک و سرویس وابسته است و **نیازمند بررسی** است.

### مرحله‌ی `Shown` و `Activated`

در `MainForm_Shown`، اگر نوع کاربر `UserTypes.Parkban` باشد، `manageTrafficButtonItem` غیرفعال می‌شود و handler پایان می‌یابد. این کنترل مکمل کنترل دسترسی مرحله‌ی `Load` است.

برای `MainForm_Activated` handler در Designer متصل است، اما بدنه‌ی آن منطق اجرایی ندارد. refresh context، بازبینی مجوزها یا بازیابی ارتباط در فعال‌شدن مجدد فرم در رفتار فعلی انجام نمی‌شود؛ این موضوع **ناقص/نیازمند تصمیم محصول** است.

### بازکردن و بازگشت فرم‌های مقصد

فرم‌های مقصد عمدتاً با متد عمومی `ShowForm(Form)` باز می‌شوند:

```text
ساخت Form مقصد با _parking
  ↓
ثبت در _currentOpenForm
  ↓
ShowDialog() به‌صورت modal
  ↓
Close و Dispose فرم مقصد
  ↓
برگرداندن DialogResult به caller
```

در صورت exception در `ShowForm`، پیام خطا نمایش داده می‌شود، `_currentOpenForm` پاک می‌شود و `DialogResult.Abort` برمی‌گردد. پس از مسیر موفق، پاک‌کردن `_currentOpenForm` در کد فعلی کامنت شده است؛ بنابراین lifecycle مرجع فرم جاری از نظر وضعیت داخلی **نیازمند اصلاح/تأیید** است.

در بسیاری از handlerها فرم مقصد داخل `using` نیز ساخته می‌شود و `ShowForm` خودش `Close` و `Dispose` را اجرا می‌کند. این الگوی دوگانه، رفتار فعلی است و باید در نسخه‌ی وب به یک قرارداد روشن برای مالکیت و cleanup تبدیل شود.

### lifecycle تب داخلی

`mainTabControl` در Designer دو تب داخلی دارد و header آن‌ها در زمان Load مخفی می‌شود. در صورت فعال‌بودن close button، handler `mainTabControl_CloseButtonClick` این مراحل را انجام می‌دهد:

1. تب انتخاب‌شده را می‌گیرد؛ اگر تب انتخابی وجود نداشته باشد، کاری انجام نمی‌دهد.
2. خود تب را dispose می‌کند.
3. کنترل‌های تب را پاک می‌کند.
4. تب را از `TabPages` حذف می‌کند.
5. اگر بیش از یک تب باقی مانده باشد، آخرین تب را انتخاب می‌کند.

در کد فعلی پیش از dispose، قرارداد عمومی برای اعلام unsaved changes یا لغو بستن وجود ندارد و استفاده از `GC.Collect()` نیز بخشی از lifecycle پیاده‌سازی قدیمی است؛ این رفتار نباید مستقیماً به نسخه‌ی وب منتقل شود.

### تغییر نمای محتوا

`ribbonControl1_SelectedPageChanged` مسئول همگام‌سازی Ribbon و تب داخلی است:

- اگر صفحه‌ی انتخاب‌شده `reportRibbonPage` باشد، `reportTabPage` فعال می‌شود.
- در غیر این صورت، `mainTabPage` فعال می‌شود.
- انتخاب Tile گزارشات نیز با تنظیم `SelectedPage` همین مسیر را فعال می‌کند.

بنابراین انتخاب گزارش از Accordion lifecycle جدیدی برای `MainForm` ایجاد نمی‌کند؛ فقط FilterPanel داخل تب گزارش جایگزین می‌شود.

### بستن فرم، خروج و تغییر کاربر

| رویداد/عملیات | handler | رفتار فعلی | وضعیت |
|---|---|---|---|
| تغییر کاربر | `changeUserButtonItem_ItemClick` | تنظیم `DialogResult.Retry` و بستن فرم | رفتار فعلی |
| خروج | `exitButtonItem_ItemClick` | تنظیم `DialogResult.OK` و بستن فرم | رفتار فعلی |
| شروع بسته‌شدن | `MainForm_FormClosing` | توقف schedule کنترل اطلاعات پارکینگ | رفتار فعلی |
| فعال‌شدن مجدد | `MainForm_Activated` | بدون منطق اجرایی | ناقص/نیازمند تأیید |
| خطا در فرم مقصد | `ShowForm` | نمایش خطا و بازگرداندن `Abort` | رفتار فعلی |

ترتیب مطلوب برای خروج این است که ابتدا عملیات دوره‌ای و subscriptionها متوقف شوند، سپس فرم‌های مقصد و کنترل‌های داخلی dispose شوند و در پایان نتیجه‌ی خروج به مسیر بالادست برگردد. در کد فعلی فقط توقف schedule در `FormClosing` صراحتاً ثبت شده و cleanup کامل فرم‌های باز یا cancellation درخواست‌های جاری قرارداد عمومی ندارد؛ این بخش **ناقص/نیازمند تأیید** است.

### وضعیت‌های lifecycle و خطاها

| وضعیت | رفتار فعلی | پوشش |
|---|---|---|
| context معتبر | فرم ساخته و عنوان‌گذاری می‌شود | رفتار فعلی |
| context ناقص | رفتار صریح برای `null` مشخص نیست | ناقص/نیازمند تأیید |
| بارگذاری اولیه | دریافت اطلاعات و شروع schedule | رفتار فعلی |
| خطای بارگذاری | قرارداد retry/error boundary مشخص نیست | ناقص |
| فرم مقصد باز | modal و blocking برای MainForm | رفتار فعلی |
| خطای فرم مقصد | پیام خطا و `Abort` | رفتار فعلی |
| تغییر کاربر | `Retry` و بازگشت به Login | رفتار فعلی |
| خروج عادی | `OK` و بسته‌شدن فرم | رفتار فعلی |
| بستن با تغییر ذخیره‌نشده | رفتار عمومی وجود ندارد | ناقص/نیازمند تأیید |
| انقضای session/token | رفتار مستقل در MainForm مشخص نیست | ناقص |

### نیازمندی و پیشنهاد نسخه‌ی وب

در نسخه‌ی وب lifecycle باید route-based و قابل لغو باشد: ورود به route پارکینگ context را اعتبارسنجی کند، queryهای وضعیت پارکینگ با mount شروع و با unmount یا تغییر پارکینگ متوقف شوند، فرم‌های مقصد به route یا dialog دارای مالکیت مشخص تبدیل شوند، و خروج/تغییر کاربر session را invalidate و تمام polling و درخواست‌های قابل لغو را متوقف کند. برای هر مرحله باید stateهای `loading`، `ready`، `error`، `unauthorized` و `session-expired` تعریف شوند. این موارد **پیشنهاد نسخه‌ی وب** هستند و توصیف رفتار فعلی نیستند.

## ۱. کنترل وضعیت و اطلاعات پارکینگ

### نقش کنترل

کنترل مشترک `EosParkingInfoControl` در صفحه‌ی اصلی MainForm وضعیت خلاصه‌ی پارکینگ جاری را نمایش می‌دهد. این کنترل فقط برای مشاهده است و از داخل MainForm عملیات ویرایش یا فرمان عملیاتی ارائه نمی‌کند.

### API و زمان‌بندی فعلی

```text
GET ParkingApi.GetInfoById
ورودی: شناسه پارکینگ جاری (_parking.Id)
خروجی مورد استفاده: ParkingInfoDto
```

در `MainForm_Load`، کنترل به پارکینگ جاری متصل می‌شود، یک دریافت اولیه انجام می‌شود و timer با فاصله‌ی `10000` میلی‌ثانیه (۱۰ ثانیه) فعال می‌گردد. در هر Tick ابتدا timer متوقف، داده دریافت و سپس timer دوباره فعال می‌شود؛ بنابراین درخواست‌ها روی هم اجرا نمی‌شوند.

اگر کنترل visible نباشد یا timer فعال باشد، `GetFromServer` درخواست جدید را رد می‌کند. خطای دریافت در کنترل فعلی به‌صورت silent مدیریت می‌شود و در exception، thread برای ۵ ثانیه متوقف می‌شود؛ پیام خطای مشخص یا وضعیت stale در UI فعلی وجود ندارد.

### وضعیت‌های لازم برای نسخه وب

| وضعیت | رفتار فعلی ویندوزی | نیازمندی وب |
|---|---|---|
| بارگذاری اولیه | درخواست در شروع Load | skeleton یا loading state برای کارت‌ها |
| به‌روزرسانی دوره‌ای | polling هر ۱۰ ثانیه | polling کنترل‌شده یا WebSocket با توقف هنگام خروج/عدم مشاهده |
| موفق | جایگزینی مقدارها و نمودار | نمایش زمان آخرین به‌روزرسانی و داده معتبر |
| خطا | بدون پیام؛ retry ضمنی در چرخه بعدی | پیام قابل فهم، حفظ آخرین داده و دکمه retry |
| پاسخ تهی/ناقص | قرارداد صریح ندارد | تفکیک null، مقدار صفر و داده ناقص |
| توقف صفحه | در `FormClosing` timer متوقف می‌شود | cancel درخواست و unsubscribe از polling هنگام unmount |

### پیشنهاد UI وب

این کنترل در وب به یک بخش Dashboard با کارت‌های آماری و نمودار ظرفیت تبدیل شود:

- کارت‌های جدا برای طبقات، درب‌ها، ظرفیت، آزاد، اشغال و اعضا
- نمایش درصد اشغال از داده‌ی معتبر backend یا قرارداد مشخص محاسبه
- نمایش شیفت جاری و تعداد کاربران شیفت در بخش وضعیت عملیاتی
- نمایش زمان آخرین دریافت و زمان سرور، با تفکیک روشن
- نمایش وضعیت دستگاه به‌صورت badge بدون افشای متن فنی غیرضروری
- نمایش مالک فقط برای نقش‌های مجاز
- responsive و قابل استفاده در موبایل، با RTL و دسترسی‌پذیری
- تعریف interval قابل تنظیم در backend/config و جلوگیری از polling هم‌زمان

## ۲. lifecycle، فرم‌های مقصد و تب‌ها

### رفتار فعلی ویندوزی

`MainForm` یک فرم والد modal است و فرم‌های مقصد را با `ShowForm` اجرا می‌کند. این helper فرم مقصد را باز می‌کند، نتیجه را می‌خواند، سپس `Close` و `Dispose` می‌کند. در نتیجه، فرم‌های مقصد در lifecycle فعلی صفحه‌ی مستقل داخل MainForm نیستند و جزئیاتشان در سند خودشان ثبت خواهد شد.

صفحه‌ی اصلی و صفحه‌ی گزارش در `mainTabControl` قرار دارند، اما header تب‌ها با `ShowTabHeader = False` مخفی است. انتخاب صفحه‌ی Ribbon گزارشات، `reportTabPage` را فعال می‌کند و انتخاب سایر صفحه‌ها، `mainTabPage` را فعال می‌کند. close تب، تب انتخاب‌شده را dispose و از مجموعه حذف می‌کند؛ در صورت باقی‌ماندن بیش از یک تب، آخرین تب انتخاب می‌شود.

### جریان lifecycle

```text
constructor(ParkingEntity)
  ↓ تنظیم _parking و عنوان
Load
  ↓ اتصال کنترل اطلاعات، دریافت اولیه، شروع polling، اعمال دسترسی
Shown
  ↓ قواعد ویژه پارکبان‌ها، یعنی نوع کاربری `Parkban`
کار با Ribbon/Tile و بازکردن فرم مقصد
  ↓
Closing
  ↓ توقف polling و آزادسازی منابع
```

### خروجی‌های lifecycle

| رویداد | نتیجه فعلی |
|---|---|
| فرم مقصد خطا دهد | پیام خطا و `DialogResult.Abort` از `ShowForm` |
| تغییر کاربر | `Retry` برای بازگشت به مسیر Login |
| خروج | `OK` و بسته‌شدن MainForm |
| خروج از فرم با پنجره مقصد باز | lifecycle مقصد باید قبل از بازگشت کامل شود |
| خطای عمومی بعضی handlerها | در برخی مسیرها با `catch` خالی نادیده گرفته می‌شود |

### طراحی پیشنهادی وب

- `MainForm` به layout پایدار شامل header، sidebar، context پارکینگ و `Outlet` محتوای route تبدیل شود.
- فرم‌های مقصد به route/page مستقل تبدیل شوند؛ modal فقط برای عملیات کوتاه و تاییدیه استفاده شود.
- تغییر route، polling کنترل وضعیت پارکینگ را مدیریت کند و منابع صفحه قبلی را آزاد کند.
- تغییر کاربر و خروج session را invalidate و کاربر را به Login هدایت کنند؛ `Retry` داخلی ویندوزی به navigation contract تبدیل شود.
- خطاهای route، فرم مقصد و API در error boundary/notification واحد مدیریت شوند.
- back navigation، deep-link، refresh مرورگر و بازگشت به پارکینگ قبلی صریحاً تعریف شوند.

## ۳. کنترل دسترسی و رفتار نقش‌ها

### الگوریتم فعلی

در `MainForm_Load` و `MainForm_Shown` دسترسی‌ها روی سه سطح اعمال می‌شوند:

1. کنترل‌ها و BarItemهایی که `Tag` دارند با `AccessPermissionValuePart1` مقایسه می‌شوند.
2. صفحات Ribbon با bitmask بخش اول یا دوم مجوز visible/hidden می‌شوند.
3. آیتم‌های گزارش Accordion با `AccessPermissionValuePart2` مقایسه و enabled/disabled می‌شوند.

قاعده‌ی bitmask به‌صورت مفهومی:

```text
hasAccess = (userPermissionPart AND requiredPermission) == requiredPermission
```

اعداد `Tag` در Designer نگاشت فنی فعلی هستند و جایگزین نام رسمی مجوز در قرارداد وب نیستند.

### نگاشت مجوزهای مشاهده‌شده

| قابلیت | شناسه/منبع مشاهده‌شده |
|---|---|
| مشخصات پارکینگ | Tag عددی روی `informationButtonItem` |
| تجهیزات | Tag عددی روی `equipmentButtonItem` |
| طبقات/تقسیمات | Tag عددی روی `floorButtonItem` |
| زون‌ها | Tag عددی روی `zoonButtonItem` |
| درب‌ها | Tag عددی روی `doorButtonItem` |
| تعرفه | Tag عددی روی `tariffButtonItem` |
| انواع عضویت | Tag عددی روی `memberRegisterKindButtonItem` |
| اعضا | `ParkingMember` در handler و Tag منو |
| کارت‌ها | Tag عددی روی `cardButtonItem` |
| کنترل خودروها | Tag عددی روی `blackListButtonItem` |
| عملیات ورود/خروج | Tag عددی روی `manualTrafficButtonItem` |

### رفتار پارکبان‌ها؛ `UserTypes.Parkban`

طبق تعریف محصول، کاربران سیستم دو گروه اصلی دارند: اپراتورها که با برنامه ویندوزی کار می‌کنند و پارکبان‌ها که از نرم‌افزار اندرویدی استفاده می‌کنند. در `MainForm`، رفتار زیر برای نوع کاربری `Parkban` در برنامه ویندوزی اعمال می‌شود:

- Tileهای عضویت، کارت، اختصاص شیفت و گزارش مخفی می‌شوند.
- `manageTrafficButtonItem` غیرفعال می‌شود.
- اگر مجوز عادی کنترل ورود و خروج باعث disabledشدن Tile دستی شده باشد، کد آن را برای `Parkban` فعال می‌کند.
- handler مدیریت ورود/خروج نیز دوباره نوع کاربر را بررسی می‌کند و برای `Parkban` بازگشت می‌دهد.
- این محدودیت‌ها باید در معماری وب با تفکیک روشن بین پنل اپراتورها و تجربه پارکبان‌ها پیاده شوند؛ مخفی‌کردن منو به‌تنهایی جایگزین مجوز backend نیست.

### طراحی پیشنهادی وب

- مجوزها به‌صورت capability نام‌دار مانند `parking.traffic.manual.view` ارائه شوند، نه عدد خام bitmask.
- backend باید دسترسی را enforce کند؛ hidden/disabled فقط تجربه کاربری است.
- navigation، route guard، action guard و API authorization یک منبع مجوز مشترک داشته باشند.
- وضعیت unauthorized، forbidden و session expired از هم تفکیک شوند.
- تغییر مجوز کاربر در session جاری با refresh token/permission snapshot مشخص مدیریت شود.
- برای هر نقش، ماتریس قابل تست شامل menu، route، action و داده‌ی قابل مشاهده تهیه شود.

### ۱. کنترل دسترسی

#### الگوریتم فعلی

hasAccess = (userPermissionPart AND requiredTag) == requiredTag

تعریف وضعیت‌ها در این سند:

- `hidden`: عنصر در UI دیده نمی‌شود و کاربر مسیر مستقیم آن را ندارد؛ امنیت محسوب نمی‌شود.
- `disabled`: عنصر دیده می‌شود اما قابل اجرا نیست؛ علت می‌تواند نداشتن مجوز یا محدودیت نقش باشد.
- `unauthorized/forbidden`: درخواست یا route اجرا شده اما مجوز لازم وجود ندارد؛ باید پیام و پاسخ backend مشخص داشته باشد. در کد فعلی فقط بعضی handlerها پیام عدم دسترسی نشان می‌دهند.

در نسخه‌ی وب، route guard، action guard و authorization API باید از permission registry واحد و نام‌دار استفاده کنند؛ اعداد Tag فقط legacy mapping هستند.

### ۲. کنترل وضعیت پارکینگ

`EosParkingInfoControl` در `mainTabPage` خلاصه‌ی وضعیت پارکینگ جاری را نمایش می‌دهد. داده‌های قابل نمایش شامل تعداد طبقات، درب‌ها، ظرفیت، جای پارک آزاد و اشغال، تعداد اعضا، شیفت جاری، کاربران شیفت، زمان سرور، اطلاعات پردازش دستگاه و نام مالک است. کنترل نمودار آزاد/اشغال را نیز به‌روزرسانی می‌کند.

| مورد | وضعیت فعلی |
|---|---|
| API | `GET ParkingApi.GetInfoById` با `_parking.Id` و پاسخ مصرفی `ParkingInfoDto` |
| دریافت اولیه | در `Load` با task جدا آغاز می‌شود و فرم حداکثر ۱۰۰ میلی‌ثانیه منتظر می‌ماند |
| polling | با `StartScheduleGeting(10000)` هر ۱۰ ثانیه آغاز می‌شود |
| جلوگیری از هم‌پوشانی | کنترل هنگام timer فعال یا نامرئی بودن، دریافت جدید را رد می‌کند؛ در هر چرخه timer متوقف و پس از دریافت دوباره فعال می‌شود |
| refresh | فقط از مسیر `GetFromServer` کنترل مشترک انجام می‌شود؛ refresh دستی در MainForm دیده نشد |
| توقف | `MainForm_FormClosing`، `StopScheduleGeting()` را اجرا می‌کند |
| موفقیت | مقدارهای `ParkingInfoDto` و نمودار کنترل به‌روزرسانی می‌شوند |
| خطا | exception در کنترل فعلی silent مدیریت می‌شود و retry داخلی با توقف ۵ ثانیه‌ای انجام می‌گیرد؛ پیام یا status مشخص در MainForm نمایش داده نمی‌شود |

وضعیت‌های online، stale، offline و degraded در UI فعلی به‌صورت قرارداد نام‌دار وجود ندارند؛ بنابراین نمایش زمان آخرین دریافت، وضعیت اتصال و retry دستی **ناقص/نیازمند تأیید** است. در وب باید polling با cancellation، backoff، last-success timestamp و تفکیک خطای API از خطای دستگاه طراحی شود.

### ۹. تفاوت نسخه ویندوز و پیشنهاد نسخه وب

**رفتار فعلی:** یک فرم modal با Ribbon و تب داخلی، context پارکینگ در `_parking`، user/token در state عمومی، polling داخلی کنترل، مجوزهای عددی و بازکردن فرم‌های مقصد به‌صورت Dialog دارد.

**پیشنهاد نسخه وب:**

- layout پایدار شامل header، sidebar و route محتوای پارکینگ؛
- route صریح برای `currentParking` و context امن کاربر/session؛
- route/action guard مبتنی بر permission نام‌دار؛
- query قابل لغو برای وضعیت پارکینگ با refresh، last update و offline/degraded state؛
- تبدیل فرم‌های modal اصلی به route و استفاده از dialog فقط برای عملیات کوتاه؛
- قرارداد واحد برای loading، empty، error، unauthorized، forbidden و session expired؛
- audit برای تغییر تنظیمات، تعرفه، مجوزها، تردد، import و عملیات حساس؛
- عدم انتقال `GC.Collect`، polling بدون cancellation، bitmask خام، ذخیره‌سازی ناامن credential یا catch خالی به معماری وب.

## بستن خلأهای review تا قبل از فرم‌های تردد

این بخش فقط خلأهای مربوط به `MainForm`، `ParkingForm`، ارتباط با سیستم‌های خارجی، ابزارهای عمومی و `EquipmentForm` را تعیین تکلیف می‌کند. جزئیات فرم‌های عملیاتی در اسناد مستقل آن‌ها ثبت شده‌اند.

### قرارداد تکمیلی API و خطا

| حوزه | قرارداد قابل ثبت در این مرحله | تصمیم/وضعیت |
|---|---|---|
| وضعیت پارکینگ | `GET ParkingApi.GetInfoById`، ورودی `parkingId`، خروجی `ParkingInfoDto` | نام endpoint از کد قطعی؛ method و schema رسمی backend باید با Controller تأیید شود |
| تنظیم پارکینگ | `POST ParkingApi.Save`، بدنه `ParkingEntity`، خروجی مصرفی `long` یا `bool` بسته به caller | اختلاف نوع خروجی در callerها ثبت شد؛ backend باید یک response contract واحد ارائه کند |
| تجهیزات | `GET GetParkingEquipments`، `POST SaveParkingEquipment`، حذف `DeleteEquipmentById` | نام endpoint و مدل مصرفی مشخص؛ method حذف فعلی و status code رسمی نیازمند backend است |
| درب/تعرفه/ساختار | APIهای آن‌ها در فرم مقصد مصرف می‌شوند | تا بررسی فرم‌های وابسته، قراردادشان خارج از scope فعلی است |
| import | `POST CheckingExternalMember/{parkingId}`، `ImportMembersExternalSource/{parkingId}` و `UpdatingMembersThroughExternalSource/{parkingId}` | نام endpoint از کلاینت مشخص؛ schema و خطای ردیفی باید در سند import نهایی شود |

قرارداد خطای پیشنهادی مشترک نسخه وب:

```json
{
  "code": "PARKING_EQUIPMENT_INVALID",
  "message": "اطلاعات تجهیز معتبر نیست.",
  "details": [{ "field": "ip", "message": "آدرس معتبر نیست." }],
  "traceId": "..."
}
```

frontend باید پاسخ‌های `401` (session منقضی)، `403` (مجوز ناکافی)، `409` (تعارض/وابستگی)، `422` (اعتبارسنجی) و `5xx` (خطای سرویس) را جداگانه مدیریت کند. این قرارداد **پیشنهاد نسخه وب** است و تا تأیید backend قرارداد فعلی محسوب نمی‌شود.

هر مجوز باید در backend enforce شود و frontend فقط برای navigation/action guard از آن استفاده کند. نگاشت دقیق هر نام به عدد Tag موجود، مرجع enum و policy نقش‌ها باید هنگام اتصال backend ثبت شود؛ تا آن زمان نام‌های بالا **پیشنهاد نسخه وب** هستند.

### قرارداد session، retry، cancellation و unsaved changes

| موضوع | تصمیم مستندشده برای نسخه وب |
|---|---|
| session | پاسخ `401` باعث تلاش یک‌باره برای refresh امن می‌شود؛ در شکست، polling و درخواست‌ها متوقف و کاربر به Login هدایت می‌شود |
| retry | خطاهای شبکه و `5xx` با backoff محدود و دکمه retry؛ خطاهای `4xx` بدون retry خودکار |
| cancellation | queryهای وضعیت پارکینگ، تست تجهیز و import با تغییر route/پارکینگ یا خروج کاربر cancel می‌شوند |
| polling | هنگام hidden شدن صفحه یا نبود context معتبر متوقف؛ پس از بازگشت با interval و last-success کنترل‌شده ادامه می‌یابد |
| unsaved changes | خروج از فرم/route در صورت dirty بودن با confirmation؛ لغو خروج، state فرم را حفظ می‌کند |
| modal مقصد | مالکیت dialog مشخص؛ بستن dialog باید نتیجه‌ی `success/cancel/error` برگرداند و resource را یک‌بار آزاد کند |

این جدول **قرارداد پیشنهادی نسخه وب** را تثبیت می‌کند؛ رفتار WinForms فعلی در همه‌ی موارد چنین قراردادی ندارد.

### تعیین تکلیف ابزارهای عمومی

- `AboutForm` بدون API و بدون workflow کسب‌وکاری است؛ برای وب یک صفحه/دیالوگ read-only کافی است.
- IMEI فقط در صورت مجوز `system.device-identity.view` نمایش داده شود و copy آن audit یا محدود شود.
- لینک سایت باید HTTPS و allowlist‌شده باشد؛ `Process.Start` به‌عنوان رفتار وب منتقل نشود.
- فعال‌سازی/غیرفعال‌سازی قفل عملیاتی حساس است و به `system.license.manage`، confirmation، audit و ثبت نتیجه نیاز دارد.
- `settingButtonItem` چون visibility آن `Never` و handler آن خالی است، قابلیت فعال محسوب نمی‌شود و route وب برای آن ایجاد نمی‌شود مگر با تصمیم محصول.

### وضعیت نهایی این مرحله

خلأهای قابل تصمیم‌گیری برای حوزه‌های غیرتردد با قراردادهای بالا بسته شدند. مواردی که هنوز نیازمند منبع بیرونی هستند، به‌جای حدس به‌صورت «نیازمند تأیید backend» باقی می‌مانند: method و schema رسمی API، نگاشت نهایی permission registry، status code واقعی و policy مجوز قفل/IMEI. بررسی فرم‌های تردد طبق ترتیب تعیین‌شده در مرحله‌ی بعد انجام می‌شود.
