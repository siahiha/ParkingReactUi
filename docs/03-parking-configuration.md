## مستندات فرم `ParkingForm`

### هدف و مسیر دسترسی

`ParkingForm` برای ایجاد پارکینگ جدید یا مشاهده و ویرایش مشخصات پارکینگ جاری استفاده می‌شود. از `DashboardForm` برای ایجاد/ویرایش پارکینگ و از `MainForm` با موجودیت `_parking` برای ویرایش پارکینگ جاری باز می‌شود.

منبع: `EosParkingProfessional/EosForms/ParkingForm.cs` و `ParkingForm.Designer.cs`.

### ساختار UI و فیلدها

| گروه | کنترل/عنوان | مدل مقصد | نوع/رفتار |
|---|---|---|---|
| مشخصات | نام | `ParkingName` | متن، حداکثر ۱۰۰ نویسه، الزامی |
| مشخصات | آدرس | `Address` | متن، حداکثر ۱۰۰ نویسه |

### بارگذاری و حالت‌های فرم

- سازنده‌ی بدون پارامتر برای ایجاد رکورد استفاده می‌شود و فرم را با مقدار خالی ایجاد می‌کند.
- سازنده‌ی دارای `ParkingEntity`، مقدار را در `Building` قرار داده و `FillForm()` را اجرا می‌کند.
- در حالت ویرایش، مقدارهای موجودیت در کنترل‌ها قرار می‌گیرند؛ گروه شیفت سوم فقط وقتی شیفت دوم وجود دارد فعال می‌شود.
- در تغییر `hostelryCheckBox`، کنترل حداقل ساعت توقف فعال یا غیرفعال می‌شود.
- در اعتبارسنجی `shift2ToTextBox`، اگر زمان شیفت دوم وارد شده باشد گروه شیفت سوم فعال می‌گردد.
- دکمه‌ی تأیید ذخیره می‌کند؛ دکمه‌ی لغو در پوسته‌ی فرم پایه قرار دارد و جزئیات handler آن از این فایل مشخص نیست.

### اعتبارسنجی و خطاها

1. مجوز `ParkingInformationAddOrEdit` قبل از ذخیره بررسی می‌شود.
2. نام پارکینگ نباید خالی باشد؛ پیام «نام پارکینگ را وارد کنید» نمایش داده می‌شود.
3. زمان شروع شیفت اول باید غیرصفر باشد؛ پیام «شیفتی انتخاب نشده است» نمایش داده می‌شود.
4. هم‌پوشانی بازه‌های کاری شیفت دوم و سوم با شیفت قبلی کنترل می‌شود؛ در صورت خطا پیام «بازه های کاری مجموعه هم پوشانی دارند» نمایش داده می‌شود.
5. تبدیل فیلدهای عددی به `LongValue`/`IntValue` به کنترل‌های مشترک وابسته است؛ قرارداد پیام خطای مقدار نامعتبر در این فرم صریح نیست.
6. مقدارهای زمانی دوم و سوم در صورت زمان صفر به `null` تبدیل می‌شوند؛ برای زمان پایان دوم و سوم چنین نرمال‌سازی صریحی وجود ندارد و نیازمند تأیید است.

### ذخیره و API

```text
POST ApiAddress.ParkingApi.Save
request: ParkingEntity
response مورد استفاده: ResponseResultWeb<long>
موفقیت: response.Values به‌عنوان Id در Building قرار می‌گیرد و DialogResult.OK تنظیم می‌شود
خطا: MessageShowError(response)
```

در ایجاد، در صورت `Building == null` یک `ParkingEntity` ساخته می‌شود. سپس فیلدهای UI روی موجودیت نگاشت و درخواست ارسال می‌شوند. method نهایی HTTP، schema کامل request/response، status codeها و قرارداد خطا در Controller این پروژه تأیید نشده‌اند؛ وضعیت پوشش API **نام endpoint مشخص، قرارداد ناقص** است.

### خروجی و اثر در MainForm

- موفقیت ذخیره با `DialogResult.OK` به caller برمی‌گردد.
- `MainForm` پس از بازگشت از این فرم `RefreshTitle()` را اجرا می‌کند؛ بنابراین تغییر نام پارکینگ در عنوان Ribbon و پنجره منعکس می‌شود.
- refresh عمومی فهرست یا سایر کنترل‌های وابسته در این فرم انجام نمی‌شود و باید در caller یا workflow وب تعیین شود.

### پیشنهاد نسخه‌ی وب و موارد باز

در نسخه‌ی وب فرم باید create/edit یکسان با route یا drawer مشخص، اعتبارسنجی عددی و زمانی مستقل، نمایش هم‌پوشانی شیفت‌ها، کنترل وابستگی‌ها و پیام نتیجه داشته باشد. وضعیت loading، خطای شبکه، retry و unsaved changes در نسخه‌ی فعلی قرارداد کامل ندارند. تکلیف `TrafficType`، فیلدهای مخفی، اعتبارسنجی بازه‌ی پایان شیفت‌ها و permission backend باید تأیید شود.

## مستندات فرم `EquipmentForm`

### هدف و مسیر دسترسی

`EquipmentForm` برای مشاهده، ایجاد، ویرایش، حذف و تست ارتباط تجهیزات متصل به پارکینگ استفاده می‌شود. فرم از `MainForm` با `EquipmentForm(_parking)` باز می‌شود و تمام فهرست تجهیزات را بر اساس شناسه‌ی پارکینگ جاری دریافت می‌کند.

منبع: `EosParkingProfessional/EosForms/EquipmentForm.cs` و `EquipmentForm.Designer.cs`.

### ساختار UI

صفحه از جدول فهرست تجهیزات و پنل مشخصات تجهیز تشکیل شده است:

| ناحیه | اجزا و رفتار |
|---|---|
| جدول | ستون نام تجهیز، عملیات ویرایش و حذف؛ حذف بر اساس مجوز `ParkingEquipmentDelete` visible می‌شود |
| toolbar | ایجاد تجهیز جدید از `EosEntityModifyToolsControl` |
| پنل مشخصات | در حالت عادی غیرفعال و مخفی؛ با ایجاد یا ویرایش فعال می‌شود |
| نوع تجهیز | انتخاب از `EquipmentTypes` |
| وضعیت | انتخاب «فعال» یا «غیر فعال» |
| نوع ارتباط | انتخاب از `ConnectionTypes`؛ TCP/IP یا اتصال سریال روی فعال‌بودن فیلدهای شبکه/baud rate اثر دارد |
| تب دستگاه تردد | پورت، IP، COM، رله، baud rate، timeout خواندن/نوشتن، کنترل PC و کنترل از سرویس |
| تب دوربین شبکه | IP، پورت، نام کاربری، رمز عبور، تصویر دوربین و تست ارتباط |
| پردازش پلاک | popup برای تعریف منبع تشخیص پلاک از سرویس IP، وب‌سرویس یا دیتابیس |
| ابعاد/موقعیت تصویر | چپ، بالا، عرض و ارتفاع ناحیه‌ی تشخیص پلاک |
| نتیجه تست | `deviceInfoLabel` برای نمایش اطلاعات تجهیز در صورت اتصال موفق |

header تب‌های داخلی در Load مخفی می‌شود. گروه «کنترل از سرویس» و برخی کنترل‌های قدیمی مانند وضعیت پردازش و کنترل PC در Designer مخفی هستند یا فقط برای بعضی نوع تجهیزات قابل استفاده‌اند.

### جریان‌های اصلی

#### بارگذاری

```text
Load
  ↓
GET ParkingApi.GetParkingEquipments(parking.Id)
  ↓
نمایش List<EquipmentEntity> در جدول
  ↓
پرکردن enumهای نوع تجهیز، نوع ارتباط، وضعیت و baud rate
```

#### ایجاد و ویرایش

```text
جدید/ویرایش
  ↓ فعال‌شدن پنل مشخصات
انتخاب نوع تجهیز و ورود اطلاعات
  ↓
اعتبارسنجی مجوز، نام و ارتباط
  ↓
POST ParkingApi.SaveParkingEquipment
  ↓
افزودن رکورد جدید یا refresh جدول و بستن پنل
```

با انتخاب دوربین، تب دوربین فعال می‌شود؛ برای سایر نوع‌ها تب دستگاه تردد فعال می‌گردد. نوع ارتباط TCP/IP فیلد IP را فعال و baud rate را غیرفعال می‌کند؛ اتصال سریال برعکس عمل می‌کند.

#### حذف

پس از تأیید کاربر، `ParkingApi.DeleteEquipmentById` با شناسه‌ی تجهیز فراخوانی می‌شود. در پاسخ موفق، ردیف از Grid حذف می‌شود. وابستگی تجهیز به درب یا سوابق تردد پیش از حذف در این فرم بررسی نمی‌شود و **نیازمند تأیید backend/محصول** است.

### اعتبارسنجی و تست ارتباط

- مجوز `ParkingEquipmentAddOrEdit` برای ذخیره و مجوز `ParkingEquipmentDelete` برای نمایش حذف بررسی می‌شود.
- نام تجهیز الزامی است.
- برای دوربین، IP دوربین نباید خالی باشد.
- برای تجهیز غیر دوربین با اتصال TCP/IP، IP باید با `IPAddress.TryParse` معتبر باشد.
- اعتبارسنجی پورت در `IsValidat` کامنت شده است؛ بنابراین مقدار پورت نامعتبر ممکن است تا مرحله‌ی تست یا API عبور کند.
- دکمه‌ی تست بر اساس نوع تجهیز رفتار متفاوت دارد: دوربین، POS، کارت‌خوان و دستگاه‌های دیگر.
- کارت‌خوان با `OnlineEncoder` و POS با `TestPcPos` تست می‌شوند؛ دستگاه‌های دیگر با `DeviceManager` متصل شده و اطلاعات firmware/device خوانده می‌شود.
- در تست دوربین، `EosIpCamView` به IP، پورت، username و password متصل می‌شود و تصویر دریافت‌شده نمایش داده می‌شود.
- تست پردازش پلاک از سه منبع IP service، web service و data service پشتیبانی می‌کند؛ قبل از ثبت popup، IP، پورت‌ها، شناسه دوربین و در data service نام کاربری/رمز عبور اعتبارسنجی می‌شوند.
- خطای تست ارتباط عمدتاً با پیام عمومی نمایش داده می‌شود و جزئیات فنی در UI قرارداد مشخصی ندارد.

### API و وضعیت پوشش

| عملیات | API مشاهده‌شده | request | response مصرفی | اثر UI |
|---|---|---|---|---|
| دریافت فهرست | `ParkingApi.GetParkingEquipments` | `parking.Id` | `List<EquipmentEntity>` | پرکردن جدول |
| ایجاد/ویرایش | `ParkingApi.SaveParkingEquipment` | `EquipmentEntity` | `long`؛ شناسه تجهیز | افزودن/refresh جدول |
| حذف | `ParkingApi.DeleteEquipmentById` | شناسه تجهیز | `bool` | حذف ردیف |
| تست دستگاه | driver/library محلی | مشخصات ارتباطی تجهیز | وضعیت اتصال/اطلاعات دستگاه | پیام و اطلاعات تست |

مسیر HTTP نهایی، schema رسمی Entity، status codeها، مدل خطا، timeout و retry از Controller این پروژه قابل تأیید کامل نیستند؛ وضعیت API **نام endpoint مشخص، قرارداد ناقص** است. رمز دوربین در مدل و فرم وجود دارد و نحوه‌ی حفاظت/رمزنگاری آن باید در backend مشخص شود.

### وضعیت‌ها و نیازمندی نسخه‌ی وب

حالت‌های فعلی شامل loading در دریافت/تست، empty جدول، پنل غیرفعال، ایجاد، ویرایش، حذف، خطای API و خطای دستگاه است؛ اما empty state صریح، retry، cancellation تست و نمایش offline/degraded قرارداد یکپارچه ندارند.

در نسخه‌ی وب، فرم باید بر اساس نوع تجهیز schema پویا داشته باشد، secrets دوربین را mask کند، تست ارتباط را قابل لغو و دارای timeout کند، خطای API را از خطای دستگاه جدا نشان دهد، پیش از حذف وابستگی‌ها را بررسی کند و عملیات حساس را audit نماید.

## تعیین تکلیف خلأهای فرم‌های تنظیمات

### قرارداد مشترک دسترسی و وضعیت

برای `ParkingForm` و `EquipmentForm`، دسترسی مشاهده باید از دسترسی ایجاد/ویرایش و حذف جدا باشد. در نسخه‌ی فعلی نام مجوزهای اصلی از کد قابل مشاهده است: `ParkingInformationAddOrEdit`، `ParkingEquipmentAddOrEdit` و `ParkingEquipmentDelete`. نام‌های پیشنهادی وب و رفتار آن‌ها:

| قابلیت | مجوز پیشنهادی وب | اثر unauthorized/forbidden |
|---|---|---|
| مشاهده مشخصات پارکینگ | `parking.settings.view` | route قابل مشاهده نیست یا 403 |
| ویرایش مشخصات پارکینگ | `parking.settings.edit` | فرم read-only یا 403 |
| مشاهده تجهیزات | `parking.equipment.view` | route قابل مشاهده نیست یا 403 |
| ایجاد/ویرایش تجهیزات | `parking.equipment.manage` | پنل و action ذخیره غیرفعال یا 403 |
| حذف تجهیزات | `parking.equipment.delete` | action حذف مخفی/غیرفعال یا 403 |

در WinForms، `ParkingForm` مجوز ویرایش را هنگام تأیید بررسی می‌کند و `EquipmentForm` مجوز حذف را برای ستون حذف و مجوز ویرایش را هنگام ذخیره بررسی می‌کند؛ enforce سمت backend از این پروژه تأیید نشده است.

قرارداد state مشترک پیشنهادی وب:

```text
loading → ready → dirty → saving → saved
                         └→ error (قابل retry)
route exit در dirty → confirmation → discard یا stay
```

`empty` برای پارکینگ جدید یا فهرست بدون تجهیز، `unauthorized/forbidden` برای مجوز، و `offline` برای خطای شبکه باید مستقل از پیام خطای کسب‌وکاری نمایش داده شوند.

### تکمیل `ParkingForm`

- route ایجاد: `/parking/new`؛ route ویرایش: `/parking/:parkingId/settings`؛ این‌ها **پیشنهاد وب** هستند.
- پاسخ موفق ذخیره باید یک مدل کامل پارکینگ یا شناسه‌ی معتبر برگرداند؛ اختلاف مصرف `long` در `ParkingForm` و `bool` در تنظیم ETS باید در backend به response contract واحد تبدیل شود.
- مقادیر عددی باید غیرمنفی و دارای واحد مشخص باشند؛ مالیات در بازه‌ی ۰ تا ۱۰۰ و زمان‌ها در بازه‌ی ۰۰:۰۰ تا ۲۳:۵۹ اعتبارسنجی شوند.
- شیفت اول اجباری، شیفت دوم و سوم اختیاری، و هر بازه باید start کمتر از end داشته باشد؛ هم‌پوشانی همه‌ی شیفت‌ها باید کنترل شود.
- `HasHostelryTariff = false` باید مقدار حداقل ساعت شبانه‌روزی را بی‌اثر یا پاک کند؛ تصمیم فعلی فقط disabled کردن کنترل است و ذخیره‌ی مقدار قبلی را مشخص نمی‌کند.
- `TrafficType` و فیلدهای مخفی تا زمان تصمیم محصول در UI وب نمایش داده نمی‌شوند.
- خروج موفق باید نتیجه‌ی `saved` و داده‌ی به‌روز برای refresh Dashboard/MainForm داشته باشد؛ لغو باید بدون API و بدون تغییر context انجام شود.

### تکمیل `EquipmentForm`

- route پیشنهادی: `/parking/:parkingId/equipment` و `/parking/:parkingId/equipment/new`.
- empty state جدول باید امکان «ایجاد تجهیز» داشته باشد؛ خطای دریافت باید پیام، retry و trace id داشته باشد.
- schema فرم بر اساس `DeviceType` تغییر کند: دوربین، POS، کارت‌خوان و دستگاه‌های تردد؛ فیلدهای غیرمرتبط نباید به backend ارسال شوند.
- IP، پورت، COM، baud rate و timeout باید سمت client و server اعتبارسنجی شوند؛ پورت در کد فعلی عملاً در validation اصلی کنترل نمی‌شود.
- تست اتصال باید timeout و cancellation داشته باشد و نتیجه‌ی `connected/device-error/timeout/invalid-config` را جدا نمایش دهد.
- رمز دوربین و credential دیتابیس باید secret محسوب شوند، در UI mask شوند و در log یا response بازگردانده نشوند.
- حذف تجهیز باید قبل از اجرا وابستگی به درب، دستگاه فعال یا سوابق تردد را از backend بپرسد؛ در صورت وابستگی، `409` و فهرست وابستگی‌ها برگردد.
- تغییر نوع تجهیز یا connection type باید dirty state ایجاد کند؛ لغو باید مقدار قبل از ویرایش را حفظ کند.

### وضعیت نهایی پوشش API این دو فرم

نام endpointهای اصلی و مدل‌های مصرفی مستند شده‌اند؛ method نهایی، مسیر HTTP کامل، status code، schema خطا، timeout و policy retry باید با backend تطبیق داده شوند. تا آن زمان وضعیت رسمی این دو فرم **نام endpoint مشخص، قرارداد ناقص** است و ادعای آماده‌بودن برای پیاده‌سازی وب مجاز نیست.
