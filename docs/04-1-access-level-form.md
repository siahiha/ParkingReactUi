# AccessLevelForm؛ تعریف سطح دسترسی

## هدف

`AccessLevelForm` برای ایجاد، مشاهده، ویرایش و حذف سطوح دسترسی استفاده می‌شود. هر سطح دسترسی شامل یک نام، توضیح و مجموعه‌ای از مجوزهای انتخاب‌شده برای بخش‌های مختلف سیستم است.

## مسیر دسترسی

```text
DashboardForm
  ↓
سطوح دسترسی
  ↓
AccessLevelForm
```

در `DashboardForm` قبل از بازکردن فرم، مجوز `ParkingAccessLevels` بررسی می‌شود. همین فرم از داخل `UsersForm` نیز برای تازه‌سازی فهرست سطوح دسترسی قابل بازشدن است.

## ساختار صفحه

صفحه از دو ناحیه‌ی اصلی تشکیل شده است:

1. جدول فهرست سطوح دسترسی
2. پنل مشخصات و جزئیات سطح انتخاب‌شده

### جدول

- ستون نام سطح دسترسی
- دکمه‌ی ویرایش برای ردیف انتخاب‌شده
- دکمه‌ی حذف برای ردیف انتخاب‌شده
- انتخاب ردیف برای نمایش جزئیات
- عدم نمایش فیلتر و گروه‌بندی جدول
- حذف سطوحی که `IsSystemType` آن‌ها فعال است از فهرست قابل مدیریت

### پنل مشخصات

- نام سطح دسترسی
- توضیحات
- درخت مجوزها با checkbox
- دکمه‌ی «تایید»
- دکمه‌ی «لغو»

پنل ویرایش و دکمه‌های تأیید/لغو در حالت عادی غیرفعال یا مخفی هستند و با انتخاب «جدید» یا «ویرایش» فعال می‌شوند.

## بارگذاری اولیه

هنگام بازشدن فرم:

1. سطوح دسترسی از API دریافت و در جدول قرار می‌گیرند.
2. درخت مجوزها از فهرست ثابت `AccessItemDto.GetAccessItems()` ساخته می‌شود.
3. فقط گره‌هایی که `isVisible` هستند در درخت نمایش داده می‌شوند.

## ایجاد سطح دسترسی

```text
انتخاب «جدید»
  ↓
فعال‌شدن پنل مشخصات
  ↓
ورود نام و توضیحات
  ↓
انتخاب checkboxهای مجوز
  ↓
تایید
  ↓
ساخت و ذخیره‌ی AccessLevelDto
  ↓
افزودن رکورد به جدول
```

در شروع ایجاد رکورد، فرم درخت مجوزها را انتخاب‌شده قرار می‌دهد. بنابراین در نسخه‌ی وب باید رفتار پیش‌فرض انتخاب مجوزها به‌صورت آگاهانه تعریف شود و بدون بررسی محصول، این رفتار عیناً کپی نشود.

## ویرایش سطح دسترسی

با انتخاب دکمه‌ی ویرایش یک ردیف، مشخصات رکورد در پنل قرار می‌گیرد و مجوزهای ذخیره‌شده روی درخت اعمال می‌شوند.

مجوزهای هر رکورد با دو مقدار عددی نگهداری می‌شوند:

- `AccessPermissionPart1`: مجوزهای عملیاتی و دسترسی‌های اصلی
- `AccessPermissionPart2`: مجوزهای گزارش‌ها و بخش‌های ثانویه

در زمان ویرایش، وضعیت checkboxها با مقایسه‌ی bitwise این دو مقدار با مجوز هر گره تعیین می‌شود.

## ذخیره‌سازی

هنگام تایید:

- نام و توضیحات از فرم خوانده می‌شود.
- مجوزهای انتخاب‌شده از درخت محاسبه می‌شوند.
- مقدارهای `AccessPermissionPart1` و `AccessPermissionPart2` ساخته می‌شوند.
- درخواست ذخیره به API ارسال می‌شود.
- در رکورد جدید، شناسه‌ی برگشتی در جدول قرار می‌گیرد.
- پس از ذخیره‌ی موفق، پنل ویرایش غیرفعال می‌شود.

API:

```text
GET  AccessLevelApi.Get
POST AccessLevelApi.Save
```

## الگوریتم اعمال مجوزها در UI

### مدل bitmask

هر مجوز به‌جای ذخیره‌شدن به‌صورت فهرست متنی، یک مقدار عددی مستقل دارد که معمولاً توان متفاوتی از ۲ است. چند مجوز با عملیات جمع یا OR در یک مقدار عددی ترکیب می‌شوند.

در مدل فعلی دو فضای مجوز وجود دارد:

```text
AccessPermissionPart1 → مجوزهای اصلی و عملیاتی
AccessPermissionPart2 → مجوزهای گزارش و برخی ارتباطات جانبی
```

### ساخت مقدار مجوز هنگام ذخیره

هنگام تایید فرم، درخت به‌صورت بازگشتی پیمایش می‌شود:

```text
برای هر گره‌ی انتخاب‌شده:
  اگر گره «مشاهده» نباشد:
    AccessPermissionPart1 آن به مقدار اصلی اضافه می‌شود
    AccessPermissionPart2 آن به مقدار گزارش/ثانویه اضافه می‌شود
  سپس فرزندان گره نیز به‌صورت بازگشتی محاسبه می‌شوند
```

به‌صورت مفهومی:

```text
part1 = OR تمام AccessPermissionPart1های انتخاب‌شده
part2 = OR تمام AccessPermissionPart2های انتخاب‌شده
```

در پیاده‌سازی موجود، محاسبه با جمع مقادیر انجام می‌شود؛ چون مقادیر مجوزها برای ترکیب به‌صورت bitmask تعریف شده‌اند، نتیجه‌ی مورد انتظار همان ترکیب بیت‌هاست.

### بازیابی مقدار مجوز هنگام ویرایش

هنگام انتخاب یک سطح برای ویرایش، هر گره با مقدار ذخیره‌شده مقایسه می‌شود:

```text
اگر (storedPart1 AND nodePart1) == nodePart1
    گره انتخاب‌شده است

یا اگر (storedPart2 AND nodePart2) == nodePart2
    گره انتخاب‌شده است

در غیر این صورت گره انتخاب‌نشده است
```

این مقایسه برای گره‌های ریشه، فرزند و نوه انجام می‌شود و وضعیت checkbox درخت را بازسازی می‌کند.

### اثر انتخاب والد و فرزند

درخت با قابلیت انتخاب بازگشتی ساخته شده است؛ بنابراین انتخاب یک گره‌ی والد می‌تواند وضعیت فرزندان را نیز تحت تأثیر قرار دهد. با این حال، مقدار نهایی مجوز از تمام گره‌های انتخاب‌شده در پیمایش بازگشتی محاسبه می‌شود.

### نکته‌ی مهم درباره‌ی گره‌های «مشاهده»

در الگوریتم ذخیره‌ی فعلی، گره‌ای که عنوان آن با «مشاهده» شروع شود مستقیماً به مقدار مجوز اضافه نمی‌شود. در عین حال، هنگام بازیابی، مقدار مجوز همان گره برای تعیین وضعیت checkbox بررسی می‌شود. این رفتار باید هنگام طراحی نسخه‌ی وب به‌صورت آگاهانه تصمیم‌گیری و با قرارداد backend هماهنگ شود؛ تشخیص مجوز نباید صرفاً به متن نمایشی گره وابسته باشد.

### الگوریتم بررسی مجوز در سایر فرم‌ها

پس از Login، مقادیر مجوز در `CurrentUser` قرار می‌گیرند. فرم‌ها با بررسی bitmask تصمیم می‌گیرند که یک قابلیت مجاز است یا نه:

```text
hasAccess = (userPermissionPart AND requiredPermission) == requiredPermission
```

برای نمونه، Dashboard برای بازکردن کاربران و سطوح دسترسی، مجوزهای `ParkingUsers` و `ParkingAccessLevels` را با همین منطق بررسی می‌کند. این بررسی باید در نسخه‌ی وب هم در سطح UI و هم در backend وجود داشته باشد.

## نگاشت پیشنهادی برای نسخه‌ی وب

برای جلوگیری از وابستگی UI به اعداد bitmask، بهتر است API یا یک لایه‌ی frontend مجوزها را به شکل قابل فهم ارائه کند:

```json
{
  "permissions": [
    "parking.users.view",
    "parking.access-levels.manage",
    "traffic.manual-io.edit-car-info"
  ]
}
```

در صورت حفظ قرارداد bitmask، باید فهرست رسمی نگاشت زیر نیز وجود داشته باشد:

```text
نام مجوز → مقدار بیت → عنوان نمایشی → عملیات وابسته
```

این نگاشت باید منبع واحد داشته باشد تا اختلاف بین درخت UI، backend و کنترل دسترسی فرم‌ها ایجاد نشود.

## لغو و حذف

### لغو

لغو، پنل ویرایش را می‌بندد یا پاک می‌کند و تغییرات ذخیره‌نشده را ارسال نمی‌کند.

### حذف

```text
انتخاب حذف
  ↓
نمایش تاییدیه
  ↓
AccessLevelApi.DeleteById
  ↓
حذف ردیف در صورت پاسخ موفق
```

سطوح سیستمی در جدول فرم نمایش داده نمی‌شوند و از مسیر معمول حذف قابل انتخاب نیستند.
