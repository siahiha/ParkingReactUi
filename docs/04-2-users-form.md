# UsersForm؛ تعریف و مدیریت کاربر

## هدف

`UsersForm` برای مشاهده، ایجاد، ویرایش و حذف کاربران سیستم استفاده می‌شود. در این فرم برای هر کاربر اطلاعات هویتی، اطلاعات ورود، نوع کاربری، سطح دسترسی و وضعیت فعال‌بودن ثبت می‌شود.

## مسیر دسترسی

```text
DashboardForm
  ↓
کاربران
  ↓
UsersForm
```

در Dashboard مجوز `ParkingUsers` قبل از بازشدن فرم بررسی می‌شود. فرم همچنین از داخل پنجره‌ی انتخاب سطح دسترسی، امکان بازکردن `AccessLevelForm` را دارد.

## ساختار صفحه

صفحه شامل دو ناحیه‌ی اصلی است:

1. جدول فهرست کاربران
2. پنل مشخصات کاربر

### جدول کاربران

- نمایش نام کاربری
- انتخاب ردیف و نمایش اطلاعات آن در پنل
- دکمه‌ی ویرایش
- دکمه‌ی حذف
- دکمه‌ی ایجاد کاربر جدید از کنترل عمومی عملیات موجودیت

### پنل مشخصات کاربر

#### مشخصات ورود و دسترسی

- نام کاربری
- کلمه عبور
- سطح دسترسی
- نوع کاربری
- گزینه‌ی «غیرفعال شود»

#### مشخصات فردی و تماس

- نام
- نام خانوادگی
- نام پدر
- کد ملی
- تلفن
- همراه
- آدرس
- توضیحات

دکمه‌ی کنار سطح دسترسی، فرم ایجاد/مدیریت سطح دسترسی را باز می‌کند و پس از بسته‌شدن آن، فهرست سطح دسترسی‌ها را دوباره بارگذاری می‌کند.

## بارگذاری اولیه

هنگام ساخت فرم، این داده‌ها دریافت می‌شوند:

1. فهرست سطوح دسترسی از `AccessLevelApi.Get`
2. فهرست انواع کاربر از enum داخلی `UserTypes`
3. فهرست کاربران از `UserApi.Get`

سطح دسترسی با عنوان نمایش داده می‌شود و شناسه‌ی آن در کاربر ذخیره می‌شود. نوع کاربری نیز از مقدار enum به همراه عنوان توضیحی ساخته می‌شود.

## ایجاد کاربر

```text
انتخاب «جدید»
  ↓
پاک‌شدن فرم
  ↓
فعال‌شدن پنل مشخصات
  ↓
انتخاب سطح دسترسی و نوع کاربر
  ↓
ثبت اطلاعات ورود و مشخصات فردی
  ↓
تایید
  ↓
اعتبارسنجی
  ↓
ذخیره‌ی کاربر
  ↓
افزودن کاربر به جدول
```

## ویرایش کاربر

با انتخاب ویرایش، اطلاعات `UserDto` در فرم قرار می‌گیرد:

- نام کاربری و رمز عبور
- اطلاعات فردی
- سطح دسترسی
- نوع کاربری
- وضعیت فعال

وضعیت checkbox با عنوان «غیرفعال شود» معکوس مقدار `IsActive` است:

```text
checkbox.Checked = true  → IsActive = false
checkbox.Checked = false → IsActive = true
```

## اعتبارسنجی فعلی

برای ذخیره‌ی کاربر، موارد زیر الزامی هستند:

- نام کاربری
- کلمه عبور
- سطح دسترسی معتبر
- نوع کاربری

تلفن و همراه در زمان ذخیره به عدد تبدیل می‌شوند؛ مقدار غیرعددی باعث خطای ذخیره و نمایش پیام خطا می‌شود. برای کد ملی در UI طول حداکثر ۱۰ رقم تعریف شده، اما اعتبارسنجی صریح آن در متد اصلی اعتبارسنجی دیده نمی‌شود.

## ذخیره‌سازی

در زمان ذخیره:

- رمز عبور قبل از ارسال با helper داخلی رمزنگاری می‌شود.
- سطح دسترسی با `UserAccessLevelId` ذخیره می‌شود.
- نوع کاربری با `UserType` ذخیره می‌شود.
- مقدار فعال‌بودن از checkbox محاسبه می‌شود.
- تاریخ ثبت/ویرایش در `PersistOn` قرار می‌گیرد.
- در کاربر جدید، شناسه‌ی برگشتی API در جدول قرار می‌گیرد.
- پس از موفقیت، پنل ویرایش پاک و غیرفعال می‌شود.

API:

```text
GET  UserApi.Get
POST UserApi.Save
GET  AccessLevelApi.Get
GET  UserApi.DeleteById
```

### قرارداد API مورد نیاز فرم

### وضعیت پوشش API

وضعیت فعلی این بخش **ناقص** است: مسیرهای اصلی از کد کلاینت و Controller شناسایی شده‌اند، اما schema رسمی کامل request/response، همه‌ی status codeها و قرارداد خطا هنوز به‌صورت مستقل تأیید نشده‌اند.

| عملیات | مسیر فعلی | ورودی | خروجی مورد استفاده‌ی UI |
|---|---|---|---|
| دریافت کاربران | `GET api/user/Get` | بدون ورودی در فرم فعلی | `ResponseResultWeb<List<UserDto>>` |
| دریافت سطوح دسترسی | `GET api/AccessLevel/Get` | بدون ورودی | `ResponseResultWeb<List<AccessLevelDto>>` |
| ایجاد/ویرایش کاربر | `POST api/user/Save` | بدنه‌ی `UserDto` | `ResponseResultWeb<long>`؛ شناسه‌ی کاربر ذخیره‌شده |
| حذف کاربر | `GET api/user/Delete?id={id}` | شناسه‌ی کاربر | `ResponseResultWeb<bool>` |

درخواست‌های فرم از مسیر پایه‌ی سرور ساخته می‌شوند و به احراز هویت سرویس وابسته‌اند. token دریافت‌شده در Login برای درخواست‌های بعدی استفاده می‌شود.

### فیلدهای `UserDto` مورد نیاز فرم

```text
Id
UserName
UserPass
FirstName
LastName
FatherName
NationalCode
Address
Description
TellNumber
PhonNumber
UserAccessLevelId
UserType
IsActive
IsSystemType
PersistOn
```

در ایجاد یا ویرایش، UI مقدار `UserAccessLevelId` را از سطح انتخاب‌شده، `UserType` را از فهرست نوع کاربر و `IsActive` را از checkbox فرم تولید می‌کند. در پاسخ فهرست، `IsSystemType` برای جلوگیری از ویرایش برخی فیلدها و حذف کاربر بررسی می‌شود.

### قرارداد خطا

- پاسخ موفق باید با `ResponseResultType.Ok` مشخص شود.
- در پاسخ ناموفق، UI پیام موجود در response را نمایش می‌دهد.
- در خطای شبکه یا exception، پیام خطا نمایش داده می‌شود و فرم در وضعیت ویرایش باقی می‌ماند.
- API باید از ذخیره‌ی رمز خام جلوگیری کند؛ UI فعلی پیش از ارسال مقدار رمز را رمزنگاری می‌کند، اما این رفتار نباید جایگزین hash امن سمت سرور شود.

### ملاحظه‌ی نسخه‌ی وب

مسیر حذف در API فعلی با `GET` فراخوانی می‌شود، اما در قرارداد پیشنهادی React بهتر است عملیات حذف با HTTP `DELETE` انجام شود و عملیات تغییر با `POST`/`PUT` تفکیک گردد. این مورد یک تصمیم API است و هنگام طراحی backend نسخه‌ی وب باید نهایی شود.

## حذف کاربر

```text
انتخاب حذف
  ↓
نمایش تاییدیه
  ↓
بررسی سیستمی‌بودن کاربر
  ↓
UserApi.DeleteById
  ↓
حذف ردیف از جدول در پاسخ موفق
```

کاربر سیستمی حذف نمی‌شود و پیام «امکان حذف کاربر سیستمی وجود ندارد» نمایش داده می‌شود.

## محدودیت کاربران سیستمی

برای کاربر دارای `IsSystemType`، کنترل‌های مربوط به سطح دسترسی، نوع کاربری و بعضی عملیات ویرایش غیرفعال می‌شوند. دکمه‌ی تغییر کلمه‌ی عبور در Designer وجود دارد، اما در وضعیت فعلی مخفی است و handler آن منطق اجرایی ندارد.

## نیازمندی پیشنهادی نسخه‌ی وب

- جدول با جستجو، فیلتر و صفحه‌بندی
- صفحه یا drawer مجزا برای ایجاد/ویرایش
- فیلد username با کنترل یکتا بودن
- فیلد password فقط در ایجاد یا تغییر رمز، نه نمایش رمز موجود
- انتخاب role/access level از داده‌ی API
- نمایش نوع کاربر با عنوان خوانا
- نمایش وضعیت فعال به‌صورت switch با برچسب مثبت مانند «فعال»
- اعتبارسنجی مستقل کد ملی، تلفن و همراه
- عدم ارسال یا نمایش رمز قبلی در فرم ویرایش
- غیرفعال‌سازی عملیات حساس برای کاربران سیستمی
- اعمال مجوز هم در UI و هم در backend
- ثبت رویداد audit برای ایجاد، تغییر سطح دسترسی، غیرفعال‌سازی و حذف کاربر
