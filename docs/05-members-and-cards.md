# اعضا، عضویت و کارت‌ها

## مرزبندی اصطلاحات: عضو پارکینگ در برابر کاربر سامانه

«عضویت و ثبت‌نام» نام قابلیت مدیریت **اعضای پارکینگ** است. در این قابلیت، مشخصات
عضو و دارایی‌ها و وضعیت عضویت او—مانند خودرو و پلاک، کارت، نوع عضویت، اعتبار و
ثبت یا لغو عضویت—مدیریت می‌شود. این ثبت‌نام به‌معنای ساخت حساب ورود به نرم‌افزار
نیست.

«کاربر سامانه» موجودیتی جداگانه است که با نام کاربری و رمز عبور وارد سیستم می‌شود
و نقش و مجوزهای عملیاتی دارد. کاربر سامانه در مستند
[04-users-and-access.md](04-users-and-access.md) تعریف شده است. هیچ رابطهٔ یک‌به‌یک
یا الزام به یکی‌بودن عضو پارکینگ و کاربر سامانه در منابع فعلی اثبات نشده است؛
بنابراین UI و API نباید چنین رابطه‌ای را فرض کنند.

## فرم‌ها

- `MemberForm`
- `MemberKindForm`
- `ParkingCardForm`
- `ImportMembersForm`
- `ControlListForm`

## مدل مفهومی

```text
نوع عضویت → عضو → خودرو/پلاک → کارت → اعتبار و ثبت عضویت
```

## MemberForm

قابلیت‌های اصلی:

- جستجو و نمایش اعضای پارکینگ
- ایجاد و ویرایش اطلاعات عضو
- ثبت نوع عضویت
- ثبت خودرو و پلاک
- تخصیص کارت
- تخصیص جای پارک
- مشاهده‌ی اعتبار یا گردش مالی

**پیاده‌سازی فعلی وب:** گفت‌وگوی «افزودن خودرو» در
`EosParkingReactUi/src/features/members/MemberManagementWorkspace.tsx` برای ورود یا ویرایش
پلاک از `IranianPlateInput` مشترک استفاده می‌کند. قرارداد قالب و اعتبارسنجی آن در
`docs/10-shared-ui-components.md` تعریف شده است.
- حذف عضو با کنترل وابستگی‌ها

### تب «جای‌پارک‌های عضو»

#### هدف و منبع

این تب تخصیص یک یا چند جای‌پارک فیزیکی به یک عضو پارکینگ را مدیریت می‌کند. این
مفهوم با «ثبت عضویت» و با «کاربر سامانه» متفاوت است: عضویت تعیین می‌کند که عضو
مجاز به داشتن جای‌پارک مشخص هست یا نه؛ تخصیص جای‌پارک، رابطهٔ عضو با فضای فیزیکی
پارکینگ است.

**رفتار فعلی Windows:** `MemberForm.Designer.cs` دو Grid هم‌اندازه را در تب
`جای پارک های عضو` تعریف می‌کند: `allParkSpacesGridControl` برای جای‌پارک‌های آزاد
و `memberParkSpaceGridControl` برای جای‌پارک‌های عضو. دکمهٔ هر ردیف، جای‌پارک را
میان این دو فهرست جابه‌جا می‌کند. `MemberForm.cs` فهرست آزاد را از API می‌گیرد و
در ذخیرهٔ عضو، فهرست دوم را در `MemberDto.MemberParkSpaces` ارسال می‌کند.

#### ساختار و رفتار نسخهٔ وب

**پیاده‌سازی فعلی وب:** تب «جای پارک‌های عضو» در
`EosParkingReactUi/src/features/members/MemberManagementWorkspace.tsx` همان دو
Grid را با `AppDataGrid` نمایش می‌دهد:

| بخش | ستون‌ها و action | رفتار |
|---|---|---|
| جای‌پارک‌های آزاد | طبقه/قسمت، جای پارک، «تخصیص» | فقط جای‌پارک‌های بدون تخصیص از سرور خوانده می‌شوند. انتخاب action، ردیف را از این Grid به Grid عضو منتقل می‌کند. |
| جای‌پارک‌های عضو | طبقه/قسمت، جای پارک، «آزادسازی» | action ردیف را به فهرست آزادِ محلی بازمی‌گرداند. |

- هر دو Grid از فیلتر ستونی مشترک `AppDataGrid` استفاده می‌کنند. فیلد جداگانهٔ
  «طبقه/قسمت» فرم Windows به وب منتقل نشده است؛ جستجو از منوی سه‌نقطهٔ ستون‌ها
  انجام می‌شود تا با استاندارد مشترک Grid سازگار بماند.
- در حالت ویرایش و عضویت مجاز، ستون انتخاب ردیف و checkbox انتخاب همه فعال است.
  نوار بالای هر Grid ابزار انتقال گروهی انتخاب‌شده‌ها را دارد: در Grid آزاد،
  «تخصیص جای پارک» و در Grid عضو، «آزادسازی جای پارک». action هر ردیف نیز برای
  انتقال تکی باقی می‌ماند.
- ارتفاع ناحیهٔ دو Grid به فضای قابل‌نمایش تب محدود است و فقط خود فهرست در صورت
  زیادبودن رکوردها scroll داخلی می‌گیرد؛ صفحه و layout اصلی به‌خاطر فهرست آزاد
  بی‌انتها نمی‌شود.
- actionها فقط در حالت ویرایش عضو نمایش داده می‌شوند. انتقال‌ها تا فشردن «ذخیره
  عضو» فقط پیش‌نویس محلی‌اند؛ خروج یا انصراف از ویرایش، آن‌ها را پایدار نمی‌کند.
- برای رکورد جدید، ابتدا باید عضو ذخیره و شناسهٔ معتبر دریافت شود. در حالت مشاهده،
  دو فهرست قابل خواندن‌اند اما action تخصیص/آزادسازی نمایش داده نمی‌شود.
- loading فهرست آزاد، خالی‌بودن هر فهرست، خطای دریافت و دکمهٔ تلاش مجدد، و پیام
  محدودیت عضویت به‌صورت مستقل در خود تب نشان داده می‌شود. کنترل‌های آیکنی نام
  دسترس‌پذیر دارند.

#### قاعدهٔ کسب‌وکار و وضعیت تب

**رفتار فعلی Windows:** فرم، آخرین عضویت فعال و منقضی‌نشده را پیدا می‌کند و نوع
آن را از `MemberRegisterKind.MembershipType` می‌خواند. تب فقط وقتی قابل تغییر است
که این نوع `Member` نباشد. مقادیر enum موجود چنین‌اند: `Owner = 0`،
`MemberWithParkspaces = 1` و `Member = 2` که عنوان آن «فاقد جای پارک مشخص» است.
در نتیجه، نوع ۰ یا ۱ تخصیص را مجاز و نوع ۲ تخصیص را غیرمجاز می‌کند. نبود عضویت
فعال یا پیدا نشدن نوع آن نیز عملاً تب را غیرفعال می‌سازد. شرط
`activeRegister.Count >= 0` در کد Windows همواره true است؛ این بخش یک خطای
بی‌اثر در پیاده‌سازی است و به‌عنوان قاعدهٔ محصول به وب منتقل نشده است.

**پیاده‌سازی فعلی وب:** همین تصمیم با پیام روشن اعمال می‌شود: عضوِ ذخیره‌نشده،
عضو بدون عضویت فعال، عضویت «فاقد جای‌پارک مشخص»، یا نوع عضویتِ حذف‌شده/ناموجود
نمی‌تواند تخصیص را تغییر دهد. فهرست تخصیص فعلی همچنان قابل مشاهده است تا حذف
ناخواستهٔ داده پنهان نماند.

**رفتار فعلی Windows و Backend:** هنگام ثبت نهایی عضویت با نوع `Member` (فاقد
جای‌پارک مشخص)، Windows پیش از پرداخت هشدار می‌دهد و `MemberRepository` همهٔ
رابطه‌های `MemberParkSpaces` عضو را حذف می‌کند. وب نیز قبل از ادامهٔ این workflow
هشدار می‌دهد؛ آزادسازی نهایی را به همان ثبت نهایی Backend واگذار می‌کند و در UI
آن را حدس یا تکرار نمی‌کند.

#### مدل داده و پایداری تغییرات

| فیلد `ParkSpaceDto` | کاربرد در UI و payload |
|---|---|
| `Id` | شناسهٔ رابطهٔ تخصیص `MemberParkSpaceEntity` برای یک تخصیص موجود؛ هنگام حذف از payload کنار گذاشته می‌شود تا Backend آن رابطه را حذف کند. |
| `ParkSpaceId` | شناسهٔ فضای فیزیکی؛ کلید یکتای Grid و جلوگیری از تخصیص تکراری در پیش‌نویس. |
| `FloorId` و `FloorTitle` | گروه/نمایش طبقه یا قسمت. |
| `ParkSpaceTitle` | عنوان قابل نمایش جای‌پارک. |

**رفتار فعلی Backend:** `MemberRepository.Save` برای رابطه‌های بدون `Id`، عضو و
زمان ثبت را تنظیم و رابطه را ایجاد می‌کند؛ سپس رابطه‌های فعلی همان عضو را که
شناسه‌شان در payload نیست حذف می‌کند. بنابراین نسخهٔ وب باید `Id` تخصیص‌های موجود
را حفظ کند و کل فهرست نهایی `MemberParkSpaces` را در `api/Member/Save` بفرستد.
شناسهٔ `ParkSpaceId` جایگزین `Id` رابطه نیست.

#### APIها و وضعیت پوشش

وضعیت این workflow **کامل بر اساس Controller، DTO و Repository موجود** است. پاسخ
موفق و خطای دامنه‌ای در پوستهٔ `ResponseResultWeb` برمی‌گردد؛ UI علاوه بر خطای HTTP
باید `ResponseResultType` و پیام پاسخ را کنترل کند.

| API | روش | ورودی/خروجی | اثر UI |
|---|---|---|---|
| `api/Parking/GetParkingParkSpacesById?parkingId={id}` | GET | `parkingId`؛ فهرست `ParkSpaceDto` | منبع Grid جای‌پارک‌های آزاد. بدون `getAllParkSpaces=true` فقط فضاهایی را می‌دهد که رابطهٔ عضو ندارند. |
| `api/Member/GetByParkingId?parkingId={id}` | GET | `parkingId`؛ فهرست `MemberDto` با `MemberParkSpaces` | نمایش تخصیص‌های فعلی عضو. |
| `api/Member/GetMemberRegisterKindsByParkingId?parkingId={id}` | GET | `parkingId`؛ فهرست نوع عضویت | تشخیص مجازبودن تغییر تخصیص. |
| `api/Member/Save` | POST | `MemberDto` شامل فهرست نهایی `MemberParkSpaces`؛ خروجی شناسهٔ عضو | ایجاد یا حذف رابطه‌های تخصیص همراه ذخیرهٔ عضو. |

خطای 403 در کل فضای مدیریت عضو به پیام عدم دسترسی تبدیل می‌شود. جزئیات status code
سایر خطاهای این endpointها در Controller به‌صورت قرارداد HTTP مستقل تعریف نشده و
خطاهای دامنه‌ای می‌توانند در پاسخ موفق HTTP بازگردند؛ بنابراین متن `Message` یا
`RealMessage` برای کاربر نمایش داده می‌شود.

#### موارد باز و نیازمند تأیید

- **ناقص/نیازمند تأیید Backend:** Controller فهرست آزاد را هنگام خواندن فیلتر
  می‌کند، اما `MemberRepository.Save` در منبع بررسی‌شده اعتبار آزادبودن مجدد
  `ParkSpaceId` را صریحاً اعمال نمی‌کند. در تخصیص هم‌زمان دو اپراتور، Backend باید
  یکتایی و تعارض را به‌صورت قطعی کنترل و خطای قابل‌نمایش برگرداند؛ UI نمی‌تواند
  با فهرست قبلی این رقابت را حل کند.
- **ناقص/نیازمند تأیید محصول:** سقف تعداد جای‌پارک قابل تخصیص برای هر نوع عضویت در
  مدل‌های بررسی‌شده وجود ندارد. وب همانند Windows بیش از یک تخصیص را مجاز می‌داند
  تا زمانی که قاعدهٔ رسمی دیگری ارائه شود.

### تب «عضویت» و ثبت عضویت

#### رفتار فعلی Windows

منبع این بخش فایل‌های MemberForm.cs و MemberForm.Designer.cs در مسیر
EosParkingProfessional/EosForms است. تب «عضویت» یک workflow مالی مستقل برای
ایجاد، رزرو، جایگزینی و لغو عضویت عضو پارکینگ است.

اجزای UI:

- دکمه «ثبت عضویت» و نمایش فقط‌خواندنی «مانده اعتبار عضویت فعال» به ریال؛
- Grid سوابق با ستون‌های «نوع عضویت»، «حق عضویت»، «زمان شروع» و «زمان اتمام»؛
  تاریخ‌ها در Windows به شمسی نمایش داده می‌شوند و عضویت فعال با پس‌زمینه سبز مشخص
  است؛
- actionهای ردیف برای ویرایش، حذف و—با مجوز مستقل—لغو عضویت؛
- Dialog ثبت شامل نوع عضویت، اعتبار/حق عضویت، مالیات ارزش افزوده، تاریخ شروع و
  تاریخ اتمام. نوع انتخابی است، مبلغ عددی قابل اصلاح است و مالیات/تاریخ‌ها
  فقط‌خواندنی هستند؛
- Dialog لغو شامل وضعیت اعتبار، نوع اعتبار و نوع لغو: عودت وجه، تسویه اعتبار یا
  سوختن اعتبار.

ویرایش و حذف سابقه در Windows فقط برای عضویت استفاده‌نشده/رزرو آینده در ظاهر فعال
شده است، اما منطق پایدارسازی آن در MemberRepository کامنت شده است. نسخه وب این
actionهای ناقص را منتقل نمی‌کند و فقط ثبت و لغوِ دارای قرارداد فعال را ارائه می‌دهد.

#### جریان ثبت یا رزرو

1. عضو باید ابتدا ذخیره شده و شناسه معتبر داشته باشد. برای عضو جدید، برنامه ابتدا
   ذخیره مشخصات و سپس ادامه workflow را پیشنهاد می‌دهد.
2. هر عضو حداکثر یک عضویت فعال و، در صورت وجود عضویت فعال، حداکثر یک عضویت رزرو
   دارد. رزرو دوم با خطا متوقف می‌شود.
3. وجود عضویت فعال، انتخاب «جایگزینی عضویت قبلی» یا «ثبت به‌صورت رزرو» را ضروری
   می‌کند. در رزرو، وضعیت عضویت جدید غیرفعال است و تاریخ شروع اولیه از تاریخ اتمام
   عضویت فعال گرفته می‌شود.
4. با انتخاب نوع عضویت، تاریخ اتمام از تاریخ شروع به‌علاوه DurationDays و مبلغ
   اولیه از MembershipFee پر می‌شود؛ TaxValue نوع عضویت، مالیات اولیه را تأمین
   می‌کند.
5. قبل از پرداخت، درخواست AddMemberRegister با DoSave=false فرستاده می‌شود.
   Backend تعرفه، مالیات، انتقال اعتبار، گرد کردن و مبلغ نهایی را محاسبه می‌کند،
   اما رکورد را ذخیره نمی‌کند.
6. Windows جزئیات مبلغ را در PayForm نشان می‌دهد. پس از تأیید پرداخت، همان ثبت با
   DoSave=true ارسال می‌شود و Backend عضویت و سند مالی را در یک تراکنش ایجاد می‌کند.
7. اگر MembershipType برابر Member باشد، پیش از ادامه درباره آزادشدن تمام جای
   پارک‌های عضو هشدار داده می‌شود.

ثبت فعال، عضویت فعال قبلی را غیرفعال و تاریخ اتمام آن را ثبت می‌کند. مانده اعتبار
بر پایه نوع اعتبار و سقف انتقال تعرفه در Backend محاسبه می‌شود؛ UI نباید این محاسبه
را جایگزین پاسخ مرحله پیش‌نمایش کند.

#### جریان لغو

1. ابتدا GetMemberCurrentCreditInfo خوانده می‌شود. اگر عضویت در اعتبار جاری نباشد،
   لغو ممکن نیست.
2. کاربر نوع لغو را انتخاب می‌کند. عودت وجه فقط تا RefundDeadlineDayCount و بدون
   استفاده از پارکینگ مجاز است؛ تسویه برای اعتبار مدت‌دار مجاز نیست؛ سوختن اعتبار
   مانده را صفر می‌کند.
3. Backend عضویت را غیرفعال، تاریخ اتمام و نوع لغو را ثبت می‌کند و رزرو واجد شرایط
   را فعال می‌سازد.

#### نقش‌ها و دسترسی‌ها

- ایجاد/ویرایش عضو و آغاز ثبت عضویت: ParkingMemberAddOrEdit
- حذف عضو: ParkingMemberDelete
- لغو عضویت: ParkingMembersCreditCancellation

Backend مرجع نهایی authorization است؛ پنهان‌سازی action در UI جایگزین کنترل سمت
Backend نیست.

#### مدل‌های مورد استفاده

| مدل/فیلد | کاربرد |
|---|---|
| MemberRegisterKindEntity.Id و Title | انتخاب و نمایش نوع عضویت |
| MembershipFee و DurationDays | مبلغ پیش‌فرض و تاریخ اتمام |
| TaxValue، MembershipCreditType و MembershipType | مالیات، نمایش نوع اعتبار و تصمیم آزادسازی جای پارک |
| MemberRegisterEntity | شامل MemberId، نوع، مبلغ، مالیات، تاریخ‌ها، IsActive و DoSave |
| MemberRegisterResultDto | شامل Id، CreditAmount، Tax، TransferAmount و TotalAmount |

TariffId، TransferCreditAmount، RoundingValue و اطلاعات ثبت توسط Backend تعیین
می‌شوند. TotalAmount مبلغ گرد‌شده قابل پرداخت است.

#### APIهای ثبت عضویت و وضعیت پوشش

وضعیت APIهای اصلی ثبت عضویت **کامل بر اساس Controller، Entity، DTO و منطق Windows
موجود** است. پاسخ‌ها در پوسته ResponseResultWeb بازمی‌گردند؛ حتی خطای دامنه‌ای
ممکن است HTTP 200 با ResponseResultType ناموفق داشته باشد. UI باید هم HTTP status
و هم ResponseResultType و Message/RealMessage را کنترل کند.

| API | روش | ورودی و خروجی | اثر UI |
|---|---|---|---|
| api/Member/GetMemberRegisterKindsByParkingId?parkingId={id} | GET | فهرست MemberRegisterKindEntity | گزینه‌های ثبت عضویت |
| api/Member/AddMemberRegister | POST | MemberRegisterEntity؛ خروجی MemberRegisterResultDto | پیش‌نمایش با DoSave=false و ثبت نهایی با DoSave=true |
| api/traffic/GetMemberCurrentCreditInfo?memberId={id} | GET | فهرست MemberCreditDto | تشخیص امکان لغو و نمایش وضعیت/نوع اعتبار |
| api/Member/MembershipCreditCancellation | POST | MemberRegisterEntity با CancellingMembershipType | لغو و فعال‌سازی رزرو احتمالی |
| api/Member/Save | POST | MemberDto؛ خروجی long | ذخیره ضروری عضو جدید قبل از آغاز ثبت عضویت |

خطاهای قابل مشاهده شامل عضو ناموجود، تعریف‌نشدن تعرفه برای نوع عضویت، عضویت رزرو
تکراری، پایان مهلت عودت وجه، استفاده از پارکینگ و تسویه اعتبار مدت‌دار است. متن خطا
از پاسخ API نمایش داده می‌شود و قواعد مالی در UI بازتولید نمی‌گردد.

**ناقص/نیازمند تأیید Backend:** DTO بازگشتی MemberDto در منابع فعلی TaxValue را در
سابقه عضویت برنمی‌گرداند، اما مسیر لغو در محاسبه عودت وجه از TaxValue موجود در
payload استفاده می‌کند. این ناسازگاری از خود منابع Windows است؛ UI وب همان payload
موجود را می‌فرستد و نباید برای جبران آن مالیات را حدس بزند. تیم Backend باید مشخص
کند که TaxValue از رکورد ذخیره‌شده خوانده می‌شود یا باید به DTO سابقه افزوده شود.

#### پیاده‌سازی فعلی وب

تب «عضویت» در MemberManagementWorkspace.tsx اکنون مانده اعتبار، تاریخچه، وضعیت
فعال/رزرو و action لغو را نمایش می‌دهد. عضو جدید را ابتدا ذخیره می‌کند، قاعده یک
رزرو را اعمال می‌کند، جایگزینی یا رزرو را از کاربر می‌پرسد، مبلغ/مالیات/تاریخ را از
نوع عضویت پر می‌کند، پیش‌نمایش Backend را نشان می‌دهد و فقط پس از تأیید پرداخت،
درخواست ثبت نهایی را می‌فرستد.

Windows پرداخت نقدی و اتصال مستقیم POS/LCD را در PayForm و تجهیزات محلی انجام
می‌دهد. Browser به این تجهیزات اتصال مستقیم ندارد؛ در وب، «تأیید پرداخت» جایگزین
تأیید اپراتور است و سپس همان ثبت نهایی را ارسال می‌کند. پرداخت آنلاین یا اتصال POS
وابستگی مستقل به سرویس یا Agent تجهیزات است و نباید در UI حدس زده شود.

## ParkingCardForm

- مشاهده‌ی کارت‌های پارکینگ
- ثبت کارت جدید یا گروهی
- مشاهده‌ی وضعیت کارت
- تخصیص کارت به عضو
- فعال یا غیرفعال‌کردن کارت

### تصمیم نهایی طراحی نسخه وب

فرم «مدیریت کارت‌ها» یک استثنای آگاهانه در الگوی Popup CRUD است و باید به‌صورت
workspace متراکم و نزدیک به چیدمان `ParkingCardForm` ویندوزی طراحی شود:

- بالای Grid یک نوار عملیاتی ثابت قرار می‌گیرد؛
- شماره کارت و کنترل‌های ویرایش در همان نوار قرار دارند؛
- ایجاد، ویرایش، حذف، اعمال تغییرات، لغو تغییرات و refresh فقط از Toolbar بالای Grid انجام می‌شوند؛
- برای ایجاد یا ویرایش هیچ Popup یا Dialog فرم استفاده نمی‌شود؛
- انتخاب ردیف، مبنای ویرایش و حذف است؛ حذف ابتدا به‌صورت inline در نوار بالای Grid تأیید می‌شود؛
- تغییرات در Grid به‌صورت draft نگه‌داری و با یک درخواست `SaveAll` ارسال می‌شوند؛
- همهٔ ستون‌های قابل‌فیلتر Grid در این فرم به‌صورت پیش‌فرض ورودی جستجو را داخل همان
  سرستون باز دارند؛ منوی سه‌نقطهٔ هر ستون همچنان گزینه‌های جستجو و بستن ورودی را ارائه می‌کند؛
- دوبارکلیک روی هر ردیف همان ردیف را مستقیماً وارد حالت ویرایش می‌کند؛
- اگر تغییر ذخیره‌نشده وجود داشته باشد، پیش از دوبارکلیک روی ردیف دیگر یا ناوبری به مسیر دیگر
  هشدار سه‌گزینه‌ای «ذخیره و ادامه»، «ادامه بدون ذخیره» و «ماندن در صفحه» نمایش داده می‌شود؛
  در انتخاب ذخیره، ادامه فقط پس از موفقیت `SaveAll` انجام می‌شود و خروج از مرورگر نیز هشدار native دارد؛
- کارت‌خوان و هر نوع اتصال مستقیم به تجهیزات در scope این فرم نیست؛ شماره کارت به‌صورت دستی وارد می‌شود؛
- تخصیص کارت به عضو در این فرم قابل مشاهده است، اما مالکیت/تخصیص باید با workflow عضو و قرارداد Backend هماهنگ بماند.

چینش مرجع Windows شامل نوار بالایی شماره کارت و جستجوی عضو، Grid مرکزی، و نوار وضعیت پایین
است. در نسخه وب، actionهای mutation طبق تصمیم محصول در نوار بالای Grid قرار می‌گیرند؛
فیلترهای جستجو فقط از قرارداد مشترک `AppDataGrid` داخل Header و از منوی سه‌نقطهٔ هر ستون
ارائه می‌شوند و فیلتر جداگانه‌ای بالای صفحه وجود ندارد. نوار پایین فقط برای شمارش رکورد و
وضعیت تغییرات استفاده می‌شود.

### فیلدها و ستون‌های فهرست

ستون‌های قطعی قابل استخراج از فرم Windows عبارت‌اند از: شماره کارت، کد عضویت، نام عضو،
وضعیت فعال/غیرفعال، تاریخ ثبت و توضیحات. شماره کارت و کد عضویت باید در RTL با جهت LTR
نمایش داده شوند. فیلدهای عضو در این فرم read-only هستند و تخصیص کارت نباید با حدس در UI
پیاده‌سازی شود.

### وضعیت پوشش API

وضعیت این فرم **نام endpoint مشخص، قرارداد ناقص** است. عملیات مشاهده‌شده عبارت‌اند از
`CardApi.GetByParkingId`، `CardApi.Save` و `CardApi.SaveAll`؛ نسخه وب این تصمیم را اتخاذ کرده
است که تغییرات محلی را با `CardApi.SaveAll` ارسال کند. مسیر HTTP قطعی، schema کامل DTO،
status code، خطای کارت تکراری، نتیجه‌ی ردیفی و قرارداد رسمی پاسخ هنوز باید از Backend تأیید شود.

حذف کارت در سورس Windows با رکورد `Id < 0` در payload `SaveAll` نمایش داده شده است؛ این
قرارداد فقط پس از تأیید رسمی Backend معتبر است و UI نباید آن را به‌عنوان شناسه موقت رکورد جدید
استفاده کند. اتصال reader، `GetCardStatus` و `GetParkingDoor` برای این فرم وب استفاده نمی‌شوند؛
`GetCardStatus` فقط در workflowهای دیگر مانند ثبت کارت از مسیر عضو، در صورت نیاز، بررسی می‌شود.
