# اجزای مشترک UI

## پروژه‌ی مشترک

بخش عمده‌ی کنترل‌ها در `EosParkingTools` قرار دارد و توسط فرم‌های برنامه‌ی اصلی استفاده می‌شود.

## الگوهای UI قابل استخراج

- جدول با toolbar عملیات
- فرم ویرایش در modal یا پنل جانبی
- فهرست کارت‌محور برای موجودیت‌هایی که نباید در جدول نمایش داده شوند
- فیلتر ستونی داخل سرستون و زیر عنوان، با کنترل باز/بسته‌شدن روی Grid
- صفحه‌بندی
- پیام تأیید حذف
- پیام موفقیت و خطا
- loading overlay
- کنترل ورود پلاک
- کنترل ورود پلاک ایرانی باید در وب با یک component مشترک پیاده‌سازی شود. **رفتار
  فعلی Windows:** `EosPlateControl` در نوار بالای خود انتخاب نوع خودرو شامل سواری/وانت،
  موتور، ون/مینی‌بوس، اتوبوس/کامیون و تریلی دارد. برای خودرو، چهار بخش «دو رقم اول»،
  «حرف پلاک»، «سه رقم میانی» و «کد دو رقمی منطقه» دریافت می‌شود؛ برای موتور، دو بخش
  سه‌رقمی و پنج‌رقمی دریافت می‌شود. مقدار ارسالی در هر دو حالت بدون فاصله یا جداکننده
  است (نمونهٔ خودرو `12ب34567` و نمونهٔ موتور `12345678`). ثبت خودرو تا تکمیل قالب
  منتخب مجاز نیست.
- نمایش تاریخ شمسی و بازه‌ی زمانی

## نیازمندی نسخه‌ی وب

- ایجاد design system مشترک برای دکمه‌ها، فرم‌ها، جدول‌ها و پیام‌ها
- اعمال تراکم ظریف و یکسان در کل برنامه؛ اندازه‌ی فونت، ارتفاع کنترل، padding، radius و shadow نباید در هر صفحه جداگانه تعریف شود.
- تعریف componentهای قابل استفاده در تمام صفحات
- پشتیبانی راست‌به‌چپ و زبان فارسی
- پشتیبانی از تاریخ شمسی
- تعریف stateهای استاندارد: loading، empty، error، unauthorized، success
- جداسازی componentهای عمومی از componentهای مخصوص workflow تردد

## قرارداد `IranianPlateInput`

### وضعیت و منبع

- **رفتار فعلی Windows:** کنترل مبنا `EosPlateControl` در
  `EosParkingTools/EosControls/EosPlateControl.cs` و Designer آن است.
- **پیاده‌سازی فعلی وب:**
  `EosParkingReactUi/src/components/IranianPlateInput.tsx` کنترل مشترک ورود پلاک است.
  این component تنها مالک فرمت، نمایش و پیمایش کیبوردی ورود پلاک در React است.
- **پوشش فعلی:** در گفت‌وگوی «افزودن خودرو» از قابلیت عضویت و ثبت‌نام استفاده می‌شود.
  بررسی source فعلی React نشان می‌دهد سایر رخدادهای `Plate`/`CarPlate` فقط نمایش در
  Grid هستند و ورودی دستی پلاک دیگری وجود ندارد.

### قرارداد استفاده — اجباری

- هر فرم React که **مقدار پلاک ایرانی را ایجاد یا ویرایش** می‌کند باید از
  `IranianPlateInput` استفاده کند؛ ساختن `TextField`، mask یا تقسیم‌بندی مستقل برای
  پلاک در featureها مجاز نیست.
- Grid، گزارش و نمایش فقط‌خواندنی پلاک، مصرف‌کنندهٔ این component نیستند و باید مقدار
  ذخیره‌شده را با `dir="ltr"` نمایش دهند.
- در زمان پیاده‌سازی صفحات فعلاً placeholder، از جمله `manual-traffic`، این کنترل باید
  برای ورود دستی جایگزین شود. مقدار event دوربین پلاک‌خوان نیز باید از طریق prop
  `value` به همین کنترل برسد. نگاشت نوع خودرو در event یا API هنوز **ناقص/نیازمند
  تأیید Backend** است؛ UI نباید آن را حدس بزند.

### API کامپوننت

| prop | نوع | نقش |
|---|---|---|
| `value` | `string` | مقدار canonical پلاک؛ ارقام ذخیره‌شده لاتین‌اند. |
| `onChange` | `(value: string) => void` | مقدار canonical جدید را بازمی‌گرداند. |
| `carType` | `'0' \| '1' \| '2' \| '3' \| '4'` | نوع وسیله؛ `1` موتور و سایر مقادیر قالب خودرو را فعال می‌کنند. |
| `onCarTypeChange` | `(carType) => void` | انتخاب نوع وسیله را به feature مالک state منتقل می‌کند. |
| `label` | `string` | نام قابل‌دسترس گروه کنترل و بخش‌های آن. |
| `disabled`، `error`، `helperText` | اختیاری | وضعیت دسترسی و feedback نزدیک به کنترل. |

### قالب، اعتبارسنجی و رفتار

- برای سواری/وانت، ون/مینی‌بوس، اتوبوس/کامیون و تریلی، ترتیب canonical برابر است با
  `دو رقم + حرف + سه رقم + کد دو رقم منطقه`؛ مثال: `12ب34567`.
- برای موتور، ترتیب canonical برابر با `سه رقم + پنج رقم` است؛ مثال: `12345678`.
- UI ارقام را فارسی نمایش می‌دهد ولی `onChange` ارقام لاتین و بدون فاصله یا جداکننده
  برمی‌گرداند تا با `EosPlateControl` Windows سازگار بماند.
- `isValidIranianPlate(value, carType)` باید پیش از submit توسط feature فراخوانی شود؛
  کامل‌نبودن هیچ بخش نباید به API ارسال شود.
- با رسیدن هر بخش عددی به سقف مجاز، focus به بخش بعد می‌رود؛ پس از آخرین بخش، به کنترل
  tabbable بعدی فرم منتقل می‌شود. انتخاب حرف نیز focus را به سه رقم میانی منتقل می‌کند.
- تغییر نوع وسیله، مقدار پلاک را پاک می‌کند تا داده با قالب جدید ناسازگار نماند.

### الزام‌های ظاهری و دسترس‌پذیری

- نمای کنترل شامل نوار انتخاب نوع وسیله، پرچم، بخش‌های متناسب پلاک و جداکنندهٔ کد
  منطقه است. اندازه‌ها و CSS تنها در component مشترک تعریف می‌شوند.
- همهٔ بخش‌ها label و accessible name مستقل دارند؛ فقط رنگ، وضعیت خطا را منتقل نمی‌کند.
- مقدار فنی پلاک در همهٔ حالت‌های RTL با `dir="ltr"` خوانا باقی می‌ماند.

## قرارداد `MoneyTextField`

### وضعیت و منبع

- **رفتار فعلی Windows:** فیلدهای مالیِ تنظیمات پارکینگ از قالب جداکنندهٔ هزارگان
  استفاده می‌کنند؛ این رفتار برای `MaxTransferCredit`،
  `MinOfNotFoundEnterCar`، `RoundingMoneyBorder` و `RoundingMoneyValue` در
  مستندات پیکربندی پارکینگ ثبت شده است.
- **پیاده‌سازی وب:**
  `EosParkingReactUi/src/components/MoneyTextField.tsx` تنها کنترل مشترک ورود
  مبلغ صحیح است و `EosParkingReactUi/src/utils/formatters.ts` تنها مرجع
  `formatMoney` برای نمایش مبلغ است.

### قرارداد استفاده — اجباری

- همهٔ فیلدها، ستون‌های Grid، خلاصه‌ها و تأییدیه‌هایی که مبلغ ریالی را نمایش
  می‌دهند باید از `formatMoney` استفاده کنند. نمایش مستقیم عدد مالی یا ساختن
  formatter محلی در featureها مجاز نیست.
- هر فیلد قابل ویرایشِ مبلغ صحیح باید از `MoneyTextField` استفاده کند؛ ساختن
  `TextField type="number"` برای مبلغ در featureها مجاز نیست.
- درصدها، تعدادها، شناسه‌ها و مدت‌زمان‌ها مبلغ نیستند و از این قرارداد مستثنا
  هستند؛ مانند `TaxRate`، تعداد روز و ساعت.
- مقدار نمایشی با ارقام لاتین، جهت `ltr` و جداکنندهٔ سه‌رقمی نمایش داده می‌شود؛
  مثال: `1,234,567`. کنترل ورودی ارقام فارسی و عربی را نیز می‌پذیرد.
- مقدار `onValueChange` و مقدار ارسالی به API همواره فقط شامل رقم لاتین و بدون
  جداکننده است. component هیچ مبلغ، مالیات، rounding یا مبلغ نهایی را محاسبه
  نمی‌کند.

### پوشش فعلی

- تعریف نوع عضویت: حق عضویت در فرم و Grid.
- تنظیمات پارکینگ: مبلغ مفقودی کارت، سقف انتقال اعتبار، حداقل دریافتی خودرو با
  ورود نامشخص و دو مقدار گردکردن.
- تعرفه: هزینهٔ ورود بر اساس نوع خودرو و همهٔ نرخ‌های بازه‌ای و تنظیمات گردکردن.
- عضویت و ثبت‌نام: حق عضویت قابل ویرایش، مالیات، مانده اعتبار، سابقهٔ عضویت و
  تمام ردیف‌های تأیید پرداخت.

## قرارداد فیلتر ستونی مشترک Grid

این قرارداد برای تمام `AppDataGrid`ها اجباری است و باید از طریق همان component عمومی
پیاده‌سازی شود؛ feature نباید فیلتر داخل سرستون یا منطق جستجو را دوباره بسازد.

- ورودی جستجو داخل همان سلول سرستون و زیر عنوان ستون قرار می‌گیرد و در حالت پیش‌فرض
  مخفی است. دکمهٔ سه‌نقطهٔ هر سرستون، یک منوی شناور متصل به همان ستون باز می‌کند؛
  گزینهٔ «نمایش جستجوی ستون» از همان منو ورودی همان ستون را فعال می‌کند. فیلتر و
  گزینه‌های آن نباید در ردیف مستقل یا نوار ابزار جداگانهٔ بالای Grid قرار بگیرند.
- فعال‌بودن جستجو برای هر ستون مستقل است؛ `defaultFilterOpen` فقط ورودی همهٔ ستون‌های
  قابل‌فیلتر را از ابتدا باز می‌کند. ورودی فشرده و ظریف است و از نظر background، Border،
  radius و تراکم بخشی از Header محسوب می‌شود، نه یک ردیف داده.
- در فرم‌هایی که جستجوی فوری جزء نیاز اصلی است، prop `defaultFilterOpen` می‌تواند
  ورودی‌های ستون‌های قابل‌فیلتر را از ابتدا باز کند. این تنظیم استثنای صفحه‌ای است
  و قرارداد ظاهری/رفتاری را تغییر نمی‌دهد.
- `filterable` به‌صورت پیش‌فرض فعال است؛ `allowSearchOptions` و
  `allowCaseSensitive` برای سناریوهایی که گزینه‌های مربوط لازم نیستند قابل غیرفعال‌سازی
  هستند. حالت اولیهٔ جستجو با `defaultSearchMode` و `defaultCaseSensitive` تعیین می‌شود.
- هر ورودی به ستون خودش تعلق دارد و چند فیلتر هم‌زمان با منطق AND روی ردیف‌های
  موجود در UI اعمال می‌شوند. ستون‌هایی که مقدار قابل جستجو ندارند می‌توانند
  `filterable: false` شوند؛ برای مقدار محاسباتی، `getFilterValue` باید مقدار متنی
  قابل جستجو را تعیین کند.
- گزینه‌های مشترک جستجو شامل `contains`، `startsWith` و `equals`، انتخاب حساسیت به
  بزرگی حروف و پاک‌کردن همهٔ فیلترهاست. همهٔ این کنترل‌ها باید label و accessible name
  داشته باشند و در RTL/LTR از جهت صفحه پیروی کنند.
- منوی ستون باید accessible name، `aria-haspopup` و وضعیت باز/بسته داشته باشد؛ ستون
  دارای فیلتر فعال باید در Header نشانهٔ بصری داشته باشد. انتخاب همه و انتخاب ردیف‌ها
  فقط روی مجموعهٔ قابل‌مشاهده پس از فیلتر اعمال می‌شود و selectionهای خارج از فیلتر
  نباید بی‌دلیل حذف شوند.
- این فیلتر در گریدهای عادی یک فیلتر client-side روی مجموعهٔ از قبل دریافت‌شده است و
  API جدیدی نمی‌خواهد. در گریدهای server-side، صفحه‌بندی‌شده یا حجیم، همین قرارداد
  UI حفظ می‌شود اما مقدار/گزینه‌ها باید به query و قرارداد رسمی API نگاشت شوند؛
  دریافت کل داده برای شبیه‌سازی فیلتر server-side مجاز نیست.

### رویداد ویرایش با دوبارکلیک و تغییرات ذخیره‌نشده

- `AppDataGrid` می‌تواند callback اختیاری `onRowDoubleClick` داشته باشد؛ featureهایی که
  ویرایش ردیفی دارند باید با دوبارکلیک همان ردیف را به editor موجود منتقل کنند.
- فرم‌های draftدار باید پیش از تغییر مسیر یا انتقال به editor ردیف دیگر، وضعیت dirty را بررسی
  کنند. پیام استاندارد شامل سه انتخاب «ذخیره و ادامه»، «ادامه بدون ذخیره» و «ماندن در صفحه» است؛
  انتخاب ذخیره باید موفقیت درخواست persistence را بررسی کند و سپس ادامه دهد. برای خروج کامل از
  مرورگر نیز `beforeunload` باید هشدار native ایجاد کند و `returnValue` آن بر اساس زبان فرم
  مقداردهی شود؛ متن سفارشی ممکن است توسط مرورگر با متن استاندارد خودش جایگزین شود.

## قرارداد فهرست کارت‌محور و Popup CRUD

این قرارداد برای همه‌ی فرم‌هایی که موجودیت را به‌صورت کارت نمایش می‌دهند اجباری است:

> **استثنای فرم مدیریت کارت:** `ParkingCardForm` فهرست جدولی و عملیاتی است، نه فهرست
> کارت‌های نمایشی. این فرم از Popup/Dialog برای ایجاد و ویرایش استفاده نمی‌کند؛ actionهای
> mutation و editor آن در Toolbar بالای Grid قرار می‌گیرند. این استثنا فقط برای مدیریت کارت‌ها
> معتبر است و الگوی Popup عمومی سایر فرم‌ها را تغییر نمی‌دهد.

- صفحه‌ی فهرست فقط باید شامل action اصلی ایجاد و مجموعه‌ی کارت‌های رکوردها باشد؛ فرم ایجاد نباید به‌صورت یک باکس ثابت بالای کارت‌ها نمایش داده شود.
- هر کارت خلاصه‌ی اطلاعات اصلی رکورد را نمایش می‌دهد و actionهای ویرایش و حذف را در اختیار می‌گذارد.
- فهرست کارت‌ها باید responsive باشد و در صفحه‌های کوچک بدون اسکرول افقی به چند ردیف تبدیل شود.
- برای ایجاد و ویرایش، از یک Popup مشترک مانند `CrudDialog` استفاده شود؛ برای این دو workflow Popup جداگانه ساخته نشود.
- Popup باید عنوان context-aware، محتوای فرم، دکمه‌ی «لغو» و دکمه‌ی Primary «تأیید/ذخیره» داشته باشد.
- دکمه‌ی لغو Popup را بدون mutation می‌بندد؛ دکمه‌ی تأیید validation و mutation را اجرا می‌کند و در زمان درخواست loading/disabled می‌شود.
- خطای validation کنار فیلد مربوط و خطای عمومی API در ابتدای محتوای Popup نمایش داده شود.
- پس از ایجاد یا ویرایش موفق، Popup بسته و فهرست کارت‌ها refresh شود؛ در خطا Popup باز بماند تا کاربر بتواند اصلاح کند.
- Popup مشترک باید generic باشد و فقط پوسته و رفتار عمومی را فراهم کند؛ فیلدها، مدل، validation و API هر موجودیت باید از بیرون به آن تزریق شود.
- حذف رکورد از کارت باید قبل از mutation با `ConfirmDialog` تأیید شود و نام/شناسه رکورد را نشان دهد.
