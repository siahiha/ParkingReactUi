# اجزای مشترک UI

## پروژه‌ی مشترک

بخش عمده‌ی کنترل‌ها در `EosParkingTools` قرار دارد و توسط فرم‌های برنامه‌ی اصلی استفاده می‌شود.

## اجزای مهم

| جزء | نقش پیشنهادی در نسخه‌ی وب |
|---|---|
| `EosBaseForm` | layout و رفتار مشترک صفحات |
| `EosBaseDialogForm` | modal و فرم‌های تأیید |
| `EosBaseRibbonForm` | ساختار navigation و commandها |
| `EosGridControl` | جدول داده |
| `EosPagingToolsGridControl` | جدول صفحه‌بندی‌شده |
| `EosEntityModifyToolsControl` | عملیات ایجاد، ویرایش، حذف و ذخیره |
| `CrudDialog` | پوسته‌ی مشترک Popup برای ایجاد و ویرایش فرم‌ها |
| `AppGroupBox` | گروه‌بندی مشترک و معنایی فیلدها با Caption روی خط بالایی Border |
| `AppDataGrid` | Grid/Table مشترک برای فهرست‌های جدولی با ظاهر فشرده، انتخاب تک/چندردیفی، حذف گروهی، جلوگیری از اسکرول افقی، ستون‌های Boolean فشرده و جهت متن متناسب با زبان |
| `AppRecordCard` | پوسته‌ی مشترک کارت برای فهرست‌های کارت‌محور |
| `EosPlateControl` | ورود و نمایش پلاک |
| `EosPlateSelector` | انتخاب پلاک خودرو |
| `EosParkingInfoControl` | خلاصه‌ی اطلاعات پارکینگ |
| `EosDateTimePicker` | انتخاب تاریخ و ساعت شمسی |
| `EosLogin` | کنترل‌های ورود |
| `EosWaitPanel` | loading و انتظار پاسخ |
| `EosIpCamView` | نمایش دوربین |
| Filter Panelها | فیلتر مشترک گزارش‌ها |

## الگوهای UI قابل استخراج

- جدول با toolbar عملیات
- فرم ویرایش در modal یا پنل جانبی
- فهرست کارت‌محور برای موجودیت‌هایی که نباید در جدول نمایش داده شوند
- فیلتر بالای جدول
- صفحه‌بندی
- پیام تأیید حذف
- پیام موفقیت و خطا
- loading overlay
- کنترل ورود پلاک
- نمایش تاریخ شمسی و بازه‌ی زمانی

## نیازمندی نسخه‌ی وب

- ایجاد design system مشترک برای دکمه‌ها، فرم‌ها، جدول‌ها و پیام‌ها
- اعمال تراکم ظریف و یکسان در کل برنامه؛ اندازه‌ی فونت، ارتفاع کنترل، padding، radius و shadow نباید در هر صفحه جداگانه تعریف شود.
- تعریف componentهای قابل استفاده در تمام صفحات
- پشتیبانی راست‌به‌چپ و زبان فارسی
- پشتیبانی از تاریخ شمسی
- تعریف stateهای استاندارد: loading، empty، error، unauthorized، success
- جداسازی componentهای عمومی از componentهای مخصوص workflow تردد

## قرارداد فهرست کارت‌محور و Popup CRUD

این قرارداد برای همه‌ی فرم‌هایی که موجودیت را به‌صورت کارت نمایش می‌دهند اجباری است:

- صفحه‌ی فهرست فقط باید شامل action اصلی ایجاد و مجموعه‌ی کارت‌های رکوردها باشد؛ فرم ایجاد نباید به‌صورت یک باکس ثابت بالای کارت‌ها نمایش داده شود.
- هر کارت خلاصه‌ی اطلاعات اصلی رکورد را نمایش می‌دهد و actionهای ویرایش و حذف را در اختیار می‌گذارد.
- فهرست کارت‌ها باید responsive باشد و در صفحه‌های کوچک بدون اسکرول افقی به چند ردیف تبدیل شود.
- برای ایجاد و ویرایش، از یک Popup مشترک مانند `CrudDialog` استفاده شود؛ برای این دو workflow Popup جداگانه ساخته نشود.
- Popup باید عنوان context-aware، محتوای فرم، دکمه‌ی «لغو» و دکمه‌ی Primary «تأیید/ذخیره» داشته باشد.
- دکمه‌ی لغو Popup را بدون mutation می‌بندد؛ دکمه‌ی تأیید validation و mutation را اجرا می‌کند و در زمان درخواست loading/disabled می‌شود.
- خطای validation کنار فیلد مربوط و خطای عمومی API در ابتدای محتوای Popup نمایش داده شود.
- پس از ایجاد یا ویرایش موفق، Popup بسته و فهرست کارت‌ها refresh شود؛ در خطا Popup باز بماند تا کاربر بتواند اصلاح کند.
- Popup مشترک باید generic باشد و فقط پوسته و رفتار عمومی را فراهم کند؛ فیلدها، مدل، validation و API هر موجودیت باید از بیرون به آن تزریق شود.
- حذف رکورد از کارت باید قبل از mutation با `ConfirmDialog` تأیید شود و نام/شناسه رکورد را نشان دهد.
