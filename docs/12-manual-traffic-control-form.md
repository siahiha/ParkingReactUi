# مستند کامل فرم کنترل تردد دستی

## وضعیت سند

| مورد | مقدار |
|---|---|
| فرم | `ManualTrafficControlForm` |
| عنوان نمایشی | کنترل تردد |
| وضعیت | رفتار WinForms مستند؛ قرارداد Backend باید به‌صورت OpenAPI نسخه‌دار تحویل شود؛ معماری وب/سرویس تجهیزات مستند |
| منبع اصلی | فایل‌های `ManualTrafficControlForm.*.cs` در `EosParkingProfessional/EosForms/ManualTrafficControl/` |

برچسب «رفتار فعلی» از کد و Designer استخراج شده است. برچسب «پیشنهاد نسخه وب» تصمیم معماری برای نسخه جدید است و نباید رفتار فعلی تلقی شود.

## ۱. هدف و جایگاه فرم

فرم برای کنترل لحظه‌ای ورود و خروج خودرو در یک درب مشخص و برای شیفت کاربر طراحی شده است. فرم هم‌زمان نقش‌های زیر را دارد:

- دریافت شناسه خودرو از اپراتور، کارت، QR، UHF و دوربین پلاک‌خوان؛
- یافتن عضو، خودرو و تردد باز؛
- اجرای قواعد عضویت، تعرفه و فهرست‌های کنترلی؛
- ثبت ورود و خروج؛
- محاسبه و دریافت پرداخت؛
- چاپ قبض؛
- ارسال فرمان به راهبند؛
- نمایش ترددهای اخیر و وضعیت تجهیزات؛
- ثبت بار ورودی یا خروجی برای تردد انتخاب‌شده.

## ۲. مسیر دسترسی و پیش‌شرط‌ها

### رفتار فعلی

فرم از `MainForm` و پس از انتخاب پارکینگ باز می‌شود. در زمان نمایش:

1. نشست کاربر refresh می‌شود.
2. پارکینگ فرم با `CurrentUser.CurrentParking` مقایسه می‌شود.
3. درب متناظر با `CurrentUser.DoorShift` از `ParkingApi.GetParkingDoor` دریافت می‌شود.
4. نوع درب، نوع مجوز ورود و تجهیزات درب روی UI اعمال می‌شود.
5. تعرفه‌ها و ترددهای اخیر بارگذاری می‌شوند.

در صورت نبودن پارکینگ جاری یا درب/شیفت معتبر، پیام خطا نمایش داده شده و فرم بسته می‌شود.

### نقش و مجوز

مجوزهای مشاهده‌شده در کد:

| مجوز/شرط | اثر |
|---|---|
| `ParkingManualIOEditCarInfo` | فعال یا غیرفعال‌کردن پنل اطلاعات خودرو |
| `parkingManualIOBillControl` | نمایش کنترل صدور فیش کنترلی |
| `ParkingManualIOSetTarrif` | امکان جابه‌جایی تعرفه با میانبر Ctrl+W/Ctrl+Q |
| `LockOprator.HasAccessToCargoAbility` | نمایش عملیات ثبت بار |
| `ExitPermission` در تنظیمات | فعال‌شدن بررسی مجوز خروج |

ثبت نهایی نام مجوزها، کد عددی و تفکیک `hidden`، `disabled` و `unauthorized` نیازمند تأیید رجیستری رسمی مجوزهاست.

### ۳.۳.۱ منطق چهار دکمهٔ ورود، خروج، جستجو و لغو در Windows

**رفتار فعلی؛ استخراج از کد در ۲۰۲۶-۱۱-۱۰.** این بخش قرارداد مشاهده‌شدهٔ کلاینت
Windows است؛ اشکال‌های آن در انتهای بخش جدا شده‌اند و تأیید منطق مطلوب محصول نیستند.

دو تصمیم مستقل گرفته می‌شود:

1. `InitFormByTraficType` در `ManualTrafficControlForm.Lifecycle.cs:38`، فقط با
   `currentDoor.DoorType` نمایش ورود و خروج را تنظیم می‌کند: ورود (`Entrance=0`)،
   خروج (`Exit=1`)، هردو (`Both=2`) و درب داخلی (`EnternalDoor=3`). درب داخلی هیچ‌یک
   از دو دکمه را نشان نمی‌دهد. تعریف enum در
   `Infrastructure/EosParking.Core/Enums/DoorTypes.cs` از ریشهٔ solution است.
2. `SetFormCarInfo` در `ManualTrafficControlForm.CarInfo.cs:288`، پس از شناسایی خودرو،
   فعال‌بودن دکمه‌ها و نمایش جستجو را بر اساس `EnterDateTime` پاسخ تعیین می‌کند.
   در این تصمیم، `DumpId` و `ExitDateTime` بررسی نمی‌شوند؛ بنابراین تعبیر «تردد باز»
   وابسته به معنای پاسخ استعلام است، نه کنترل مستقل خروج در این تابع.

جدول زیر برای پاسخ معتبر، پس از عبور از بررسی عضو/کارت، و با تنظیم
«خروج بدون ورودی» خاموش است. «بدون ورود» در جدول یعنی `EnterDateTime == null` و
«دارای ورود» یعنی تاریخ بزرگ‌تر از `DateTime.MinValue`؛ حالت مرزی تاریخ حداقل پایین آمده است.

|---|---|---|---|---|---|
| ورودی | بدون ورود | نمایان و فعال | مخفی | نمایان و فعال | نمایان و فعال |

منبع جدول: `Lifecycle.cs:44–45` و `CarInfo.cs:377–499` در پوشهٔ فرم.

**شروع، بازنشانی و فوکوس:** در Designer، ورود، خروج و لغو غیرفعال و جستجو مخفی‌اند؛
نمایش ورود/خروج پس از دریافت درب تعیین می‌شود. اگر `carInfo` تهی باشد یا هیچ‌کدام از
پلاک، کارت، کد عضو و نام عضو را نداشته باشد، پنل چهار دکمه غیرفعال می‌شود و اطلاعات
جاری پاک می‌شود (`CarInfo.cs:312–329`). بازنشانی، `Visible` جستجو را صریحاً تغییر
نمی‌دهد؛ جستجوی نمایان ممکن است پس از لغو نمایان ولی غیرفعال باقی بماند. پس از
شناسایی، اولویت فوکوس برای دکمهٔ نمایان و فعال، خروج ← ورود ← جستجو است
(`Interaction.cs:95–111`). در حالت انتخاب خودروی عضو نیز لغو فعال می‌ماند
(`CarInfo.cs:441–455`).

**اثر تنظیمات و اجرای عملیات:**

- «خروج بدون ورودی» در هر سه شاخهٔ تصمیم، `carExitButton.Enabled` را `true` می‌کند؛
  `Visible` را تغییر نمی‌دهد. بنابراین درب ورودی با این گزینه دکمهٔ خروج نشان نمی‌دهد.
  در handler خروج، اگر زمان ورود `null` باشد، ابتدا `CreateEnterDump(true)` با
  `EnterDateTimeFake=true` اجرا می‌شود، سپس اطلاعات دوباره استعلام و `DoExitDump`
  فراخوانی می‌شود (`Exit.cs:17–46`، `Entry.cs:134`). این گزینه فقط آزادکردن دکمه نیست.
- «ورود چندباره بدون خروج» مستقیماً در جدول نمایش/فعال‌بودن دکمه‌ها شرط ندارد؛ در
  اجرای خودکار از دوربین ورودی و ورود خودکار اعضا دخالت دارد (`CarInfo.cs:574–600`).
- ورود و خروج هنگام اجرای handler خود موقتاً غیرفعال می‌شوند. در `finally` دوباره
  فعال می‌شوند، ولی اگر فرم پس از موفقیت پاک شده باشد، پنل والد همچنان غیرفعال است
  (`Entry.cs:208–238`، `Exit.cs:17–60`). فعال‌بودن دکمه تضمین موفقیت عملیات نیست:
  الزام کارت/پلاک/تصویر، فهرست کنترلی، مجوز خروج و پاسخ API جداگانه بررسی می‌شوند.
- ورود خودکار برای همه، ورود فعال و خروج غیرفعال را لازم دارد؛ تنظیم خروج بدون ورود
  استثنا است. ورود خودکار اعضا، «ورود فعال و خروج غیرفعال» یا گزینهٔ ورود چندباره،
  همراه با کد عضو غیرتهی را لازم دارد. خروج خودکار، خروج فعال و ورود غیرفعال، همراه با حالت «برای همه»
  یا حالت «برای اعضا» و کد عضو غیرتهی را لازم دارد (`CarInfo.cs:579–609`). این مسیرها
  خود handler دکمه را صدا می‌زنند؛ شرط `Visible` در آن‌ها وجود ندارد. کنترل‌های جهت
  دوربین و `cancelAutoSystem` پیش از این تصمیم اجرا می‌شوند (`CarInfo.cs:512–577`).
- `DoorTrafficTypes` شامل همه، اعضا و غیر اعضاست؛ در `InitFormByTraficType` استفادهٔ
  مستقیم از `currentDoor.DoorTrafficType` کامنت شده است. این فیلد شرط مستقیم نمایش
  چهار دکمه نیست. محدودیت اعضا در مسیرهای دیگری اعمال می‌شود: تنظیم محلی فقط اعضا
  برای شیوهٔ شناسایی پلاکی (`CarInfo.cs:157–164`) و تنظیم تجهیز کارت‌خوان
  (`CardReaders.cs:86–92`). این موارد با نوع جهت درب اشتباه نشوند.

**عمل جستجو:** `carSearchButton_Click`، فرم `ManageTrafficRecordForm` همان پارکینگ را
باز می‌کند و اطلاعات خودرو/عضو جاری را به آن می‌دهد (`CarInfo.cs:685–703`). پس از
بستن آن، `currentCarInfo` تهی می‌شود و کد تلاش می‌کند ورودی را دوباره Validate کند.
این دکمه «استعلام خودرو» یا «استعلام مجدد» نیست و صرفاً فیلتر گرید پایین صفحه هم نیست.

**عمل لغو:** `cancelButton_Click` و `CancelForm`، اطلاعات خودرو/عضو، پلاک، کارت، تصویر،
وضعیت درب و پیام تکمیلی را پاک می‌کنند؛ پنل عملیات غیرفعال و فوکوس به پلاک برمی‌گردد.
سپس تشخیص پلاک ادامه پیدا می‌کند، فلگ‌های توقف خواندن کارت برداشته می‌شوند و صف UHF
خوانده می‌شود (`Interaction.cs:53–86`). این عملیات API حذف یا برگشت تردد ثبت‌شده ندارد.

**ناقص/نیازمند تأیید پیش از انتقال به وب:**

- شاخهٔ درب ورودی با شرط `EnterDateTime != null || EnterDateTime > DateTime.MinValue`
  فعال می‌شود؛ یعنی با وجود ورود قبلی. با این حال پیام «ورودی برای این خودرو ثبت نشده»
  نشان می‌دهد، ورود را فعال نگه می‌دارد و جستجو را نمایش می‌دهد (`CarInfo.cs:397–413`).
  کنترل منع ورود قبلی در `CreateEnterDump` نیز کامنت شده است (`Entry.cs:103–109`).
  پیام و شرط ناسازگارند؛ قصد محصول برای ورود مجدد از این کد قطعی نیست.
- `DateTime.MinValue` یکسان با `null` مدیریت نشده است: درب ورودی وارد شاخهٔ خاص بالا
  می‌شود؛ درب خروجی جستجو را نشان می‌دهد؛ درب دوطرفه/داخلی با وجود فعال‌شدن حالت ورود،
  جستجو را نشان نمی‌دهد، چون شرط نمایش آن فقط `== null` است (`CarInfo.cs:397–445`).
- در مسیر دوربین ورودی، داخل شرط `carExitButton.Enabled`، شرط مخالف
  `!carExitButton.Enabled` آمده است؛ شاخهٔ هشدار/ورود چندبارهٔ داخل آن قابل اجرا نیست
  (`CarInfo.cs:541–568`). مسیر جداگانهٔ ورود چندباره در خط ۵۷۴ همچنان وجود دارد.
- در مسیر جستجو، آرگومان‌های `isCard`/`isMember` و Validate پس از بازگشت، در چند جا
  بر خالی‌بودن رشته شرط گذاشته‌اند؛ نمی‌توان شناسایی مجدد صحیح همهٔ حالت‌های بدون پلاک
  را تضمین کرد (`CarInfo.cs:691–703`).
- خطای عضو غیرفعال، عضو ناموجود یا کارت ناموجود با `return` زودهنگام خارج می‌شود؛
  این مسیرها بازنشانی کامل و یکسان دکمه‌ها ندارند و ممکن است وضعیت قبلی باقی بماند
  (`CarInfo.cs:292–295` و `349–369`).

**رفتار فعلی وب پس از جایگزینی دکمه‌ها:** سه دکمهٔ قبلی با چهار دکمهٔ مستقل
«ورود»، «خروج»، «جستجو» و «لغو» جایگزین شده‌اند. دکمه‌های قابل نمایش، هم‌اندازه و
در یک ردیف بالای باکس عملیات و بیرون از اسکرول اطلاعات هستند؛ مخفی‌شدن هرکدام تابع وضعیت زیر است:

ظاهر دکمه‌ها آیکون خطی و متن را هم‌زمان نگه می‌دارد: ورود با رنگ success، خروج
با رنگ primary، جستجو با ذره‌بین و لغو با علامت بستن. عمل اصلیِ قابل اجرا زمینهٔ
بسیار ملایم رنگی و تأکید باریک در لبهٔ پایین دارد؛ جستجو زمینهٔ ساده دارد و دکمه‌های
غیرفعال خنثی هستند. ارتفاع مشترک ۳۲ پیکسل، عرض حداکثر ۸۸ پیکسل و آیکون خطی ۱۶
پیکسل بدون قاب، جایگزین ظاهر درشت قبلی شده‌اند. دکمه‌ها در ابتدای ردیف و با فاصلهٔ
۸ پیکسل قرار می‌گیرند؛ در عرض محدود کوچک‌تر می‌شوند و در یک ردیف باقی می‌مانند.
رنگ‌ها، حلقهٔ فوکوس کیبورد و بازخورد هاور/فشردن از tokenهای Theme استفاده می‌کنند. دکمهٔ لغو در حالت فعال با متن و آیکن پرکنتراست، زمینهٔ خنثی ملایم و وزن ۶۰۰ نمایش داده می‌شود تا با حالت غیرفعال اشتباه نشود؛ وضعیت غیرفعال همچنان کم‌رنگ است.
جهت آیکون ورود/خروج با RTL هماهنگ و transition با reduced-motion خاموش می‌شود.
این اصلاح صرفاً بصری است.

- نوع درب از `GET api/Parking/GetParkingDoor?doorId={doorId}` خوانده و شناسه و
  `DoorType` آن در service با Zod اعتبارسنجی می‌شوند. ورود در نوع ۰ و ۲ و خروج در
  نوع ۱ و ۲ نمایش داده می‌شوند. درب داخلی هیچ‌یک را نشان نمی‌دهد. هنگام دریافت
  یا خطای دادهٔ درب، ثبت مجاز نیست؛ پاسخ دیررس درب قبلی نادیده گرفته می‌شود و
  دکمهٔ به‌روزرسانی بالای صفحه امکان تلاش مجدد دارد.
- بعد از شناسایی، ورود فقط بدون ورود باز و خروج فقط با `DumpId` مثبت، زمان ورود
  معتبر و بدون زمان خروج معتبر فعال می‌شود. تاریخ حداقل مانند مقدار خالی است.
  محدودیت‌های عضو، کارت، مجوز خروج و انتخاب خودرو همچنان کنترل می‌شوند. شناسایی
  با خروج از ورودی، Enter کارت یا کد عضو، یا دریافت پلاک دوربین انجام می‌شود؛ این کار به‌تنهایی
  تردد ثبت نمی‌کند.
- جستجو پس از شناسایی در درب ورودی همیشه و در سایر درب‌ها فقط بدون ورود باز نمایان
  است. مجوز موجود منوی «مدیریت ورودها و خروج‌ها» برای اجرای آن لازم است. فرم موجود
  سوابق همان پارکینگ در `AppPopup` با پلاک، کارت، کد عضو و درب جاری باز می‌شود؛
  اطلاعات در بخش ثبت پیش‌پر می‌شوند و سوابق با فیلتر ستونی قابل جستجو هستند.
  پس از بستن، خودرو دوباره استعلام و گریدهای درب تازه می‌شوند؛ بستن هنگام عملیات
  یا دیالوگ بازِ داخل سوابق غیرفعال است.
- لغو با وجود ورودی یا اطلاعات جاری فعال است؛ ورودی‌ها، مشخصات، تصویر آخرین تشخیص
  و پیام‌ها را پاک و فوکوس را به اولین بخش پلاک برمی‌گرداند. هیچ ترددی حذف نمی‌شود.
  پس از پاک‌شدن، جستجو مخفی و ورود/خروج غیرفعال‌اند. هنگام عملیات در حال اجرا،
  دکمه‌ها قفل می‌شوند.

**تفاوت‌های عمدی و موارد باز:** محافظ موجود وب برای جلوگیری از ورود تکراری حفظ شده؛
در درب ورودی نیز وجود ورود باز، دکمهٔ ورود را غیرفعال می‌کند. شاخهٔ متناقض Windows
که در جدول بالا ثبت شد، بازتولید نشده است. مطابق تصمیم محصول در بخش جریان ثبت خروج، خروج بدون
ورود به تعیین ورود توسط اپراتور در مدیریت سوابق نیاز دارد؛ دکمهٔ جستجو این مسیر را
در اختیار می‌گذارد و UI ورود ساختگی نمی‌سازد. گزینهٔ ورود ساختگی و ورود/خروج خودکارِ
تنظیم‌پذیر Windows در این تغییر اضافه نشده‌اند. قرارداد payload ثبت و پرداخت تغییر
نکرده و authorization نهایی همچنان با API است.

### ۳.۶.۱ طراحی وب فعلی منوی کنترل ورود و خروج

این بخش قرارداد چینش وبِ فعلی برای آیتم `manual-traffic` است و نباید با صفحهٔ وب
«مدیریت ورودها و خروج‌ها» یا فرم `ManageTrafficRecordForm` ادغام شود:

- ستون کنترل در فارسی سمت راست و ستون تصاویر سمت چپ است؛ انتخاب‌گر درب کنار refresh قرار دارد و نوع دربِ انتخاب‌شده از پاسخ API به‌صورت ورودی، خروجی، ورود و خروج یا داخلی به‌شکل متن ساده و بدون کادر در بالای صفحه نمایش داده می‌شود؛ هنگام دریافت و خطا، وضعیت در حال دریافت/نامشخص جایگزین نوع قبلی است. در انگلیسی جهت ستون‌ها با زبان هماهنگ می‌شود.
- شناسایی خودرو همان ورودی‌های قبلی را دارد: پلاک در نیمهٔ سمت شروع زبان و شماره کارت و کد عضو زیر هم در نیمهٔ مقابل. در موبایل باریک، پلاک بالای ورودی‌ها قرار می‌گیرد.
- نام عضو، مشخصات کوتاه خودرو و زمان ورود در بدنهٔ عملیات دیده می‌شوند. پس از شناسایی موفق عضو از روی پلاک، شماره کارت یا کد عضویت، کارت مشخصات خودکار کنار فرم باز می‌شود؛ کد ملی، عکس عضو، مشخصات کامل خودرو، اشتراک‌ها، تصویر ورود و ویرایش/افزودن خودرو در آن هستند. برای مهمان یا استعلام ناموفق، بازشدن خودکار انجام نمی‌شود. پس از بستن، استعلام مجدد یا انتخاب خودروی همان عضو کارت را دوباره باز نمی‌کند؛ تغییر ورودی و شناسایی دوباره آن را باز می‌کند. دکمهٔ «مشخصات» برای بازکردن دستی باقی است. بستن با Escape یا دکمهٔ بستن ممکن است و بازشدن دستی یا خودکار فوکوس را جابه‌جا نمی‌کند.
- کارت مشخصات عرض ۴۰۰ پیکسل با سقف عرض viewport دارد: عکس یا آواتار جایگزین در کنار نام و شناسه‌های عضو، بخش مستقل خودرو شامل نام، رنگ، مدل و زمان ورود، و ردیف‌های اشتراک با نشان متنی فعال/رزرو، مانده و بازهٔ اعتبار. بنا به تصمیم محصول، پلاک و تعرفه در این کارت نمایش داده نمی‌شوند؛ رنگ و مدل در دو ستون و زمان ورود در یک ردیف کامل قرار می‌گیرند. تصویر ورود در قاب کوچک بدون کشیدگی باقی می‌ماند. عنوان و دکمهٔ بستن بالا و عملیات افزودن/ویرایش خودرو پایین ثابت‌اند؛ در ارتفاع محدود فقط بدنه اسکرول می‌شود و اسکرول جداگانهٔ اشتراک‌ها حذف شده است. حاشیهٔ باریک، سایهٔ محدود، رنگ‌های Theme در هر دو حالت روشن/تیره و کاهش حرکت رعایت می‌شوند. فوکوس/هاور داخل کارت مشخصات باعث نمایش Tooltip پنل زیرین نمی‌شود. منبع ظاهر و ساختار: `TrafficIdentitySummary.tsx`، `TrafficIdentityDetails.tsx` و `trafficWorkspace.css`؛ مجوزها و API تغییر نکرده‌اند.
- چیدمان داخلی کارت فشرده است: نوار عنوان ۳۳ پیکسل، فاصلهٔ عمودی بدنه ۸ پیکسل و برچسب/مقدار شناسه‌ها و مشخصات خودرو کنار هم قرار می‌گیرند؛ متن بلند همچنان به خط بعد می‌رود. بازشدن خودکار و دستی با محوشدن و حرکت رو به بالای ۶ پیکسلی در ۲۰۰ میلی‌ثانیه و بستن با محوشدن ۱۲۰ میلی‌ثانیه‌ای همراه است؛ با `prefers-reduced-motion: reduce` هر دو بدون حرکت و تأخیر اجرا می‌شوند. بررسی مرورگر در `traffic-identity.spec.ts` فشردگی کارت، اجرای مجدد افکت پس از بازکردن، وضعیت کاهش حرکت و دسترسی به عملیات را پوشش می‌دهد.
- انتخاب خودرو برای عضو چندخودرویی یا بدون خودروی انتخاب‌شده و هشدارهای سیاست تردد در خود فرم می‌مانند. در ارتفاع محدود، فقط بدنهٔ اطلاعات اسکرول می‌شود؛ چهار دکمهٔ مستقل ورود، خروج، جستجو و لغو، مطابق قواعد بخش ۳.۳.۱، در یک ردیف بالای باکس عملیات و بیرون از این اسکرول هستند؛ جزئیات عضو و خودرو، توضیحات و هشدارها زیر دکمه‌ها قرار می‌گیرند. ترتیب DOM نیز با همین ترتیب بصری هماهنگ است. ورودی تاریخ و ساعت ورود/خروج در این صفحه وجود ندارد.
- تصویر زنده و آخرین تشخیص در دسکتاپ کنار هم با سهم تقریبی ۶۰/۴۰ نمایش داده می‌شوند. آخرین تشخیص شامل زمان، تصویر کامل، برش پلاک و متن پلاک است و با تصویر ورود قبلی تفاوت دارد. تصاویر بدون کشیدگی نمایش داده می‌شوند. بزرگ‌نمایی عکس در `AppPopup` و تصویر زنده با Fullscreen مرورگر انجام می‌شود؛ اتصال و تشخیص دوربین تغییری نکرده‌اند.
- یک جداکنندهٔ افقی با موس یا کلیدهای بالا/پایین، ارتفاع بخش بالا را تغییر می‌دهد. حداقل فضای عملیات و جدول‌ها محدود می‌شود. در موبایل صفحه عمودی است و جداکننده مخفی می‌شود؛ اسکرول جدول‌ها در قاب خودشان باقی می‌ماند.
- گریدهای ورود/خروج، انتخاب و اکشن‌ها، جستجوی مشترک، مرتب‌سازی و refresh با حفظ انتخاب و scroll برقرارند. رفتار هاور/فوکوس و سهم عرض ۶۰/۴۰ گرید فعال حفظ شده است. ردیف‌ها حدود ۳۰ پیکسل و تک‌خطی‌اند؛ متن کامل عضویت/پرداخت و تاریخ کامل زمان از Tooltip با هاور یا فوکوس در دسترس است. جزئیات در بخش «گرید تردد وب» [سند ۶](06-traffic-and-payment.md) ثبت شده است.
- منابع چینش: `trafficWorkspace.css`، `TrafficIdentitySummary.tsx`، `TrafficWorkspaceSplitter.tsx`، `TrafficDetectionPanel.tsx` و `TrafficControlGrids.tsx`. منابع منطق چهار دکمه در بخش ۳.۳.۱ آمده‌اند. endpoint جدید Backend یا تغییر payload ثبت/پرداخت ایجاد نشده؛ اطلاعات نوع درب و مجوز موجود سوابق در تصمیم دکمه‌ها مصرف می‌شوند.

**وضعیت تنظیمات دوربین در وب:** در `TrafficCameraPanels.tsx` پیام «قالب سرویس تشخیص پلاک دوربین معتبر نیست.» داخل بدنهٔ باکس نمایش داده نمی‌شود؛ آیکن هشدار با رنگ معنایی `warning` کنار دکمهٔ بزرگ‌نمایی، متن را با Tooltip در هاور یا فوکوس کیبورد نشان می‌دهد. خود آیکن نام دسترس‌پذیر دارد. خطاهای دریافت دوربین و قطع ارتباط سرویس همچنان در جایگاه قبلی نمایش داده می‌شوند.

|---|---|

| اجزای پلاک | تکمیل دو رقم اول و سه رقم میانی به بخش بعد می‌رود؛ انتخاب/Enter حرف به سه رقم میانی می‌رود. Backspace در بخش خالی، فوکوس را به بخش قبلی برمی‌گرداند. Enter در کد منطقه فقط برای پلاک معتبر تکمیل و شناسایی را اجرا می‌کند؛ موتور نیز در بخش دوم همین رفتار را دارد. |
| Enter کارت/عضویت | همان مسیر استعلام موجود را با مقدار جاری اجرا می‌کند. ثبت ورود یا خروج فقط با فعال‌کردن دکمهٔ عملیات انجام می‌شود. |
| روش کارت و پلاک، مقدار ۳ | برای منبع کارت یا پلاک، اگر کارت خالی باشد فوکوس به کارت و اگر پلاک ناقص باشد به اولین بخش پلاک می‌رود؛ پیش از تکمیل هر دو، استعلام اجرا نمی‌شود. شناسایی مستقیم با کد عضویت مانند handler ویندوز از این شرط مستقل است. دریافت پلاک دوربین نیز این پیش‌نیاز را رعایت می‌کند. |
| شناسایی موفق | فوکوس پس از پایان وضعیت انتظار به اولین دکمهٔ فعال با اولویت خروج، ورود، جستجو می‌رود. اگر هیچ‌کدام مجاز نباشند، لغو مقصد جایگزین است. |
| نیاز عضو به انتخاب خودرو | فوکوس ابتدا به انتخاب‌گر خودروی عضو می‌رود؛ پس از انتخاب، به عملیات مناسب منتقل می‌شود. خطای شناسایی، ورودی و مقدار کاربر را حفظ و فوکوس را به منبع استعلام برمی‌گرداند. |
| لغو و پایان موفق عملیات | فوکوس به اولین بخش پلاک برمی‌گردد. در خروج، ابتدا صورتحساب فوکوس را مدیریت می‌کند و پس از بسته‌شدن، فوکوس به پلاک می‌رسد. |

کارت مشخصات در هر دو حالت خودکار و دستی با `Popper` و بدون backdrop، قفل اسکرول یا گرفتن/حبس فوکوس نمایش داده می‌شود؛ بازکردن کارت به‌تنهایی فوکوس را تغییر نمی‌دهد و ورود اطلاعات و عملیات زمینه قابل استفاده می‌مانند. Escape و کلیک بیرون آن را می‌بندند. فقط اگر کاربر خودش فوکوس را وارد کارت کرده باشد، پس از بستن از داخل کارت فوکوس در حالت خودکار به انتخاب خودرو/عملیات و در حالت دستی به دکمهٔ «مشخصات» برمی‌گردد؛ بستن هنگام کار روی زمینه، فوکوس آن را جابه‌جا نمی‌کند. کلیک دوبارهٔ «مشخصات» وقتی کارت از قبل خودکار باز است، backdrop یا قفل فوکوس ایجاد نمی‌کند. موقعیت کارت در هر دو محور به viewport محدود می‌شود. ظاهر، انیمیشن و شرط بازشدن خودکار کارت حفظ شده‌اند. تست‌های مرورگر در عرض‌های ۱۴۴۰ و ۳۹۰ پیکسل، حفظ فوکوس، نبود backdrop/قفل اسکرول و کار با کنترل‌های زمینه را پوشش می‌دهند.

منابع: `useTrafficKeyboardNavigation.ts` برای انتقال فوکوس پس از آماده‌شدن کنترل‌ها، `TrafficRecordsWorkspace.tsx` برای منبع استعلام و نمایش نوع درب، `IranianPlateInput.tsx` برای حرکت میان اجزای پلاک و `TrafficIdentitySummary.tsx` برای کارت مشخصات. هیچ endpoint یا payload ثبت/پرداخت تغییر نکرده است. پوشش آزمون: ماتریس چهار نوع درب و ورود باز، الزام کارت و پلاک، Shift+Tab، انتخاب خودرو، کارت مشخصات بدون گرفتن فوکوس، و ثبت با Enter روی دکمه در تست‌های موجود مرورگر؛ اعتبار قرارداد درب و Enter/Backspace پلاک در تست‌های واحد بررسی می‌شوند.

### ۳.۶.۳ پاپاپ هزینهٔ وب

**تصمیم محصول/رفتار فعلی وب:** `TrafficPaymentPopup.tsx` با پوستهٔ مشترک `AppPopup` و سیاست متمرکز `trafficPaymentPolicy.ts` نمایش داده می‌شود. طبق تصحیح صریح کاربر، پاپاپ پس از خروج برای عضو و غیرعضو باز می‌شود؛ قواعد زمان زیر بر شرط عدم نمایش غیرعضو و زمان‌های استخراج‌شدهٔ قبلی تقدم دارند. Backend تغییر نکرده است.

- خروج ابتدا با `DoSave=true` ثبت و Grid تازه می‌شود؛ مبلغ از صورتحساب موفق API دریافت می‌شود و برای عضو و غیرعضو پاپاپ باز می‌شود. برای تشخیص عضو در زمان‌بندی کوتاه، `MemberCode` غیرخالی یا `MemberId` مثبت لازم است؛ شمارهٔ کارت به‌تنهایی عضویت نیست، چون غیرعضو نیز می‌تواند کارت داشته باشد.
- بعد از ثبت خروج: غیرعضو ۲۰ ثانیه؛ عضو با `CommonCost=0` پنج ثانیه؛ عضو با مبلغ غیرصفر ۲۰ ثانیه. شمارنده دقیقاً با رسیدن به صفر بسته می‌شود، نه یک تیک بعد. سه تنظیم اضافه‌شدهٔ قبلی (`trafficPaymentHideNonMembers`، `trafficPaymentTimeoutSeconds` و `trafficExitMode`) از تنظیمات وب حذف شده‌اند؛ مقادیر قدیمیِ احتمالی در فایل تنظیمات یا پاسخ API این قواعد را عوض نمی‌کنند.
- مبنای پرداخت `CommonCost` است. صفر: modeless بدون مسدودکردن شناسایی و کیبورد فرم؛ غیرصفر: modal. مبلغ مفقود/نامعتبر خطای صورتحساب می‌دهد و صفر فرض نمی‌شود. برای صفر، عمل اصلی «تأیید» فعال است و فقط پنجره را می‌بندد؛ هیچ درخواست `PayDump` نمی‌فرستد. برای مبلغ مثبت، «تأیید و پرداخت» با شناسهٔ معتبر فعال است.
- ورود ماوس، کلیک/لمس یا تعامل کیبورد شمارش را برای همان پنجره دائماً متوقف می‌کند؛ خروج ماوس آن را از سر نمی‌گیرد. پس از تعامل، پنجره تا تصمیم صریح کاربر یا تکمیل پرداخت باز می‌ماند. autofocus اولیهٔ پنجره تعامل محسوب نمی‌شود. بسته‌شدن خودکار هیچ درخواست پرداختی ایجاد نمی‌کند.
- پرداخت صریح از Grid فقط برای خروج معتبر با `PayType=0` یا `9` باز می‌شود؛ مبلغ مثبت در این مسیر همچنان بدون تایمر و صفر با شمارندهٔ ۵ است. درخواست دوم، پنجرهٔ فعال را focus می‌کند؛ صورتحساب و context درب snapshot مستقل‌اند و با لغو، refresh یا شناسایی خودروی بعدی تغییر نمی‌کنند. بسته‌شدن پنجرهٔ صفر هنگام تایپ، فوکوس زمینه را نمی‌گیرد.
- ترتیب داخلی برگرفته از `ExitBillDto.ToString()` و `PayForm.Designer.cs`: تاریخ/زمان ورود و خروج؛ مجموع حضور شامل مدت واقعی و مبلغ کل؛ سهم عضویت فقط با `MemberDuration>0`؛ دریافتی شامل مدت گرد شده، مالیات و مبلغ فقط با `CommonDuration>0`؛ تعرفه در انتها؛ سپس مبلغ درشت `CommonCost`. footer یک ردیف ثابت با ترتیب چپ به راست تأیید و پرداخت، خروج و POS مشروط است. محتوا در ارتفاع محدود اسکرول می‌شود؛ عملیات پایین در دسترس می‌ماند. QR ساختگی نمایش داده نمی‌شود.
- در پرداخت نقدی، تا پاسخ API دکمه‌ها و بستن قفل می‌شوند و تایمر متوقف می‌شود. رسید خالی یا خطای کسب‌وکار موفقیت محسوب نمی‌شود؛ صورتحساب باز می‌ماند. بستن پنجرهٔ مبلغ مثبت یا پایان تایمر به معنی تسویه نیست.

**کمبود قرارداد تجهیزات:** وجود POS فعال از `PcPos.Disabled` و وجود LCD از `HaveLcdPrice` در پاسخ موجود درب خوانده می‌شود؛ جزئیات اتصال در state نگهداری نمی‌شوند. دکمه‌های مربوط مطابق شرط وجود دستگاه نمایش داده می‌شوند اما تا فراهم‌شدن قرارداد عملیاتی وب غیرفعال‌اند و وضعیت عدم دسترسی دارند. LCD تنها برای مبلغ مثبت ظاهر می‌شود. API شروع تراکنش POS، دریافت نتیجهٔ معتبر دستگاه، نمایش مبلغ، چاپ رسید و تکمیل فرمان راهبند در دامنهٔ این تغییر موجود نیست؛ `PayDump` با نوع POS بدون تراکنش واقعی فراخوانی نمی‌شود. تکمیل این مسیر نیازمند Backend/Windows Service است.

**اعتبارسنجی:** تست سیاست مبلغ/عضو، مرز دقیق ۵ و ۲۰ ثانیه، تأیید بدون پرداخت، رسید پرداخت و قاب مشترک؛ تست مرورگر برای نمایش غیرعضو حتی با تنظیم قدیمی عدم نمایش، صفر بدون قفل فرم، حفظ snapshot و یک پنجره، لغو تایمر با ماوس/لمس/کیبورد، تایمر مثبت بدون تسویه، پرداخت Grid، خطای پرداخت/رسید خالی و چیدمان در صفحهٔ باریک.

5. وجود ورود قبلی کنترل می‌شود. **تصمیم محصول برای نسخه وب:** اگر ورود پیدا نشود، workflow خروج متوقف و `ManageTrafficRecordForm`/صفحه مدیریت ورود و خروج برای تعیین ورود توسط اپراتور باز می‌شود؛ UI ورود ساختگی ایجاد نمی‌کند. مجوز نهایی این اقدام را API تعیین می‌کند.
6. مدل خروج با `ExitDoorId`، شناسه تردد، عضو، خودرو، تعرفه، تصویر و کاربر ساخته می‌شود.
7. `TrafficApi.DoExitDump` فراخوانی می‌شود.
8. `ExitBillDto` دریافت می‌شود.
9. در صورت نیاز `PayForm` باز می‌شود.
10. پس از پرداخت یا صفر بودن مبلغ، چاپ فیش و فرمان راهبند اجرا می‌شود.
11. state فرم پاک می‌شود.

## ۸. قوانین کنترلی

### عضویت

- عضویت مسدود اجازه ادامه‌ی عادی ندارد.
- کارت و کد عضو به اطلاعات عضو و خودرو نگاشت می‌شوند.
- برای عضو چندخودرویی، انتخاب خودرو الزامی است.
- اعتبار جاری عضو از `TrafficApi.GetMemberCurrentCreditInfo` دریافت می‌شود.

### فهرست‌های کنترلی

- `Black`: عملیات متناظر متوقف و هشدار نمایش داده می‌شود.
- `Stealing`: بسته به نوع عملیات و درب، محدودیت اعمال می‌شود.
- `Observation`: هشدار نمایش داده می‌شود و الزاماً عملیات متوقف نمی‌گردد.

### تردد تکراری

در صورت فعال‌بودن گزینه، Grid جاری بررسی می‌شود و اگر ورود یا خروج مشابه در بازه مشخص وجود داشته باشد، عملیات متوقف می‌شود.

## ۱۰. خطاها و وضعیت‌های فعلی

| وضعیت | رفتار فعلی |
|---|---|
| loading | غیرفعال‌شدن موقت دکمه اصلی و نمایش انتظار محدود |
| empty | پاک‌شدن اطلاعات خودرو و غیرفعال‌شدن پنل عملیات |
| عضو پیدا نشد | پیام خطا و توقف ادامه عملیات |

| عضویت مسدود | پیام «عضویت غیر فعال است» |
| پلاک نامعتبر | توقف validation و درخواست اصلاح |
| تردد تکراری | پیام خطا و لغو state جاری |
| ورود ثبت نشده | جلوگیری از خروج، مگر گزینه استثنا فعال باشد |
| پرداخت ناموفق | راهبند باز نمی‌شود |
| اتصال قطع | رنگ وضعیت دستگاه و پیام خطا |

### خطاهای فنی و رفتارهای پنهان فعلی

- بسیاری از exceptionها با `catch` خالی یا پیام عمومی پوشانده می‌شوند.
- دریافت ترددها با Thread جداگانه انجام می‌شود و خطای آن قرارداد قابل نمایش مستقلی ندارد.
- در `GetParkingDoorDevices` مسیرهای دریافت تجهیزات و برخی null-checkها شکننده‌اند و باید در Backend/Service بازطراحی شوند.
- بخشی از بازکردن راهبند مستقیماً از SQL به جدول `Equipments` یا `OpenGateRequest` متصل است.
- متد عمومی قدیمی `OpenGate(bool)` در ابتدای خود `return` دارد؛ بنابراین مسیر `DeviceManager.OpenGate` عملاً غیرفعال است و مسیرهای G4/Service/StPro جداگانه استفاده می‌شوند.
- فهرست جلوگیری از تکرار پلاک و کارت فقط روی کلاینت نگهداری می‌شود و مرجع قطعی جلوگیری از duplicate نیست.

## ۱۱. رفتارهایی که نباید مستقیماً به وب منتقل شوند

- اتصال TCP/IP به راهبند از Browser؛
- اتصال مستقیم Browser به کارت‌خوان، UHF، StPro یا G4؛
- اجرای Thread و `Thread.Sleep` برای کنترل workflow؛
- نگهداری state عملیاتی فقط در حافظه‌ی تب؛
- اعتماد به مقدار تعرفه یا مبلغ ارسالی از UI؛
- بازکردن راهبند صرفاً بر اساس موفقیت ظاهری UI؛
- ذخیره‌ی تنظیمات عملیاتی به‌صورت رشته‌ی comma-separated در مرورگر؛
- پنهان‌کردن خطا با `catch` خالی؛
- استفاده از اتصال مستقیم SQL برای فرمان راهبند از لایه UI.

### ۱۲.۲ مسئولیت Web UI

UI وب فقط باید این موارد را انجام دهد:

- نمایش state رسمی سرور؛
- دریافت ورودی پلاک، کارت، کد عضو و انتخاب تعرفه؛
- ارسال commandهای دامنه‌ای مانند «استعلام خودرو»، «ثبت ورود» و «ثبت خروج»؛
- نمایش نتیجه، خطا و پیشرفت عملیات؛
- نمایش وضعیت تجهیزات دریافت‌شده از Backend/Service؛
- مدیریت route، مجوز نمایشی و accessibility.

UI نباید مستقیماً به IP تجهیزات، SQL یا SDK دستگاه دسترسی داشته باشد.

### ۱۲.۳ مسئولیت Backend API

Backend باید مرجع اصلی این موارد باشد:

- اعتبارسنجی نشست و مجوز؛
- تعیین پارکینگ، درب و شیفت جاری؛
- تعیین تعرفه معتبر؛
- یافتن عضو، خودرو و تردد باز؛
- کنترل فهرست‌های کنترلی؛
- ثبت اتمیک ورود یا خروج؛
- محاسبه مبلغ و وضعیت پرداخت؛
- صدور فرمان عملیاتی برای Service؛
- ثبت audit برای ورود، خروج، پرداخت و بازشدن راهبند؛
- جلوگیری از duplicate command و replay؛
- تبدیل خطاهای Service به خطای قابل فهم برای UI.

### ۱۲.۴ مسئولیت Windows Device Service

سرویس ویندوزی باید در شبکه پارکینگ نصب شود و مسئول این موارد باشد:

- اتصال و احراز هویت با تجهیزات؛
- نگهداری connection pool و reconnect؛
- دریافت event کارت، UHF و رکورد دستگاه؛
- دریافت تصویر یا trigger دوربین؛
- نگهداری credential دوربین و ارتباط با camera/plate detector؛
- ارسال فرمان بازکردن راهبند؛
- تنظیم ساعت تجهیزات؛
- پایش heartbeat و health؛
- صف‌کردن فرمان‌ها در قطعی موقت Backend؛
- گزارش نتیجه‌ی واقعی فرمان، نه صرفاً ارسال درخواست؛
- دریافت پاسخ POS و تبدیل آن به نتیجه پرداخت؛
- جلوگیری از بازکردن تکراری راهبند؛
- ثبت log و correlation id.

### ۱۲.۵ مرز مسئولیت سرویس تجهیزات در نسخه وب

کد WinForms موجود ارتباط مستقیم با بخشی از تجهیزات را نشان می‌دهد، اما سورس سرویس واسط یا Backend در scope مستندات نیست. **تصمیم محصول:** Browser مستقیم به تجهیز وصل نمی‌شود؛ تیم Backend باید معماری Agent/Windows Service و قرارداد command/event را طراحی و تحویل دهد. UI فقط API و event تأییدشده را مصرف می‌کند.

## ۱۴. API ارتباط Backend با Windows Service

### مدل پیشنهادی: Service به Backend متصل شود

## ۱۵. realtime و همگام‌سازی UI وب

پس از ورود کاربر، UI باید به کانال محدود به `parkingId` و `doorId` متصل شود. eventهای قابل ارسال:

- `traffic.updated`
- `plate.detected`
- `card.detected`
- `device.status_changed`
- `gate.command_status_changed`
- `payment.updated`
- `session.revoked`

اگر اتصال realtime قطع شد:

1. UI وضعیت disconnected نمایش دهد.
2. عملیات حساس جدید تا دریافت context معتبر محدود شود.
3. از polling با backoff استفاده شود.
4. پس از اتصال مجدد، snapshot کامل context و ترددها دریافت شود.

تنظیمات محلی فرم ویندوزی در کلید `Enter&ExitType` و به‌صورت رشته‌ی comma-separated ذخیره می‌شوند؛ این روش نباید قرارداد ذخیره‌سازی نسخه وب باشد. در وب، تنظیمات باید با schema نسخه‌دار و scope مشخص کاربر/درب/پارکینگ ذخیره شوند.

## ۱۶. session، retry و cancellation در نسخه وب

- هر عملیات ورود، خروج، پرداخت و راهبند باید `operationId` و `idempotencyKey` داشته باشد.
- retry فقط برای خطای شبکه یا timeout مجاز است؛ ثبت دوباره‌ی تردد بدون idempotency ممنوع است.
- cancellation در UI فقط باید command در حال انتظار را لغو کند؛ اگر دستگاه فرمان را اجرا کرده باشد، لغو ظاهری نباید نتیجه را معکوس اعلام کند.
- خروج از صفحه نباید عملیات ثبت‌شده را متوقف یا ناموفق تلقی کند.
- انقضای session باید با پیام واضح و توقف عملیات جدید مدیریت شود.
- تغییر پارکینگ یا درب باید تمام subscriptionهای قبلی را ببندد.

## ۱۷. audit و امنیت

برای هر عملیات حساس باید ثبت شود:

- کاربر؛
- پارکینگ و درب؛
- دستگاه؛
- زمان درخواست و زمان اجرا؛
- شناسه تردد؛
- command id؛
- نتیجه واقعی دستگاه؛
- مبلغ و روش پرداخت؛
- دلیل استثنا مانند خروج بدون ورود؛
- IP یا شناسه سرویس؛
- correlation id.

تصویر پلاک و اطلاعات شخصی عضو باید با سطح دسترسی و retention policy کنترل شود. **تصمیم محصول:** تصویر زنده تا حد امکان از خود دوربین نمایش داده شود، در قطع ارتباط reconnect خودکار با backoff داشته باشد و UI فقط buffer محدود نگه دارد و هنگام خروج/تغییر درب آن را آزاد کند. retention، محل ذخیره‌سازی، حذف، کیفیت/حجم، reconnect و permissionها باید در تنظیمات schema‌دار پارکینگ/درب قابل کنترل و در Backend enforce شوند. credential دستگاه نباید به Browser یا JavaScript ارسال شود.

## ۱۸. موارد باز و نیازمند backend

| مورد | وضعیت |
|---|---|
| method رسمی endpointها | نیازمند بررسی Controller/API client |
| schema کامل DTOها | نیازمند بررسی backend |
| status code و کد خطا | نیازمند قرارداد رسمی |
| محاسبه مبلغ و rounding | تصمیم محصول: کاملاً در Backend محاسبه می‌شود؛ UI فقط ورودی‌های لازم را ارسال و نتیجه را نمایش می‌دهد |
| تراکنش اتمیک ثبت خروج/پرداخت/فرمان راهبند | نیازمند تصمیم معماری |
| رفتار قطعی خروج بدون ورود | تصمیم محصول ثبت شد: انتقال به مدیریت ورود/خروج برای تعیین ورود؛ authorization نهایی با API |
| رفتار چند درب و چند سرویس دستگاه | نیازمند طراحی topology |
| ذخیره موقت eventهای قطع شبکه | نیازمند تصمیم درباره offline mode |
| منبع تصویر پلاک‌خوان | نیازمند انتخاب SDK/service |
| مجوزهای رسمی عملیات | نیازمند رجیستری نام‌دار |
| قرارداد پرداخت POS | نیازمند بررسی `PcPosManager` و backend |
| قرارداد ثبت بار | نیازمند تکمیل API فرم بار |
