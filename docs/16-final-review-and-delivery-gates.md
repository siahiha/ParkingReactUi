# بازبینی نهایی مستندات UI React

**وضعیت:** آماده‌ی طراحی و توسعه UI با mock؛ اتصال واقعی هر قابلیت منوط به قرارداد تحویلی Backend است.  
**تصمیم دامنه:** UI React باید تا حد ممکن قابلیت‌های فعال برنامه Windows را با دسته‌بندی مشابه آن پوشش دهد، اما طراحی آن مطابق استانداردهای وب است و Backend در scope پیاده‌سازی UI نیست.

## ۱. نتیجه تطبیق با سورس حاضر

منبع تطبیق، فرم‌های موجود در `EosParkingProfessional/EosForms`، مسیرهای بازکردن فرم در `MainForm` و `DashboardForm` و call siteهای API است.

| گروه قابلیت | فرم‌های فعال یا قابل دسترسی از مسیر اصلی | وضعیت UI وب |
|---|---|---|
| شروع و ورود | `Splash`، `LoginForm`، `DashboardForm`، `MainForm` | باید پیاده‌سازی شود |
| کاربران و دسترسی | `UsersForm`، `AccessLevelForm`، `ParkingUserShiftForm` | باید پیاده‌سازی شود |
| ساختار پارکینگ | `ParkingForm`، `EquipmentForm`، `ParkingFloorForm`، `ParkingSectionForm`، `ParkingParkSpaceKindForm`، `ParkingDoorForm`، `ParkingTariffForm` | باید پیاده‌سازی شود |
| اعضا و کارت | `MemberKindForm`، `MemberForm`، `ParkingCardForm`، `ControlListForm` | باید پیاده‌سازی شود |
| تردد و پرداخت | `ManualTrafficControlForm`، `ManageTrafficRecordForm`، `PayForm`، `ExitPermissionForm`، `NewCargoForm`، `PlateDetectedList` | باید پیاده‌سازی شود؛ بخش تجهیزات وابسته به Backend است |
| مانیتورینگ و گزارش | `MonitoringForm`، `MonitoringAnprForm` و report filter panelها | باید پیاده‌سازی شود؛ realtime/report API وابسته به Backend است |
| import | `ImportDataConfigurationForm`، `ImportMembersForm` | باید پیاده‌سازی شود؛ اتصال ETS/Excel وابسته به Backend است |
| اطلاعات محصول | `AboutForm` | باید به یک صفحه/دیالوگ ساده وب تبدیل شود |

### مواردی که قابلیت فعالِ قابل بازسازی تلقی نمی‌شوند

| مورد | شاهد کد | تعیین تکلیف |
|---|---|---|
| `ManualTrafficControlFormNew` | فایل و Designer دارد، ولی از `MainForm` یا `DashboardForm` ساخته نمی‌شود | نسخه عملیاتی مبنا `ManualTrafficControlForm` است. فرم New تا وقتی مسیر دسترسی یا تفاوت محصولی آن تأیید نشود، قابلیت جداگانه وب نیست؛ کد آن فقط منبع مقایسه است. |
| `AnprHoliday` | فقط سازنده و handler خالی دارد | UI مستقلی برای آن ساخته نمی‌شود؛ رفتار قابل مشاهده‌ای برای بازسازی ندارد. |
| `simpleButton2` در Dashboard و کنترل‌های hidden/commented | handler یا مسیر فعال ندارند | به UI وب منتقل نمی‌شوند، مگر یک نیاز محصول برایشان ثبت شود. |

## ۲. تصمیم‌های تثبیت‌شده

| موضوع | تصمیم قطعی |
|---|---|
| Backend | UI React فقط مصرف‌کننده API است. APIهای لازم، OpenAPI و قابلیت‌های سروری باید از تیم Backend درخواست شوند. |
| تجهیزات | UI اتصال مستقیم به دوربین، راهبند، POS یا کارت‌خوان ندارد. Backend باید روش Agent/Windows Service، API command و realtime monitoring را تحویل دهد. |
| مبلغ | UI هیچ مبلغ، مالیات، rounding، اعتبار عضو یا نتیجه پرداخت را محاسبه/اصلاح نمی‌کند؛ پاسخ Backend authoritative است. |
| POS موفق / API نامشخص | UI استعلام یا ثبت مجدد خودکار نمی‌کند؛ هشدار شامل اطلاعات تردد/POS نشان می‌دهد و اپراتور پیگیری می‌کند. |
| خروج بدون ورود | UI خروج را متوقف و صفحه مدیریت ورود/خروج را باز می‌کند تا اپراتور ورود را تعیین کند. API مجوز نهایی را کنترل می‌کند. |
| حذف | `Id < 0` در payload یعنی حذف فیزیکی entity با شناسه قدرمطلق. soft delete/archive فقط استثنای مستند است. |
| اتصال شبکه | سامانه فقط آنلاین است؛ صف محلی، offline mode و همگام‌سازی بعدی وجود ندارد. |
| تصویر | تصویر تا حد امکان realtime از دوربین، reconnect با backoff و buffer محدود Browser دارد. retention، حجم، کیفیت، دسترسی، حذف و ذخیره‌سازی تنظیمات Backend-enforced هستند. |
| هم‌ارزی Windows | قابلیت فعال حذف نمی‌شود؛ اگر در Browser ممکن نیست، با API، Agent یا workflow اپراتور جایگزین می‌شود. UI شبیه WinForms طراحی نمی‌شود، ولی دسته‌بندی‌ها حفظ می‌شوند. |

## ۳. رفتارهای امن UI که بدون تصمیم محصول اضافی اعمال می‌شوند

1. route بدون session، پارکینگ یا درب معتبر باز نمی‌شود؛ UI به ورود/انتخاب context بازمی‌گردد و خطا را نمایش می‌دهد.
2. برای ایجاد، ویرایش و حذف، UI confirmation و وضعیت loading/error دارد؛ API مرجع نهایی مجوز، وابستگی و نتیجه عملیات است.
3. عملیات حساس (ورود، خروج، پرداخت، حذف، فرمان تجهیز) با دوبارکلیک یا refresh نباید از UI دوباره ارسال شوند. UI تا دریافت پاسخ، کنترل مربوط را قفل می‌کند؛ جلوگیری قطعی از تکرار نیز نیاز Backend است.
4. خطای شبکه، خطای کسب‌وکار، عدم مجوز و قطع تجهیز در UI جدا نمایش داده می‌شوند. در حالت آنلاینِ قطع‌شده، عملیات محلی ذخیره یا خودکار retry نمی‌شود.
5. گزارش‌ها در وب با جدول/KPI/نمودار و print مرورگر نمایش داده می‌شوند. فایل `.mrt` یا viewer ویندوزی مستقیماً به وب منتقل نمی‌شود؛ export رسمی فقط در صورت API/فایل تحویلی Backend فعال می‌شود.
6. قابلیت‌های چاپ فیش، POS و راهبند از مسیر command API/Agent انجام می‌شوند. UI فقط وضعیت درخواست و نتیجه واقعی را نمایش می‌دهد.

## ۴. قانون حداقل پوشش فرم‌های وب

هیچ فرم وبی نباید فقط بر اساس نام فرم، چند فیلد نمونه یا یک تصویر کلی از WinForms پیاده‌سازی شود. پیش از شروع پیاده‌سازی هر فرم، مستندات و سورس مرجع باید به یک ماتریس ردیابی کامل تبدیل شوند و همه‌ی موارد زیر برای هر فیلد ثبت شوند:

| مورد اجباری | حداقل اطلاعات قابل ثبت |
|---|---|
| فیلد و مدل | عنوان فارسی/انگلیسی، نام property، نوع داده، nullable بودن، مقدار پیش‌فرض و محدودیت طول/بازه |
| رفتار UI | visible/hidden، read-only/قابل ویرایش، وابستگی به checkbox یا فیلد دیگر، ترتیب و گروه‌بندی |
| اعتبارسنجی | اجباری بودن، فرمت، بازه، پیام خطا، نرمال‌سازی و رفتار مقدار خالی |
| workflow | مسیر ایجاد، ویرایش، لغو، حذف، refresh بعد از موفقیت و رفتار unsaved changes |
| مجوز | مجوز مشاهده، ایجاد/ویرایش، حذف و رفتار UI در حالت unauthorized/forbidden |
| API | endpoint، method، request mapping، response، خطاهای شناخته‌شده و وضعیت قرارداد |
| وضعیت پوشش | `active`، `hidden-by-source`، `incomplete`، `needs-product-decision` یا `blocked-by-backend` |

### گیت تطبیق پیش از تحویل

- نسخه‌ی وب باید برای تمام فیلدها و رفتارهای دارای وضعیت `active` پوشش داشته باشد؛ حذف، ساده‌سازی یا نادیده‌گرفتن آن‌ها بدون ثبت تصمیم محصول مجاز نیست.
- موارد `hidden-by-source` فقط با ذکر دلیل در مستندات می‌توانند در UI وب نمایش داده نشوند؛ مخفی‌بودن در Designer به‌تنهایی نباید به حذف بی‌مستند قابلیت تعبیر شود.
- موارد `incomplete` و `needs-product-decision` باید به‌صورت صریح در UI و API تعیین تکلیف شوند؛ توسعه‌دهنده نباید برای آن‌ها حدس بزند.
- هر فرم قبل از تحویل باید یک جدول «منبع → وب» داشته باشد که برای هر property، control، validation و action، محل پیاده‌سازی وب را نشان دهد.
- تست پذیرش فرم باید حداقل شامل ایجاد، بارگذاری ویرایش، ذخیره، لغو، خطای validation، خطای API، مجوز، refresh و مقایسه‌ی payload باشد.
- اگر ماتریس ردیابی یا قرارداد API کامل نیست، وضعیت فرم `incomplete` است و فرم نباید به‌عنوان «تکمیل‌شده» تحویل شود؛ می‌توان فقط با برچسب واضح `mock/prototype` آن را نمایش داد.

این قانون برای `ParkingForm` نیز لازم‌الاجرا است؛ بنابراین فیلدهای شیفت‌ها، حداقل ساعت تعرفه شبانه‌روزی، حداقل دریافتی ورود نامشخص، ثبت فیش کنترلی و تنظیمات گرد کردن، تا زمان تعیین تکلیف مستند، جزو موارد حذف‌شده‌ی مجاز محسوب نمی‌شوند.

## ۵. گیت‌های تحویل Backend؛ ابهام‌های باقی‌مانده اکنون مسئول مشخص دارند

موارد زیر دیگر ابهام محصولی برای UI نیستند؛ هر کدام یک خروجی لازم از Backend پیش از اتصال production است.

| گیت | خروجی لازم از Backend | اثر تا زمان تحویل |
|---|---|---|
| API contract | OpenAPI نسخه‌دار، request/response، enum، status code و error schema | UI با mock کار می‌کند |
| Authorization | permissionهای نام‌دار، scope پارکینگ/درب، پاسخ 401/403 | route/action guard موقت است |
| تردد و پرداخت | قرارداد Create/Exit/Pay، idempotency، status عملیات و audit | اتصال واقعی عملیات حساس ممکن نیست |
| ورود دستی | API ایجاد/اصلاح ورود و کد عدم مجوز | flow خروج بدون ورود با mock باقی می‌ماند |
| تجهیزات | topology Agent/Service، command/event contract، acknowledgement و health | کنترل/monitor واقعی تجهیزات ممکن نیست |
| تصاویر | stream امن، reconnect state، settings و permission/retention contract | UI با تصویر نمونه/mock کار می‌کند |
| گزارش و export | schema فیلتر، داده گزارش و export/print contract | فقط نمایش mock ممکن است |
| ETS/import | schema منبع، upload/validation و result per row | wizard UI با mock قابل ساخت است |

جزئیات هر گیت در [درخواست‌های Backend](14-web-backend-requests.md) آمده است. پس از تحویل هر قرارداد، باید همان capability از mock به integration test ارتقا یابد.

## ۶. یافته‌های سورس که نباید بازتولید شوند

- retry پرداخت بدون شناسه یکتا و ارسال دوباره `SaveAll` کارت در یک مسیر وجود دارد؛ UI جدید آن‌ها را تکرار نمی‌کند.
- `Application.DoEvents`، `Thread.Sleep`، `Task.Wait`، global mutable state و `catch`های خاموش در Windows دیده می‌شوند؛ در React با state صریح، cancellation، error state و cleanup جایگزین می‌شوند.
- credential پایگاه‌داده و تجهیزات یا اتصال مستقیم دستگاه در Browser قرار نمی‌گیرد.
- کنترل client-side مجوز به‌تنهایی اعتبار امنیتی ندارد؛ API باید آن را enforce کند.

## ۷. نتیجه نهایی

با تصمیم‌های ثبت‌شده، ابهام‌های محصولی اصلی برای طراحی UI بسته شده‌اند. مانده‌ها همگی قراردادها یا پیاده‌سازی‌های لازم از تیم Backend هستند و در گیت‌های تحویل بالا تعیین مسئولیت شده‌اند. بنابراین توسعه UI React می‌تواند با mock و دسته‌بندی فرم‌های Windows آغاز شود؛ اتصال production هر بخش فقط پس از دریافت قرارداد همان گیت مجاز است.
