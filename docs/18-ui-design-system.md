# قوانین طراحی ظاهری UI React

**وضعیت:** استاندارد لازم‌الاجرا برای تمام صفحه‌ها و componentهای UI.  
**هدف:** یک رابط دو‌زبانه، راست‌به‌چپ/چپ‌به‌راست، قابل دسترس، سبک و یکدست که از ظاهر WinForms کپی نمی‌کند اما دسته‌بندی‌های محصول را حفظ می‌کند.

## ۱. اصول پایه

1. ابتدا از componentهای استاندارد MUI استفاده شود. ساخت component اختصاصی فقط وقتی مجاز است که MUI نیاز واقعی محصول را پوشش ندهد.
2. ابتدا از `@mui/icons-material` استفاده شود. SVG، تصویر یا icon library دیگر فقط برای لوگوی محصول یا آیکونی که معادل مناسب MUI ندارد مجاز است.
3. رنگ، فاصله، فونت، radius و shadow فقط از theme/token خوانده شوند؛ مقدار پراکنده در componentها ممنوع است.
4. ظاهر باید آرام، عملیاتی و خوانا باشد: رنگ‌های تزئینی زیاد، gradient، animation غیرضروری و cardهای پرتعداد استفاده نشود.
5. هر صفحه باید در light و dark mode، فارسی و انگلیسی، desktop و mobile بررسی شود.

## ۲. Theme واحد

یک `ThemeProvider` در ریشه برنامه قرار می‌گیرد و همه صفحه‌ها از آن استفاده می‌کنند. theme شامل `colorSchemes` برای `light` و `dark` و CSS variables است.

### حالت رنگ

- سه انتخاب به کاربر ارائه شود: `system`، `light` و `dark`.
- انتخاب پیش‌فرض `system` است؛ انتخاب کاربر فقط به‌عنوان preference غیرحساس ذخیره می‌شود.
- تغییر theme نباید رنگ‌های دستی یا flicker ایجاد کند.
- Dark mode از مشکی مطلق استفاده نمی‌کند؛ background، surface و border جدا اما کم‌کنتراست‌اند.

### رنگ‌های معنایی

فقط این نقش‌ها در UI استفاده شوند؛ هیچ صفحه‌ای رنگ hex اختصاصی تعیین نکند.

| نقش | کاربرد |
|---|---|
| `primary` | عمل اصلی صفحه، لینک و انتخاب فعال |
| `secondary` | عمل فرعی محدود |
| `success` | عملیات موفق، اتصال سالم، پرداخت تأییدشده |
| `warning` | نیاز به توجه اپراتور، وضعیت stale یا نامشخص |
| `error` | خطا، عدم مجوز، حذف و وضعیت خطر |
| `info` | اطلاع‌رسانی خنثی |
| `background.default` | پس‌زمینه صفحه |
| `background.paper` | card، dialog، table و پنل |
| `text.primary/secondary` | متن اصلی و کم‌اهمیت |

رنگ هر وضعیت باید همراه متن یا icon باشد؛ رنگ به‌تنهایی نباید حامل معنا باشد.

## ۳. تایپوگرافی و دو‌زبانه‌بودن

- فونت فارسی: یک فایل محلی WOFF2 از **Vazirmatn** یا فونت تأییدشده برند؛ font stack باید fallback سیستم داشته باشد.
- فونت انگلیسی: system font یا Inter؛ بارگیری فونت اضافی فقط در صورت نیاز واقعی انجام شود.
- مقیاس متن: `12` برای label کم‌اهمیت، `14` متن و فرم، `16` عنوان بخش، `20` عنوان صفحه و `24` عنوان‌های محدود dashboard.
- line-height متن فارسی حداقل `1.7` باشد.
- همه متن‌ها از فایل‌های ترجمه خوانده شوند؛ متن hard-code داخل component ممنوع است.
- زبان فارسی `dir="rtl"` و انگلیسی `dir="ltr"` دارد. Dialog، Menu، Popover و Portal نیز باید direction صحیح داشته باشند.
- شماره کارت، پلاک، مبلغ، تاریخ ISO، کد خطا، شماره رسید و شناسه‌ها باید با `dir="ltr"` و رقم لاتین نمایش داده شوند، حتی در UI فارسی.
- تاریخ نمایشی فارسی با تقویم جلالی و تاریخ API با ISO مشخص و تبدیل‌شده مدیریت شود؛ تبدیل تاریخ داخل component تکرار نشود.

## ۴. Layout و responsive behavior

- Desktop: sidebar ثابت یا collapsible، header کم‌ارتفاع و محتوای صفحه با max-width مناسب.
- Tablet/Mobile: sidebar به Drawer تبدیل شود؛ عملیات اصلی قابل دسترسی بماند.
- صفحه‌ها شامل `PageHeader`، عنوان، breadcrumb در صورت نیاز، action اصلی و content هستند.
- فرم‌های کوچک در Dialog و فرم‌های بزرگ مانند عضو، تعرفه و تردد در صفحه مستقل با section/tab طراحی شوند.
- جدول‌های پرتراکم در desktop نمایش کامل دارند؛ در mobile فقط ستون‌های کلیدی نمایش داده و جزئیات در Drawer/Dialog باز می‌شود.
- breakpointها فقط از MUI theme استفاده کنند؛ media queryهای پراکنده ساخته نشوند.

## ۵. الگوی componentهای مشترک

این‌ها wrapperهای کوچک روی MUI هستند، نه یک design system دوم:

| wrapper | کاربرد |
|---|---|
| `AppLayout` | header، navigation، container و sidebar/drawer |
| `PageHeader` | عنوان، breadcrumb و action اصلی |
| `WorkspaceToolbar` | نوار action مشترک بالای کارت، فهرست یا جدول |
| `AppButton` | variant و loading state یکسان برای Button MUI |
| `ConfirmDialog` | تأیید حذف یا عملیات حساس |
| `CrudDialog` | پوسته‌ی reusable برای فرم‌های ایجاد و ویرایش با دکمه‌های لغو و تأیید |
| `AppGroupBox` | گروه‌بندی معنایی فرم با `fieldset/legend` و Caption روی خط Border |
| `AppDataGrid` | پوسته‌ی مشترک Grid/Table با تراکم، مرزها، انتخاب ردیف، locale و RTL/LTR یکسان |
| `AppRecordCard` | پوسته‌ی مشترک کارت رکورد با محتوای خلاصه و ناحیه‌ی action استاندارد |
| `AppFormField` | اتصال یکدست MUI field به React Hook Form |
| `StatusChip` | رنگ و icon معنایی وضعیت‌ها |
| `LoadingState`، `EmptyState`، `ErrorState` | stateهای ثابت صفحه و جدول |
| `PermissionGuard` | پنهان/غیرفعال‌کردن UX بر اساس مجوز UI |

اگر یک wrapper تنها در یک صفحه استفاده می‌شود، ساخته نشود؛ همان component MUI با `sx` محلی استفاده شود.

## ۶. فرم، جدول، dialog و icon

### فرم‌ها

- MUI `TextField`، `Select`، `Autocomplete`، `Checkbox`، `RadioGroup` و `DatePicker` به‌عنوان کنترل پیش‌فرض استفاده شوند.
- در فرم‌های بزرگ و چندمرحله‌ای، React Hook Form و Zod مسئول state و validation باشند؛ فرم‌های فعلی Login و Home که سبک و محدود هستند از state محلی React استفاده می‌کنند و باید همین قرارداد اعتبارسنجی و نمایش خطا را رعایت کنند.
- خطای هر فیلد زیر همان فیلد، و خطای عمومی API در بالای فرم نمایش داده شود.
- دکمه Primary فقط یک مورد است؛ دکمه Cancel/Back همیشه قابل تشخیص و از عمل مخرب جداست.

#### استاندارد اجباری فیلدهای ورودی

TextField نام کاربری در صفحه Login مرجع بصری تمام فیلدهای ورودی برنامه است. هر کنترل ورودی جدید، از جمله `TextField`، `Select`، `Autocomplete` و ورودی `DatePicker`، باید از overrideهای مشترک Theme/CSS استفاده کند و نباید برای یک صفحه استایل مستقل و متناقض بسازد.

قرارداد فعلی:

| بخش | استاندارد |
|---|---|
| component پایه | MUI `TextField`، `Select`، `Autocomplete` و ورودی `DatePicker` با `variant="outlined"`، `size="small"` و `fullWidth` پیش‌فرض |
| ارتفاع فیلد | حدود `34px` |
| متن عنوان داخل فیلد خالی | کوچک و خوانا، `0.72rem` با وزن `600` |
| عنوان شناور بالای Border | جدا از متن داخل فیلد و بزرگ‌تر، `0.74rem` پس از scale داخلی MUI |
| placeholder/watermark | `0.72rem` با opacity حدود `0.72` |
| متن راهنما/خطا زیر فیلد | `0.68rem`، line-height `1.45` و فاصله‌ی کم از فیلد |
| سطح عادی | پس‌زمینه‌ی `#fbfcfd` |
| حالت Focus | پس‌زمینه‌ی سفید و outline داخلی ظریف با سایه‌ی `rgba(35,75,120,.10)` |
| RTL | عنوان در سمت راست، با فاصله‌ی `14px` از لبه و padding افقی `5px` |
| LTR | عنوان در سمت چپ، با فاصله‌ی `14px` از لبه و padding افقی `5px` |
| Dark mode | پس‌زمینه و عنوان متناسب با سطح تیره، بدون ازبین‌رفتن خوانایی |

قواعد اجرایی:

- این قرارداد در `EosParkingReactUi/src/theme.ts` و `EosParkingReactUi/src/styles.css` نگهداری می‌شود.
- تغییر اندازه، رنگ، فاصله، حالت Focus، محل label و محل icon/dropdown باید فقط در همین قرارداد انجام شود تا روی Login، Home، Dialog و تمام فرم‌های آینده اعمال شود.
- `Select` در حالت خالی باید label هم‌اندازه و هم‌وزن TextField داشته باشد؛ در RTL مقدار و label راست‌چین و آیکون بازشدن در سمت چپ است. حالت focus، background، border و label شناور نیز باید با TextField یکسان باشد.
- هر کنترل ورودی جدید باید قبل از استفاده با این قرارداد تطبیق داده شود؛ در صورت نبودن پشتیبانی مستقیم MUI، wrapper مشترک ساخته و به همین بخش افزوده شود.
- استفاده از `fontSize`، جایگذاری Label، icon یا Border اختصاصی در componentهای فرم ممنوع است مگر با ثبت دلیل طراحی و هماهنگی با همین قرارداد.
- `helperText` برای خطا یا راهنمای کوتاه استفاده شود؛ متن‌های تزئینی یا توضیح طولانی داخل فضای فیلد قرار نگیرند.
- برای فیلدهای فارسی و انگلیسی، جهت عنوان و جایگذاری آن باید از `dir` ریشه پیروی کند و با متن hard-code شده‌ی CSS جایگزین نشود.

#### استاندارد GroupBox و گروه‌بندی فرم

- هر گروه منطقی از فیلدهای فرم باید با یک GroupBox معنایی (`fieldset`/`legend` یا wrapper مشترک معادل) نمایش داده شود.
- Caption گروه باید روی خط بالایی Border قرار بگیرد و در RTL در سمت راست آن، و در LTR در سمت چپ آن قرار داشته باشد؛ Caption نباید داخل بدنه‌ی گروه یا به‌صورت یک عنوان جدا بالای Border شناور باشد.
- Border، فاصله داخلی، رنگ سطح و Typography Caption باید بین همه‌ی GroupBoxهای برنامه یکسان باشد و فقط از token/theme مشترک استفاده کند.
- GroupBox نباید برای تزئین استفاده شود؛ فقط مرز اطلاعاتی بین گروه‌های واقعی مانند مشخصات، تنظیمات و شیفت‌ها ایجاد کند.
- در حالت Dark و RTL/LTR، خوانایی Caption و پیوستگی آن با خط Border باید حفظ شود.

### جدول‌ها

- `MUI Data Grid Community` انتخاب پیش‌فرض است.
- pagination، sort و filter باید server-side باشند؛ داده کامل در Browser دریافت نشود.
- `AppDataGrid` باید loading، empty، error، locale فارسی/انگلیسی، انتخاب تک/چندردیفی و تراکم `comfortable/compact` یکسان داشته باشد.
- actionهای ردیف از icon MUI با tooltip و `aria-label` استفاده کنند؛ صرفاً icon بدون نام قابل دسترس ممنوع است.
- Grid باید تا حد ممکن در عرض container بدون اسکرول افقی نمایش داده شود: جدول `width: 100%` است، متن‌های طولانی باید wrap شوند و scroll افقی فقط fallback برای داده‌ای است که امکان شکستن یا کوتاه‌سازی آن وجود ندارد.
- ستون‌های Boolean/وضعیت مانند `IsActive`، `IsUsing` و `Has…` باید compact باشند؛ عرض آن‌ها نزدیک به عرض Caption و آیکون/مقدارشان است، متن و آیکون در مرکز قرار می‌گیرند و نباید فضای یک ستون متنی را اشغال کنند.
- هر ستون Boolean جدید باید semantic `compact` داشته باشد یا از naming استاندارد `Is…`/`Has…` استفاده کند تا `AppDataGrid` آن را خودکار فشرده کند. تعیین width بزرگ و ثابت برای ستون Boolean ممنوع است.
- جهت متن در سرستون‌ها و سلول‌های گرید باید از زبان رابط کاربری پیروی کند: در فارسی راست‌به‌چپ و راست‌چین (`RTL`) و در انگلیسی چپ‌به‌راست و چپ‌چین (`LTR`). این قانون باید به‌صورت یکسان در `AppDataGrid` اعمال شود و برای هر گرید جداگانه بازتعریف نشود.

### Dialog و عملیات مخرب

- حذف فیزیکی همیشه `ConfirmDialog` دارد و نام/شناسه رکورد و اثر حذف را نشان می‌دهد.
- هر Grid که action حذف دارد باید checkbox انتخاب ردیف و checkbox «انتخاب همه» در Header داشته باشد. حذف با یک یا چند ردیف انتخاب‌شده از Toolbar اجرا می‌شود؛ برای انتخاب چندردیفی، متن تأیید باید تعداد رکوردهای هدف را مشخص کند.
- ویرایش فقط با دقیقاً یک ردیف انتخاب‌شده فعال است؛ حذف با حداقل یک ردیف قابل‌حذف فعال می‌شود. ردیف‌های سیستمی یا غیرقابل‌حذف نباید قابل انتخاب برای حذف باشند.
- Dialog فقط برای عملیات کوتاه استفاده می‌شود؛ formهای طولانی، چندتب یا چندمرحله‌ای صفحه مستقل هستند.
- در حین mutation حساس، دکمه submit loading/disabled است و دوبارکلیک نباید درخواست دوم ایجاد کند.

### استاندارد فهرست‌های کارت‌محور و Popup فرم

- وقتی یک موجودیت باید کارت‌محور نمایش داده شود، صفحه فقط action اصلی ایجاد و کارت‌های رکوردها را نشان می‌دهد؛ فرم ایجاد یا ویرایش نباید به‌صورت پنل ثابت بالای فهرست قرار بگیرد.
- کارت باید اطلاعات خلاصه و قابل شناسایی رکورد را نمایش دهد و actionهای ویرایش و حذف را با icon، tooltip و `aria-label` ارائه کند.
- کارت‌ها باید با layout انعطاف‌پذیر و responsive چیده شوند؛ استفاده از جدول یا Data Grid برای همان فهرست مجاز نیست.
- ایجاد و ویرایش باید هر دو یک Popup مشترک داشته باشند. Popup مشترک در وب با `CrudDialog` پیاده می‌شود و نباید برای هر موجودیت modal اختصاصی با رفتار تکراری ساخته شود.
- Popup شامل عنوان، محتوای فرم، دکمه‌ی «لغو» و تنها یک دکمه‌ی Primary برای «تأیید/ذخیره» است. دکمه‌ی لغو mutation انجام نمی‌دهد.
- Popup باید برای محتوای فرم `children` یا معادل generic داشته باشد تا بتواند در فرم‌های مختلف استفاده شود؛ مدل داده و endpoint نباید داخل پوسته‌ی Popup hard-code شود.
- در زمان ارسال، دکمه‌ی تأیید disabled و در حالت loading باشد و بستن Popup نیز تا پایان mutation کنترل شود.
- پس از موفقیت، Popup بسته و collection کارت‌ها refresh می‌شود؛ پس از خطا، Popup باز می‌ماند و خطا را در همان context نشان می‌دهد.
- Popup باید در RTL/LTR، تم روشن/تیره، keyboard navigation و `aria`های استاندارد درست عمل کند.

### استاندارد Workspace Toolbar

- هر صفحه‌ای که کارت، فهرست یا جدول نمایش می‌دهد باید درست بالای محتوای اصلی یک `WorkspaceToolbar` داشته باشد.
- actionهای همان صفحه، مانند ایجاد، refresh، فیلتر، export و عملیات دسته‌ای، باید داخل Toolbar قرار بگیرند؛ action اصلی نباید جدا و شناور بالای کارت‌ها یا جدول تکرار شود.
- در RTL، Toolbar از سمت راست شروع می‌شود و در LTR از سمت چپ؛ پیاده‌سازی نباید برای فارسی و انگلیسی دو layout جدا داشته باشد.
- actionهای icon-only باید Tooltip و `aria-label` داشته باشند؛ actionهای اصلی می‌توانند icon و متن فشرده داشته باشند.
- Toolbar باید کم‌ارتفاع، یک‌خطی، دارای border و background ظریف و هم‌ترازشده با محتوای workspace باشد.
- در Gridها، تمام actionهای CRUD ردیف انتخاب‌شده باید در Header/Toolbar بالای Grid قرار بگیرند؛ ستون جداگانه‌ی عملیات در ردیف‌ها مجاز نیست.
- ردیف هدف باید با انتخاب واضح مشخص شود و actionهای ویرایش/حذف بدون انتخاب ردیف غیرفعال باشند؛ حذف کاربر سیستمی یا رکورد غیرقابل حذف نیز باید غیرفعال بماند.
- انتخاب چندردیفی فقط برای عملیات گروهی مانند حذف مجاز است و نباید موجب فعال‌شدن ویرایش شود؛ رفتار checkboxهای ردیف و Header فقط از `AppDataGrid` مشترک تأمین می‌شود.
- actionهای Header مانند «جدید»، «ویرایش»، «حذف» و «به‌روزرسانی» باید بدون متن و فقط با آیکون نمایش داده شوند و حتماً Tooltip و `aria-label` ترجمه‌شده داشته باشند.
- این قانون برای همه‌ی فهرست‌های جدولی برنامه لازم‌الاجرا است؛ دکمه‌ی «جدید» نباید در یک فهرست به‌صورت متنی و در فهرست دیگر به‌صورت آیکونی نمایش داده شود.

### قرارداد نهایی Header مدیریت و جایگاه Refresh

برای صفحه‌های مدیریت سامانه که یک فهرست کارت‌محور یا جدول دارند، Header صفحه و عنوان workspace باید یک سطح یکپارچه باشند:

- عنوان صفحه و عنوان موجودیت در یک ردیف فشرده نمایش داده شوند؛ الگوی فارسی فعلی: `مدیریت پارکینگ‌ها - پارکینگ‌ها    ۱ رکورد`.
- توضیح طولانی مانند «مدیریت امکانات سطح سیستم و فهرست پارکینگ‌ها» در این Header نمایش داده نشود؛ این متن برای این سطح از UI لازم نیست.
- عنوان موجودیت، تعداد رکورد و action مربوط به refresh نباید در یک باکس داخلیِ جداگانه تکرار شوند.
- بین Header و محتوای workspace فاصله‌ی عمودی اضافی، margin افقی یا border تکراری مجاز نیست؛ فقط یک سطح و یک جداکننده‌ی ظریف استفاده شود.
- Refresh در صفحه‌های مدیریت جزو Header بالایی است، نه Toolbar پایین. در فارسی آیکون Refresh در سمت چپ Header قرار می‌گیرد؛ در LTR جای آن به‌صورت آینه‌ای در سمت راست قرار می‌گیرد.
- Refresh فقط به‌صورت icon-only نمایش داده شود و حتماً Tooltip و `aria-label` ترجمه‌شده داشته باشد؛ در زمان loading غیرفعال شود.
- Toolbar پایین Header فقط برای actionهای محتوایی مانند ایجاد، فیلتر، export و عملیات دسته‌ای است و نباید Refresh را تکرار کند.
- Toolbar پایین تمام عرض محتوای workspace را بدون margin افقی اضافه بگیرد، با background خود صفحه هماهنگ باشد و فقط border پایینی ظریف داشته باشد.
- در RTL/LTR، ترتیب متن Header و فاصله‌گذاری باید با CSS منطقی و یک layout مشترک پیاده شود؛ برای فارسی و انگلیسی component جدا ساخته نشود.

### Iconها

- پیش‌فرض `@mui/icons-material` است؛ نام icon باید با مفهوم عملیات هماهنگ باشد، مانند `Add`، `Edit`، `Delete`، `Refresh`، `Print`، `Search` و `Settings`.
- icon جای متن دکمه اصلی را نمی‌گیرد، مگر در actionهای شناخته‌شده‌ی جدول که tooltip و `aria-label` دارند.
- اندازه استاندارد icon در دکمه/جدول `20px` و در header `24px` است؛ اندازه‌های دیگر باید استثنای واضح باشند.

## ۷. وضعیت‌های عملیاتی

تمام صفحه‌ها و queryها باید این stateها را داشته باشند:

- `loading`: Skeleton برای content/table و Spinner فقط برای action کوتاه.
- `empty`: دلیل نداشتن داده و action مناسب، مانند «ایجاد عضو» یا «تغییر فیلتر».
- `error`: پیام قابل فهم، `traceId` در صورت وجود، و retry فقط برای GET غیرحساس.
- `unauthorized`: پیام عدم مجوز؛ UI تصمیم امنیتی Backend را دور نمی‌زند.
- `offline/disconnected`: وضعیت مشخص؛ چون برنامه فقط آنلاین است، عملیات حساس locally queue یا خودکار retry نمی‌شوند.
- `success`: toast کوتاه؛ نتیجه مهم پرداخت/تردد علاوه بر toast در همان صفحه ثبت و قابل مشاهده می‌ماند.

## ۸. کارایی و بارگذاری سبک

1. routeهای feature با `lazy()` و `Suspense` بارگذاری شوند؛ dashboard اولیه همه فرم‌ها را import نکند.
2. iconها با import نام‌دار از MUI وارد شوند؛ کل مجموعه icon یا کتابخانه دیگر import نشود.
3. فقط componentهای MUI مورد استفاده import شوند؛ از importهای تجمیعی غیرضروری پرهیز شود.
4. جدول‌ها pagination server-side دارند و تصویرها thumbnail/lazy-load هستند.
5. stream دوربین و object URL فقط در صفحه فعال وجود دارند و هنگام unmount/change context آزاد می‌شوند.
6. React Query cache زمان‌دار و محدود دارد؛ تصاویر بزرگ یا frameهای زنده در Query cache ذخیره نمی‌شوند.
7. animationها کوتاه و محدود هستند؛ برای کاربران `prefers-reduced-motion` کاهش می‌یابند.
8. هر dependency جدید باید دلیل ثبت‌شده داشته باشد و نباید قابلیت موجود MUI/React را تکرار کند.

## ۹. دسترس‌پذیری و کنترل کیفیت

- کنتراست متن و controlها باید حداقل در سطح قابل قبول WCAG AA باشد.
- همه فرم‌ها با keyboard قابل پیمایش هستند و focus ring حذف نمی‌شود.
- `aria-label` برای buttonهای icon-only و label واقعی برای inputها اجباری است.
- Light/dark، فارسی/انگلیسی و desktop/mobile بخشی از checklist هر Pull Request هستند.
- برای componentهای مشترک، Storybook یا صفحه داخلی preview تنها پس از نیاز واقعی تیم اضافه می‌شود؛ در شروع اجباری نیست.

## ۱۰. مراجع اجرایی

- theme، CSS variables و style override از [MUI Theming](https://mui.com/material-ui/customization/theming/) پیروی می‌کند.
- light/dark با `colorSchemes` MUI و preference کاربر پیاده می‌شود: [MUI Dark mode](https://mui.com/material-ui/customization/dark-mode/).
- RTL باید direction در HTML، theme و styling engine را پوشش دهد: [MUI RTL](https://mui.com/material-ui/customization/right-to-left/).
- ترجمه Data Grid با locale text کنترل می‌شود: [MUI Data Grid localization](https://mui.com/x/react-data-grid/localization/).

## ۱۱. قواعد تکمیلی مصوب برای سامانه پارکینگ

این بخش نسخه‌ی دامنه‌ای و لازم‌الاجرای قواعد عمومی فایل `web_application_design_rules.txt` است. در صورت تعارض، نیازمندی‌های عملیاتی و امنیتی سامانه پارکینگ بر قواعد زیبایی‌شناختی مقدم هستند.

### شخصیت محصول

UI باید یک نرم‌افزار عملیاتی دسکتاپ‌محور در مرورگر به نظر برسد؛ سریع، دقیق، متراکم اما خوانا، فنی و قابل اتکا. طراحی تبلیغاتی، SaaS عمومی، کارت‌های تزئینی و عناصر بدون کاربرد مجاز نیستند.

مفهوم بصری محصول: **Industrial Operations Control Room** با ترکیب Industrial، Utilitarian، Command Center و Swiss Minimal.

### دامنه‌ی اطلاعاتی

نمونه‌های عمومی مانند Employee، Department و Team در این پروژه با مفاهیم زیر جایگزین می‌شوند:

- پارکینگ، درب و شیفت
- تردد، ورود، خروج و پرداخت
- عضو، خودرو و کارت
- تعرفه و جای‌پارک
- تجهیز، دوربین، ANPR و راهبند
- کاربر، سطح دسترسی و audit
- گزارش و import

### رنگ مصوب

رنگ‌ها از theme و token خوانده می‌شوند و هر وضعیت علاوه بر رنگ باید متن یا icon داشته باشد:

| token | مقدار پایه | کاربرد |
|---|---|---|
| `background.default` | `#F3F5F7` | پس‌زمینه اصلی |
| `background.paper` | `#FFFFFF` | سطح و پنل |
| `divider` | `#D7DCE2` | مرز و جداکننده |
| `primary.main` | `#234B78` | عمل اصلی و انتخاب فعال |
| `text.primary` | `#18212B` | متن اصلی |
| `text.secondary` | `#687482` | متن کم‌اهمیت |
| `success.main` | `#2E7D32` | موفقیت و اتصال سالم |
| `warning.main` | `#A86600` | هشدار و وضعیت نامطمئن |
| `error.main` | `#C62828` | خطا، عدم مجوز و حذف |
| `info.main` | `#28658A` | اطلاع‌رسانی |

Gradient، neon، purple/blue gradient، glassmorphism و پس‌زمینه‌ی متحرک ممنوع است.

### تراکم، شکل و صفحه‌آرایی

- مقیاس فاصله‌ی اصلی: `4 / 8 / 12 / 16 / 24 / 32 / 48px`.
- radius پیش‌فرض componentها بین `0` تا `4px` است؛ radius بزرگ فقط برای استثنای مشخص مجاز است.
- border یک‌پیکسلی و shadow بسیار محدود استفاده شود.
- صفحه‌ها workspace هستند، نه مجموعه‌ای از cardها: Header، Context/Status، Toolbar، Workspace اصلی، Table/List و Status/Pagination.
- جدول، فهرست و ناحیه‌ی کار محتوای اصلی‌اند و نباید داخل چند card تزئینی پنهان شوند.
- Login یک استثنای محدود برای layout مرکزی است، اما همچنان باید تخت، کم‌سایه و بدون عناصر تزئینی باشد.

### قانون تراکم ظریف و سبک Windows-like

این قرارداد برای کل برنامه، فرم‌ها، Popupها، کارت‌ها، منوها و صفحه‌های آینده اجباری است. هدف، رابطی کم‌تراکم و کاربردی با حس اپلیکیشن ویندوزی است؛ نه رابطی تزئینی، درشت یا شبیه داشبورد بازاریابی.

- اندازه‌ی پایه‌ی متن‌های `body1` و `body2` به‌ترتیب حدود `0.82rem` و `0.76rem` و متن دکمه‌ها حدود `0.76rem` باشد؛ افزایش اندازه فقط با دلیل UX مشخص مجاز است.
- `TextField` و کنترل‌های فرم به‌صورت پیش‌فرض `small`، با ارتفاع حدود `34px`، padding فشرده و label کوچک استفاده شوند.
- label شناور TextField حدود `0.74rem` باشد؛ label درشت و فاصله‌گذاری بزرگ داخل Popup ممنوع است.
- دکمه‌های معمولی حدود `32px` ارتفاع، radius حدود `3px` و padding افقی محدود داشته باشند. actionهای icon-only حدود `30px` باشند.
- عنوان Dialog حدود `0.92rem`، padding عنوان و محتوا فشرده، و فاصله‌ی actionهای Dialog کم باشد.
- فاصله‌های داخل فرم و Popup معمولاً در بازه‌ی `8 تا 16px` انتخاب شوند؛ فاصله‌ی `24px` یا بیشتر فقط برای جداسازی sectionهای مستقل مجاز است.
- منوها، Toolbar و header باید از همین تراکم پیروی کنند؛ ارتفاع آیتم‌های منو معمولاً حدود `29 تا 34px` باشد.
- کارت‌های عملیاتی border یک‌پیکسلی، radius حدود `6 تا 10px` و shadow بسیار محدود داشته باشند. hover نباید کارت را به‌صورت نمایشی جابه‌جا یا بزرگ کند.
- اطلاعات ثانویه‌ی کارت با فونت کوچک‌تر و رنگ `text.secondary` نمایش داده شود؛ جزئیات پایین کارت در بلوک‌های فشرده و قابل اسکن قرار بگیرند.
- gradient، shadow سنگین، گوشه‌های خیلی گرد، animation تزئینی و typography بزرگ در workspace و Popup مجاز نیست.
- این مقادیر باید در `theme.ts` و قراردادهای مشترک `styles.css` نگهداری شوند؛ استایل جداگانه برای هر فرم یا Popup ممنوع است مگر با ثبت استثنا.

### عملیات حساس و Backend authoritative

Optimistic UI برای ورود و خروج خودرو، پرداخت، بازکردن راهبند، حذف، تغییر تعرفه، تغییر سطح دسترسی و import مجاز نیست. در این عملیات پاسخ Backend مرجع نهایی است و UI باید وضعیت loading، موفقیت، خطا، timeout و نامشخص را نمایش دهد.

### Permission و audit

هر action می‌تواند یکی از وضعیت‌های `visible`، `readOnly`، `editable`، `restricted` یا `hidden` را داشته باشد. مخفی‌کردن کنترل جایگزین authorization سمت Backend نیست. عملیات مهم باید با شناسه پیگیری، زمان، کاربر و نتیجه قابل trace باشد.

### قواعد خاص داده‌ی زنده

در مانیتورینگ و تردد زنده، وضعیت `LIVE`، زمان آخرین به‌روزرسانی، `stale`، `offline` و خطای اتصال باید جداگانه نمایش داده شوند. رویداد جدید فقط با تأکید کوتاه و کاربردی نمایش داده شود؛ animation تزئینی ممنوع است.

### معماری Home و مدیریت پارکینگ‌ها

- مفهوم مستقل «داشبورد» در نسخه وب وجود ندارد؛ `Home` صفحه‌ی اولیه‌ی مشترک پس از ورود است.
- تفاوت کاربران در این سطح فقط تعداد منوهای قابل مشاهده و دسترسی آن‌هاست.
- مدیر سیستم منوی «مدیریت پارکینگ‌ها» را می‌بیند؛ کاربران معمولی و پارکبان‌ها این منو را نمی‌بینند.
- «مدیریت سامانه» یک منوی والد با زیرمنوهای پارکینگ‌ها، کاربران و دسترسی، سطوح دسترسی، گزارش‌های کلی و مجوز خروج است.
- اگر فهرست پارکینگ‌ها خالی نباشد، اولین پارکینگ به‌صورت پیش‌فرض انتخاب می‌شود و اطلاعات پارکینگ جاری در Toolbar بالای `Home` نمایش داده می‌شود.
- اطلاعات پارکینگ جاری نباید به‌صورت پنل تکراری داخل محتوای `Home` نمایش داده شود؛ مدیر سیستم باید همان‌جا در Toolbar امکان تغییر پارکینگ داشته باشد.
- مدیر سیستم باید امکان جابه‌جایی بین پارکینگ‌های مجاز را داشته باشد؛ انتخاب پارکینگ، context جاری برای ادامه‌ی عملیات است.
- اطلاعات و عملیات اختصاصی یک پارکینگ مانند ظرفیت، ورود، خروج و پرداخت در محیط همان پارکینگ قرار می‌گیرد، نه در منوی مدیریت سطح سیستم.

### منوی کاربر جاری

- در header، کنترل کاربر جاری باید به‌صورت کنترل آیکونی قابل تشخیص باشد: آیکون حساب و آیکون فلش بازشونده؛ نام کاربر در Tooltip نمایش داده می‌شود و نباید متن دائمی روی دکمه باشد.
- در فارسی ترتیب فیزیکی کنترل از چپ به راست «آیکون حساب، فلش» است؛ در انگلیسی ترتیب برعکس می‌شود.
- کلیک روی کنترل باید منوی بازشونده‌ی کاربر را نمایش دهد.
- تغییر حالت روز/شب یک کنترل آیکونی مستقل در Toolbar و کنار خانه/کاربر جاری است و با هر کلیک بین روشن و تیره جابه‌جا می‌شود؛ این کنترل داخل منوی کاربر قرار نمی‌گیرد.
- گزینه‌ی «خانه» باید به‌صورت یک گزینه‌ی مستقل، همراه با آیکون خانه و کنار کنترل کاربر جاری در header قرار گیرد؛ خانه نباید داخل منوی بازشونده‌ی کاربر یا نوار منوی کناری تکرار شود.
- این دو گزینه در header به‌صورت کنترل‌های آیکونی هم‌اندازه نمایش داده می‌شوند؛ متن آن‌ها داخل Tooltip و `aria-label` ارائه می‌شود.
- منوی بازشونده‌ی کاربر شامل تغییر رمز عبور، تنظیمات تم، تغییر زبان و خروج است.
- تغییر زبان از همین منو باید زبان و جهت کل محیط را تغییر دهد؛ گزینه نباید صرفاً نمایشی باشد.
- تنظیمات تم مسئول انتخاب رنگ‌بندی است، نه تغییر حالت روز/شب. برای هر حالت روشن و تیره چند پالت پیش‌فرض مانند آبی سازمانی، سبز عملیاتی و خاکستری صنعتی ارائه می‌شود و انتخاب هرکدام جداگانه ذخیره می‌گردد.
- تم باید در سطح ریشه‌ی برنامه مدیریت شود و روی Login، Home، header، menu، dialog و تمام صفحه‌های بعدی اثر بگذارد؛ ذخیره‌سازی preference در `localStorage` انجام می‌شود و هنگام شروع برنامه پیش از نمایش صفحه اعمال می‌گردد.
- تغییر رمز باید فرم شامل رمز فعلی، رمز جدید و تکرار رمز جدید با اعتبارسنجی تطابق داشته باشد؛ در نسخه فعلی درخواست از مسیر مشاهده‌شده‌ی `POST api/user/Save` با `UserPass` و `NewPass` رمزگذاری‌شده ارسال می‌شود و قرارداد نهایی Backend باید در OpenAPI تأیید شود.
- خروج باید token و context کاربر را پاک و به Login برگرداند.

## ۱۲. تصمیم‌های تثبیت‌شده‌ی نسخه وب

این بخش مرجع نهایی تصمیم‌های UI فعلی است و در صورت تعارض با نمونه‌ها یا برداشت‌های قدیمی‌تر همین سند، اولویت دارد.

### ساختار و مسیرها

- route اصلی پس از ورود `Home` است و مفهوم مستقل «Dashboard» در UI وب وجود ندارد.
- `Home` صفحه‌ی مشترک همه‌ی کاربران است و محتوای آن بر اساس پارکینگ جاری شکل می‌گیرد.
- تفاوت نقش‌ها در این سطح فقط تعداد منوهای قابل مشاهده و مجوزهای آن‌هاست.
- مدیر سیستم منوی والد «مدیریت پارکینگ‌ها» را دارد؛ کاربر عادی و پارکبان این منو را نمی‌بینند.
- زیرمنوهای مدیریت سامانه عبارت‌اند از: پارکینگ‌ها، کاربران و دسترسی، سطوح دسترسی، گزارش‌های کلی و مجوز خروج.
- اگر فهرست پارکینگ مجاز خالی نباشد، اولین آیتم به‌صورت پیش‌فرض انتخاب می‌شود.
- اطلاعات پارکینگ جاری فقط در Toolbar بالای صفحه نمایش داده می‌شود و نباید به‌صورت پنل تکراری در Home بیاید.
- مدیر سیستم باید بتواند پارکینگ جاری را از همان Toolbar تغییر دهد؛ این انتخاب context عملیات بعدی است.
- اطلاعات و workflowهای اختصاصی مانند ظرفیت، ورود، خروج و پرداخت در workspace پارکینگ جاری قرار می‌گیرند.

### Toolbar و منوی کاربر

- Toolbar شامل دکمه‌ی آیکونی Home، کنترل پارکینگ جاری، کنترل آیکونی کاربر و کنترل مستقل روز/شب است.
- Home کنار کنترل کاربر قرار دارد، با آیکون خانه نمایش داده می‌شود و داخل sidebar یا dropdown کاربر تکرار نمی‌شود.
- کنترل کاربر متن دائمی ندارد و از آیکون حساب + فلش تشکیل می‌شود؛ نام کاربر در Tooltip و `aria-label` ارائه می‌شود.
- در فارسی ترتیب فیزیکی کنترل کاربر «آیکون حساب، فلش» و در انگلیسی «فلش، آیکون حساب» است.
- در حالت عادی دکمه‌های آیکونی Toolbar بدون کادر دیده می‌شوند و فقط در hover کادر و پس‌زمینه‌ی ظریف می‌گیرند.
- dropdown کاربر شامل تغییر رمز عبور، تنظیمات رنگ تم، تغییر زبان و خروج است؛ Home و Toggle روز/شب داخل آن نیستند.

### روز/شب و رنگ‌بندی

- حالت روز/شب یک Toggle مستقل در Toolbar است؛ حالت روشن با آیکون ماه برای رفتن به شب و حالت تیره با آیکون خورشید برای رفتن به روز نمایش داده می‌شود.
- تنظیمات تم مسئول تعیین رنگ‌هاست، نه تعیین روز یا شب.
- برای هر حالت چند پالت آماده وجود دارد: آبی سازمانی، سبز عملیاتی و خاکستری صنعتی.
- پالت روشن و پالت تیره جداگانه انتخاب می‌شوند؛ انتخاب‌ها در `localStorage` ذخیره می‌شوند.
- وضعیت روز/شب نیز در `localStorage` ذخیره و هنگام شروع برنامه بازیابی می‌شود.
- تم باید از ریشه‌ی برنامه روی Login، Home، Toolbar، sidebar، menu، dialog و صفحه‌های بعدی اعمال شود.

### رفتارهای ماندگار و عملیاتی

- تغییر زبان از dropdown کاربر باید زبان، ترجمه‌ها و direction کل برنامه را تغییر دهد.
- Logout باید token، context کاربر و نشست ذخیره‌شده را پاک و کاربر را به Login برگرداند.
- پس از ورود موفق، token و context کاربر در `sessionStorage` نشست جاری ذخیره می‌شوند تا refresh باعث Logout نشود.
- ذخیره‌ی username برای پیشنهاد ورود بعدی از نشست احراز هویت جداست و رمز عبور هرگز در local/session storage ذخیره نمی‌شود.
- فرم تغییر رمز شامل رمز فعلی، رمز جدید و تکرار رمز جدید است، تطابق دو رمز جدید را اعتبارسنجی می‌کند و نتیجه‌ی ارسال را به کاربر نشان می‌دهد؛ مسیر فعلی `POST api/user/Save` از قرارداد مشاهده‌شده‌ی `UserApi.Save` استفاده می‌کند و نیازمند تأیید رسمی Backend است.
- TextField نام کاربری در Login مرجع واحد ظاهر فیلدها است؛ همه‌ی TextFieldهای Login، Home و فرم‌های آینده باید از override مشترک Theme/CSS برای عنوان شناور، فاصله‌ی عنوان از border، ارتفاع، پس‌زمینه و حالت focus استفاده کنند و استایل اختصاصی موازی نسازند.
- خروج باید عملیاتی و در دسترس باشد؛ گزینه‌های تغییر رمز و تنظیمات تم می‌توانند تا آماده‌شدن فرم مقصد به‌صورت نقطه ورود مشخص باقی بمانند.
