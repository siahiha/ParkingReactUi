# وضعیت پیاده‌سازی UI و سیاست جلوگیری از Regression

## وضعیت سند

این سند وضعیت واقعی تغییرات انجام‌شده در UI React تا این مرحله را ثبت می‌کند. هر تغییر بعدی باید علاوه بر اضافه‌کردن قابلیت جدید، رفتار و ظاهر قابلیت‌های قبلی را حفظ کند.

## محدوده فعلی پروژه

پروژه در مسیر `EosParkingReactUi` یک SPA مبتنی بر React و TypeScript است. در این مرحله، صفحه‌های زیر در UI وجود دارند:

- Login؛
- Home؛ جزئیات قرارداد آن فقط در [سند ۲۵](25-home.md) نگهداری می‌شود؛
- منوی همبرگری «پارکینگ‌ها» در بخش «مدیریت سامانه»؛
- منوهای تعاریف، عملیات، ارتباط با سیستم‌ها و گزارش‌ها؛ منوی گزارش‌ها شامل دسته‌های اعضا، تردد، مالی، سایر و گزارش‌های مدیریتی است؛
- تنظیمات theme، زبان و palette؛
- تغییر رمز عبور در UI.

برخی menu itemها هنوز placeholder هستند؛ بررسی تکمیل آن‌ها در این snapshot عمداً خارج از
دامنه است. موارد زیر فقط وضعیت قابلیت‌هایی را ثبت می‌کنند که در کد فعلی route یا workspace
واقعی دارند.

## قرارداد اجباری ترجمهٔ UI

این پروژه برای ترجمهٔ UI فقط از `i18next` و `react-i18next` استفاده می‌کند. resource هر
زبان باید در فایل مستقل خود در `src/locales/` قرار گیرد و از طریق instance مشترک در
`src/i18n/instance.ts` بارگذاری شود. componentها باید از `useTranslation()`/`t()` و کد
خارج از React از `i18n.t()` استفاده کنند.

الگوهای زیر مجاز نیستند و نباید در کد جدید یا refactor باقی‌مانده استفاده شوند:

- انتخاب متن با `language === 'fa' ? '...' : '...'` یا هر شرط زبان مشابه؛
- helperهایی مانند `text(fa, en)` یا سیستم resource/ترجمهٔ موازی؛
- متن نمایشی hard-code در JSX، hook، handler و مدل view؛
- fallback متنی inline برای مخفی‌کردن کلید مفقود یا ساخت کلید ترجمه در runtime.

شرط زبان فقط برای direction، formatter و منطق فنی مجاز است. route، API key، enum،
identifier، URL، کد خطا و نام پروتکل مقدار فنی هستند و از این قرارداد مستثنا هستند؛ اما
اگر به کاربر نمایش داده شوند، متن نمایشی آن‌ها نیز باید از resource بیاید.

افزودن زبان جدید فقط با ساخت resource مستقل و تکمیل همان قرارداد کلیدها، ثبت زبان در
`supportedLngs` و تعیین fallback رسمی انجام می‌شود. وجود کلید مفقود، resource ناقص،
متن hard-code یا روش ترجمهٔ جایگزین، blocker تحویل و regression محسوب می‌شود و باید در
بازبینی، type-check و تست missing-key کنترل شود. تا زمان انتقال کامل موارد پراکندهٔ
قبلی، مهاجرت ترجمه پایان‌یافته تلقی نمی‌شود.

برای حذف تکی و گروهی، `window.confirm` و دیالوگ native مرورگر ممنوع است. تمام workspaceها
باید از `ConfirmDialog` مشترک استفاده کنند؛ انتخاب رکورد یا رکوردها در state موقت نگهداری
شود، حذف فقط در `onConfirm` انجام شود و هنگام درخواست async با `busy` از بستن یا تأیید
مجدد جلوگیری شود. باقی‌ماندن هر `window.confirm` برای حذف، خطای قرارداد UI و blocker تحویل
است.

### رفتار route guard و مسیرهای غیرمجاز

**وضعیت:** اصلاح‌شده در UI؛ قرارداد کامل route guard، مسیرهای ناشناخته/غیرمجاز و مرز آن با authorization Backend در [سند ۲۵](25-home.md) ثبت شده است.

### قرارداد فعلی Home

قرارداد فعلی Home، شامل تفاوت وب و ویندوز، route، پوسته، منو، داشبورد، polling، retry، permission و وضعیت API، در [سند مرجع Home وب](25-home.md) نگهداری می‌شود. این سند فقط وضعیت کلی پیاده‌سازی و سیاست regression را ثبت می‌کند.

### JavaScript خام و استثنای فنی مصوب

`src/vendor/mediamtx-reader.js` در `CameraStreamPreview.tsx` استفاده می‌شود. این فایل
برای اتصال WebRTC یک وابستگی فنی خارجی/خام محسوب می‌شود و با خط قرمز JavaScript خام
در بخش ۱۰.۱۰ استاندارد تعارض دارد.

**وضعیت:** استثنای فنی مصوب؛ فعلاً بدون تغییر کد.

انتقال کامل این reader به TypeScript در این مرحله انجام نمی‌شود؛ زیرا فایل فقط یک
helper ساده نیست و منطق WHEP/WebRTC، مذاکره‌ی SDP و codec، ICE، authentication،
retry و مدیریت session را در بر می‌گیرد. بازنویسی بدون تست معادل می‌تواند اتصال
دوربین، سازگاری codec یا cleanup session را دچار regression کند. reader رسمی
MediaMTX برای همین سناریو در نظر گرفته شده و مسیر HLS نیز به‌عنوان fallback در UI
وجود دارد.

مشخصات استثنا:

- **دلیل فنی:** استفاده از reader رسمی MediaMTX برای پخش WHEP/WebRTC در مرورگر؛
  API native مرورگر به‌تنهایی WHEP و منطق signaling این سرویس را فراهم نمی‌کند.
- **محدوده:** فقط `src/vendor/mediamtx-reader.js` و فقط مسیر پخش WebRTC در
  `CameraStreamPreview.tsx`؛ این استثنا مجوز افزودن JavaScript خام جدید در سایر
  بخش‌های پروژه نیست.
- **مالک:** تیم Frontend با هماهنگی مالک زیرساخت و سرویس MediaMTX.
- **ریسک‌ها:** وابستگی به نسخه و API reader، تفاوت پشتیبانی codec/مرورگر،
  مدیریت retry و احتمال باقی‌ماندن session در صورت cleanup ناقص.
- **کنترل‌ها:** نگهداری فایل در مسیر vendor، حفظ declaration TypeScript، بستن
  reader در unmount/disconnect، استفاده از HLS به‌عنوان fallback، و اجرای تست
  lifecycle دوربین پیش از تحویل.
- **برنامه بازبینی:** در صورت تغییر نسخه MediaMTX، تغییر WHEP endpoint، رخداد
  امنیتی یا نیاز به کنترل بیشتر روی lifecycle، adapter TypeScript و جایگزینی
  reader دوباره ارزیابی شود. تا آن زمان فایل خام عمداً بازنویسی نمی‌شود.

## تغییرات انجام‌شده تا این مرحله

### زیرساخت تست

- اضافه‌شدن Vitest و React Testing Library؛
- اضافه‌شدن Playwright و تست پایه‌ی E2E؛
- اضافه‌شدن scriptهای `typecheck`، `test`، `test:watch`، `test:e2e` و `build`؛
- اضافه‌شدن selectorهای پایدار برای فیلدها و دکمه‌های Login؛
- اضافه‌شدن fixture و تست برای Login، API client و قرارداد پاسخ‌ها؛
- تعریف استاندارد اجرای تست عامل هوش مصنوعی در `20-ai-testing-standard.md`.

### API client و قرارداد داده

- اضافه‌شدن timeout پیش‌فرض API؛
- پشتیبانی از cancellation با `AbortController`؛
- مدیریت پاسخ‌های JSON، متن و `204`؛
- اضافه‌شدن parser مبتنی بر Zod برای پاسخ Login و session؛
- ردکردن کاربر نامعتبر یا شناسه کاربر صفر؛
- نگهداری سازگاری با `ResponseResultTypes.Ok = 1` در Backend قدیمی؛
- حفظ سازگاری با پاسخ‌های Legacy که `ResponseResultType` را ارسال نمی‌کنند، مشروط به معتبر بودن user.

### نشست و نگهداری token

- token نشست از Login و SSO توسط Backend در cookie `EosSession` صادر می‌شود؛ cookie
  `HttpOnly` و `SameSite=Lax` است و production باید `AuthCookieSecure=true` و HTTPS
  داشته باشد؛
- UI token را در `sessionStorage`/`localStorage` ذخیره نمی‌کند و در header یا query
  string ارسال نمی‌کند؛ client مشترک همه requestها را با `credentials: include` می‌فرستد؛
- snapshot غیرحساس کاربر در `sessionStorage` فقط برای بازسازی سریع پوسته نگهداری
  می‌شود و اعتبار نشست را تعیین نمی‌کند؛
- Backend برای گذار کم‌ریسک header `UserToken` را موقتاً می‌پذیرد، اما این مسیر
  legacy نباید در قابلیت جدید یا کد UI استفاده شود؛
- CORS باید origin دقیق UI را allow کند؛ استفاده از `Access-Control-Allow-Origin: *`
  همراه credential ممنوع است.

### Permission UI

جزئیات permission و visibility Home در [سند مرجع Home وب](25-home.md) ثبت شده است. تغییرات عمومی API client و سازگاری session باید با آن قرارداد تطبیق داده شوند.

## Regressionهای شناسایی‌شده و اصلاح‌شده

### خرابی Login

در یک تغییر، پاسخ Login بیش از حد سخت‌گیرانه تفسیر شد:

- نبودن `ResponseResultType` ناموفق تلقی شد؛
- وجود token اجباری شد.

این رفتار با Backend قدیمی سازگار نبود. شرط Login با قرارداد واقعی Windows تطبیق داده شد و تست پاسخ `ResponseResultType = 1` اضافه شد.

### خرابی Home

یک regression در تشخیص مدیر و fallback قدیمی رخ داده بود. علت، اتکای صرف به permission نام‌دار در حالی بود که Backend فعلی از `UserAccessLevelId` نیز استفاده می‌کند. وضعیت اصلاح‌شده و قرارداد نهایی آن در [سند ۲۵](25-home.md) ثبت شده است.

## تطبیق کنترل ورود و خروج در ۲۰۲۶/۱۱/۱۲

به درخواست کاربر، موارد باز ممیزی مستندات این منو به‌جز کد Publish رسیدگی شدند:

- انتخاب خودرو در فرم اصلی، چهار دکمهٔ ورود/خروج/جستجو/لغو و تفاوت refresh گرید با استعلام هویت در سند ۶ هماهنگ شدند؛ توضیحات قدیمی دکمهٔ مستقل استعلام حذف شد.
- جزئیات جداکننده، معیار عضو برای تایمر هزینه و مسیر هدف شهاب در سند ۱۲ ثبت شدند؛ منطق تایمر، فوکوس و هاور/فوکوس گریدها تغییر نکرد.
- سقف و قالب‌های فعلی decoder عکس همراه منبع PNG/JPEG در Windows و محدودیت تأیید تصاویر تاریخی در سند ۶ ثبت شدند؛ decoder تازه یا فرمت حدسی اضافه نشد.
- adapter عملیات تردد فقط کد موفقیت ۱ یا نمایش رشته‌ای عددی آن را می‌پذیرد؛ پذیرش بدون قرارداد `ok` حذف و تست مرز پاسخ و تأیید پرداخت اضافه شد. منبع قرارداد `ResponseResultTypes.Ok=1` و serializer فعلی Backend است.
- سند ۲۶ برای مسیر قدیمی Hsh و فهرست موارد نیازمند تأیید سرویس خارجی ایجاد و ارجاع مفقود جایگزین شد. این سند، Hsh را مسیر هدف شهاب معرفی نمی‌کند.

در مرحلهٔ ممیزی اولیهٔ بالا، کد Publish طبق استثنای آن زمان تغییر داده نشد. این محدودیت با درخواست بعدی کاربر برای ساخت بستهٔ مشترک برداشته شد؛ وضعیت جاری در بخش بعد و [راهنمای انتشار، سند ۲۷](27-api-publish-and-hosting.md) ثبت شده است. این یادداشت تاریخی، نقص فعلی در مسیر Publish اعلام نمی‌کند.

**اعتبارسنجی همین نوبت:** ۱۰۵ تست واحد/کامپوننت مرتبط تردد و parser Hsh، ۱۲ سناریوی مرورگر ثبت تردد/پرداخت با API شبیه‌سازی‌شده، typecheck، build و کنترل لینک‌های Markdown موفق بودند. اجرای کل تست‌ها ۲۳۰ موفق و ۴ ناموفق داشت؛ شکست‌ها در `App.test.tsx` و `MemberManagementWorkspace.test.tsx` بودند و یک خطای مدیریت‌نشدهٔ `LocalizationProvider` نیز در تست عضو گزارش شد. بنابراین نتیجهٔ کل پروژه سبز اعلام نمی‌شود؛ در این نوبت آن بخش‌ها تغییر نکرده‌اند. تست سرویس خارجی Hsh یا تصاویر تاریخی دیتابیس انجام نشده است.

## دستیار شناور پلاک‌های اخیر

**تصمیم محصول/رفتار فعلی:** تاریخچهٔ شهاب در کنترل ورود و خروج با نوار شناور قابل جابه‌جایی و بازشدن با هاور اضافه شد. حداکثر ۱۰۰ تشخیص هر پارکینگ/درب در حافظه نگهداری می‌شود؛ تکراری‌بودن پلاک، تازگی زمانی نوار و وضعیت اتصال سه مفهوم جدا هستند. جستجو و فیلتر محلی‌اند و انتخاب پلاک از همان اعتبارسنجی و استعلام فرم عبور می‌کند. تأیید جایگزینی، اطلاعات جاری را حفظ می‌کند و انتخاب تاریخچه ثبت خودکار تردد ندارد. قرارداد کامل، دسترسی‌پذیری، ذخیرهٔ موقعیت، محدودیت حافظه و منابع در [سند ۱۲، بخش ۳.۵.۲](12-manual-traffic-control-form.md) ثبت شده‌اند. Backend، payload ثبت/پرداخت و منطق هاور/فوکوس گریدها در این قابلیت تغییر نکردند.

**اعتبارسنجی این قابلیت:** ۱۳ تست واحد مرتبط تاریخچه، اتصال شهاب و formatter، ساخت TypeScript/production و ۲۶ سناریوی مرورگر تاریخچه، ثبت، پرداخت و هاور/فوکوس گریدها موفق بودند؛ چهار سناریوی نمایش دوربین نیز جداگانه موفق شدند. شبکه در این آزمون‌ها شبیه‌سازی شده است. آزمون تاریخچه، ثابت‌ماندن ردیف در حال مطالعه هنگام دریافت جدید، الزام کارت، تأیید جایگزینی، تفکیک درب، ذخیرهٔ موقعیت، resize، حالت روشن/تاریک و reduced-motion را پوشش می‌دهد؛ اتصال به SQL و سخت‌افزار واقعی بخشی از این اعتبارسنجی نبوده است.

**اصلاح جایگاه و ظاهر به درخواست بعدی کاربر:** نوار نوشته‌دار پایین صفحه با آیکن تاریخچهٔ ظریف کنار باکس آخرین تشخیص جایگزین شد؛ در فارسی چسبیده به لبهٔ چپ و در انگلیسی به لبهٔ راست است. متن فقط هنگام هاور/بازشدن نمایش داده می‌شود. جای پیش‌فرض، با scroll و تغییر اندازهٔ باکس همراه است؛ موقعیت دستی با کلید نسخهٔ جدید ذخیره می‌شود تا محل قدیمی نوار باقی نماند. ظرفیت ۱۰۰ تشخیص، تکرارها، جستجو، فیلتر و مسیر انتخاب قبلی حفظ شدند. اعتبارسنجی این اصلاح شامل ۱۰ تست واحد تاریخچه/شهاب و ۱۴ سناریوی مرورگر تاریخچه/دوربین در دسکتاپ، موبایل، فارسی و انگلیسی، به‌همراه typecheck/build است؛ شبکهٔ آزمون شبیه‌سازی شده است.

### گرید آخرین تشخیص‌های امروز

**تصمیم محصول/رفتار فعلی پس از درخواست جدید:** گرید دستیار از `AppDataGrid` مشترک استفاده می‌کند و فقط پلاک، زمان و جهت دارد. جستجوی ستونی داخل هدر است؛ نوار جستجوی مستقل و فیلترهای همه/تازه/تکراری حذف شدند. تکراری‌بودن با رنگ ملایم ردیف، همراه توضیح دسترس‌پذیر، مشخص می‌شود. شرح اولیهٔ حافظهٔ نشست و فیلترهای آن در بالا، تاریخچهٔ توسعه است و قرارداد فعلی را توصیف نمی‌کند.

برای تأمین ۱۰۰ تشخیص آخر امروز، سورس سرویس شهاب نیز در همان قابلیت مجاز تغییر کرد: متد `GetHistory` روی Hub فعال، متادیتای محدود امروزِ سرور را از `dbo.ANPR` می‌خواند؛ snapshot در اتصال اولیه/مجدد، بازشدن دستیار و تغییر روز دریافت و با پیام‌های زنده ادغام می‌شود. پاسخ تاریخی عملیات فرم را اجرا نمی‌کند. مجوز قبل/بعد از خواندن و اشتراک هنگام تحویل کنترل می‌شوند. قرارداد، روز سرور، محدودیت SQL، retry و مرز تست در [سند ۱۲، بخش ۳.۵.۲](12-manual-traffic-control-form.md) و `Hosting/README.md` ثبت شدند. این قابلیت به استقرار نسخهٔ جدید سرویس نیاز دارد؛ پوشهٔ فعال IIS در این تغییر خودکار جایگزین نشده است.

**اعتبارسنجی:** تست واحد تاریخچه، snapshot و گرید مشترک؛ ۱۹ سناریوی مرورگر تاریخچه/دوربین/هاور و فوکوس گریدها؛ typecheck و build UI موفق بودند. سورس API با وابستگی‌های Release موجود در خروجی مستقل `obj/ShahabHistoryBuild` کامپایل و `Verify-ShahabTraffic.ps1` روی آن موفق شد؛ خواندن ۱۰۰ رکورد امروز، مرز روز، دسترسی و پاسخ دیرهنگام اشتراک قطع‌شده با store شبیه‌سازی‌شده بررسی شدند. Rebuild کامل همهٔ پروژه‌های وابسته یا اجرای query تاریخچه روی SQL عملیاتی تأیید نشده است؛ موفقیت این تست‌ها به‌معنای استقرار روی IIS یا آزمایش سخت‌افزار نیست.

### فشرده‌سازی سربرگ دستیار و ثبت گزینهٔ «اولویت تصویر»

**رفتار فعلی UI:** زیرعنوان «بدون تشخیص» و زمان نسبی زیر عنوان دستیار حذف شده‌اند؛ عنوان و شمارنده در سربرگ تک‌ردیفی با حداقل ارتفاع ۳۲ پیکسل قرار دارند. ارتفاع هدف پنل نیز ۲۰ پیکسل کمتر شده و نماد ساعت با `ListAltRounded` در آیکن شناور و سربرگ جایگزین شده است. زمان دقیق هر تشخیص در گرید و Tooltip پلاک باقی است؛ قوانین تازگی رنگ، ظرفیت ۱۰۰ رکورد امروز، انتخاب، جستجو و جابه‌جایی تغییر نکرده‌اند. بیلد و چهار سناریوی موجود مرورگر برای تاریخچهٔ امروز، جابه‌جایی در عرض‌های ۳۹۰/۱۴۴۰ و انگلیسی در حالت تیره با reduced-motion موفق بودند؛ شبکه شبیه‌سازی شده بود.

**تکمیل مستندات، بدون تغییر تازهٔ کد:** گزینهٔ بصری «اولویت تصویر» در [سند ۱۲، بخش ۳.۶.۴](12-manual-traffic-control-form.md) ثبت شد. نسبت‌های نمونه، چیدمان دو دوربین و آخرین تشخیص از وضعیت فعلی جدا شده‌اند. درخواست‌های جدیدتر محصول دربارهٔ چهار اکشن بالای باکس، مشخصات غیرmodal و دستیار شناور بر جزئیات قدیمی پیش‌طرح تقدم دارند. این ثبت، اعلام اجرای کامل variant یا تغییر پیش‌فرض تب دوربین نیست؛ بررسی این نوبت محدود به تطبیق منابع و صحت مستندات است.

## قانون نمایش خطاهای ارتباط زنده در عنوان بخش‌ها

**تصمیم محصول / رفتار فعلی وب:** خطاهای ارتباط زنده، polling و snapshot همان اتصال، به آیکن در عنوان بخش با Tooltip هاور/فوکوس تبدیل شدند؛ متن خطا در بدنه، Alert و toast خودکار ندارند. این الزام برای تمام برنامه در [استاندارد، قانون مشترک خطاهای ارتباط زنده](00-documentation-standard.md) ثبت شده و `ConnectionStatusIndicator.tsx` مصرف‌کنندهٔ مشترک پیام ترجمه‌شده است. نشانگرهای تخصصی دوربین نیز همین قرارداد را رعایت می‌کنند.

| محل | تطبیق انجام‌شده |
|---|---|
| گرید ورود/خروج | آیکن کنار عنوان هر گرید؛ حفظ ردیف، انتخاب و scroll در خطای موقت؛ رفع آیکن پس از دریافت موفق |
| دستیار پلاک‌های اخیر | خطای snapshot فقط در سربرگ؛ حفظ اطلاعات معتبر امروز و retry قبلی |
| نقشهٔ جایگاه‌ها | وضعیت اتصال و stale/error فقط آیکن و Tooltip در عنوان؛ حفظ داده در قطع موقت و پاک‌کردن طبق دسترسی؛ retry مجاز روی آیکن خطا |
| داشبورد | خطای به‌روزرسانی اطلاعات پارکینگ در کنار عنوان پارکینگ؛ برنامهٔ polling و refresh قبلی حفظ شد |
| مانیتورینگ درب‌ها/ترددها | نشانگر مستقل در عنوان هر منبع؛ موفقیت یکی هشدار دیگری را پاک نمی‌کند |
| مانیتورینگ تشخیص پلاک | خطای SignalR در سربرگ؛ subscribe موفق بدون انتظار برای پلاک تازه نیز نشانگر را رفع می‌کند؛ خطای عملیات/بارگذاری مستقل پاک نمی‌شود |
| دوربین | خطای دریافت اطلاعات دوربین در toolbar، خطای پخش و تشخیص در Tooltip نشانگر تخصصی؛ نام دسترس‌پذیر و فوکوس کیبورد نشانگر پخش تکمیل شد |

مسیرهای SignalR و timerهای به‌روزرسانی برنامه برای تعیین این مصرف‌کننده‌ها بررسی شدند. خطای ثبت/پرداخت/حذف/اعتبارسنجی، دریافت عادی مستقل و empty/loading مشمول تبدیل نیستند. endpoint یا Backend تغییر نکرده است؛ 401/403 و پاک‌کردن دادهٔ غیرمجاز حفظ شده‌اند. مشخصات wrapper، قواعد بصری و سناریوی پذیرش در اسناد ۱۰، ۱۸ و ۲۰ و رفتار حوزه در اسناد ۶، ۷، ۱۲ و ۲۵ به‌روز شدند.

**اعتبارسنجی:** ۲۴ تست واحد/component مرتبط و ۲۸ سناریوی یکتای مرورگر برای گرید، شهاب، دوربین و نقشه موفق شدند؛ یک اجرای اولیهٔ انگلیسی در انتظار بارگذاری فهرست پارکینگ timeout شد و در اجرای مجدد همان سناریو با هم‌زمانی کمتر موفق بود. بررسی شامل هاور/کیبورد Tooltip، عدم Alert متنی، حفظ انتخاب/scroll/ارتفاع، recovery، خطای دو منبع مستقل، لغو دسترسی، RTL/LTR، موبایل و حالت تیره است. typecheck و production build موفق‌اند؛ شبکه و transport در تست‌ها شبیه‌سازی شده‌اند و اتصال سخت‌افزار/سرویس واقعی ادعا نمی‌شود.

## انتشار بستهٔ مشترک سرویس و IIS

**تصمیم محصول/رفتار فعلی:** اصلاح کد Publish به درخواست صریح کاربر انجام شد. پروژهٔ سرویس `Hosting/DualHostPublish.targets` را import می‌کند؛ hook پس از `PublishOnly` هم Publish واقعی IDE و هم خط فرمان را به ساخت مستقل Release/AnyCPU هدایت می‌کند. EXE ریشه برای Windows Service و DLL داخل `bin` برای IIS از همان سورس ساخته می‌شوند؛ تنظیمات مشترک‌اند. راهنمای فارسی کاربر در [سند ۲۷](27-api-publish-and-hosting.md)، جزئیات فنی در `Services/EosParkingApiWindowsService/Hosting/README.md` و الزامات شهاب در بخش ۳.۵.۱ سند ۱۲ قرار دارند.

مقصد به‌ترتیب از `DualHostPublishDir` صریح، `PublishUrl` انتخابی IDE و پیش‌فرض `publish` کنار پروژه می‌آید. بسته ابتدا در staging کامل ساخته می‌شود؛ انتشار مجدد، تنظیمات و `App_Data/RtspStreams` را حفظ و نسخهٔ قبلی را برای rollback نگه می‌دارد. کد stale به بستهٔ جدید منتقل نمی‌شود. میزبان فعال در این اصلاح خودکار متوقف یا restart نمی‌شود.

**اعتبارسنجی این اصلاح:** Publish و republish واقعی ویژوال‌استودیو در دو حالت Debug و Release روی پروژهٔ کپی‌شده و مقصد موقت موفق شدند؛ متادیتای هر دو فایل runtime، فعال‌بودن بهینه‌سازی را تأیید کرد. حفظ بایت‌به‌بایت تنظیمات، داده‌های runtime، حذف DLL قدیمی، اولویت مقصد صریح، مسیر ساخت مستقل و اعتبار XML/PowerShell بررسی شدند. بستهٔ خروجی IDE در هاست سرویس و IIS Express، با workerها/دستگاه‌های غیرفعال، تست شد؛ کشف Controllerها، مذاکرهٔ نام‌دار شهاب، مسیرهای HTTP، shutdown و جلوگیری از اجرای هم‌زمان همان نصب موفق بودند. این تست، اتصال به SQL و دستگاه واقعی یا نصب سرویس در SCM را ادعا نمی‌کند.

## اصلاح مستندات کنترل ورود و خروج بر مبنای سورس — ۲۰۲۶/۱۱/۱۲

**تصمیم صریح محصول / تغییر مستندات:** در سه مورد تطبیق جریان خروج، قرارداد API و چیدمان، سورس جاری ملاک است. نمودار و شرح اسناد ۶ و ۱۲ هماهنگ شدند: خروج ابتدا با `DoSave=true` ثبت می‌شود و تسویه می‌تواند در همان نوبت یا بعداً از گرید خروج‌ها انجام شود؛ بستن پنجره، پایان تایمر یا شکست پرداخت، خروج ثبت‌شده را برنمی‌گرداند و پرداخت محسوب نمی‌شود.

جدول API سند ۱۲ با route، method، ورودی و نوع پاسخ واقعی Controllerها تکمیل شد؛ `PayDump`، wrapper موفقیت/خطا، رفتار HTTP 200/401 و مرز احراز هویت نیز ثبت شدند. نیاز به OpenAPI و آزمون نصب واقعی از اطلاعات مشخص در سورس جدا شد. شرح چیدمان ثابت ۳۰٪/۱۹۰–۲۷۰ پیکسل و شرط قدیمی ارتفاع ۷۲۰ پیکسل با رفتار CSS و جداکنندهٔ فعلی جایگزین شد؛ گریدهای دسکتاپ فضای باقی‌مانده را می‌گیرند و ارتفاع ۲۷۰ پیکسل مربوط به قاب گرید در عرض ۶۸۰ پیکسل و کمتر است.

**اعتبارسنجی و دامنه:** تغییر فقط در اسناد ۶، ۱۲، ۲۱ و فهرست مستندات است. متن با Controllerها، `ResponseResultWeb`، فیلتر احراز هویت، DTOها، `trafficOperationService`، `TrafficRecordsWorkspace`، CSS و جداکننده تطبیق داده شد. لینک‌های محلی و نبود عبارت‌های قدیمیِ متناقض بررسی شدند؛ تست اجرایی، build، اتصال SQL یا سخت‌افزار در این نوبت انجام نشده است.

## سیاست اجباری جلوگیری از Regression

هیچ تغییر جدیدی نباید قابلیت، ظاهر یا رفتار قبلی را بدون تصمیم صریح محصول حذف یا خراب کند.

قبل از تحویل هر تغییر، حداقل این موارد باید بررسی شوند:

1. `npm run typecheck`
2. `npm run test`
3. `npm run build`
4. Login با پاسخ Legacy واقعی یا fixture معادل؛
5. Home برای کاربر مدیر و کاربر عادی با `HomeShell` مشترک و visibility صحیح navigation؛
6. حفظ Header، navigation، tabs/classic، theme، زبان و responsive behavior؛
7. حفظ route و session بعد از refresh؛
8. بررسی اینکه placeholderهای قبلی، menu itemها و navigation بدون تصمیم محصول حذف نشده باشند.

## قواعد تغییر کد

- تغییر قرارداد Backend باید با adapter انجام شود، نه با جایگزینی ناگهانی رفتار قبلی؛
- parser جدید باید پاسخ‌های Legacy ثبت‌شده را پوشش دهد؛
- permission جدید باید تا زمان تحویل Backend، fallback سازگار داشته باشد؛
- تغییر CSS یا theme باید در light/dark، فارسی/انگلیسی، desktop/mobile بررسی شود؛
- عملیات حساس نباید با mock موفقیت‌آمیز به‌عنوان قابلیت واقعی گزارش شوند؛
- هر regression باید با یک تست بازتولیدکننده ثبت و سپس اصلاح شود؛
- تست موفق به‌تنهایی کافی نیست؛ حفظ رفتار قبلی نیز بخشی از معیار پذیرش است.

## وضعیت اعتبارسنجی فعلی

در آخرین بررسی:

- نتیجه‌ی آخرین اجرای تست باید در زمان تحویل از خروجی واقعی همان commit ثبت شود؛ تعداد ثابت تست‌ها قرارداد مستندات نیست.
- `typecheck` موفق است؛
- `build` موفق است؛
- build یک هشدار non-blocking برای chunkهای بزرگ‌تر از ۵۰۰KB دارد؛ chunkهای بزرگ فعلی
  حدود ۸۲۰KB و ۷۳۳KB هستند و باید در بررسی performance/lazy-loading پیگیری شوند؛
- تست E2E از نظر کد آماده است، اما اجرای آن به نصب Chromium وابسته است و دانلود مرورگر در محیط فعلی با خطای منطقه‌ای `403` متوقف شده است؛
- اتصال واقعی Backend، session refresh، permission server-side، idempotency، تجهیزات و workflowهای اصلی هنوز نیازمند قرارداد Backend هستند.

## تصمیم تثبیت‌شده

«تکمیل یک قابلیت جدید» زمانی قابل قبول است که قابلیت‌های قبلی همچنان کار کنند. سرعت توسعه، ساده‌سازی معماری یا سخت‌گیرترکردن validation مجوز تغییر رفتار موجود بدون تست regression نیست.

## ثبت اصلاحات خطوط قرمز React

در بازبینی اخیر، موارد زیر برای انطباق با بخش ۱۰.۱۰ استاندارد اصلاح شدند:

- درخواست Login از صفحه خارج و به `features/auth/authService.ts` و hook اختصاصی منتقل شد؛
- مدیریت theme، direction، زبان و font از دستکاری مستقیم `document.documentElement` به state، props، `ThemeProvider` و ریشهٔ declarative React منتقل شده است؛ `App.tsx` نباید برای این stateهای UI مستقیماً `document` یا style آن را تغییر دهد؛
- routeهای workspace با `lazy` و `Suspense` بارگذاری می‌شوند؛
- gradient، حرکت نمایشی کارت‌ها و shadowهای سنگین فقط در صورت ثبت در سیاست افکت‌های بصری، استفاده از token مشترک، رعایت کنتراست و پشتیبانی از `prefers-reduced-motion` مجاز هستند؛ موارد فاقد هدف یا ایجادکننده‌ی اختلال باید حذف شوند؛
- کلید رمزنگاری Legacy دیگر در source قرار ندارد و فقط از پیکربندی محیطی خوانده می‌شود؛ نبودن آن باید با خطای امن متوقف شود؛
- password در هیچ storage مرورگر ذخیره نمی‌شود. مقادیر موجود در test setup صرفاً fixture تستی هستند و نباید وارد production شوند.

موارد باز این بازبینی—تکمیل workflowهای خارج از دامنه‌ی این snapshot و بهینه‌سازی
chunkهای بزرگ—هنوز اصلاح نشده‌اند و نباید به‌عنوان موارد انجام‌شده گزارش شوند.
`mediamtx-reader.js` دیگر مورد بلاتکلیف نیست و طبق استثنای فنی مصوب بالا فعلاً
بدون تغییر نگهداری می‌شود.

این تغییرات باید در هر feature جدید نیز رعایت شوند؛ هر دستکاری imperative UI، secret ثابت، ذخیره password یا API مستقیم در page، مانع تحویل است.
