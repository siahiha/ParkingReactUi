**چیدمان پنجره — ۲۰۲۶/۱۱/۱۹:** فرم ایجاد/ویرایش در `CrudDialog` با عرض `md` و گروه‌های مشترک `AppGroupBox` نمایش داده می‌شود. نام، نوع و وضعیت در گروه مشخصات تجهیز قرار دارند. اطلاعات اتصال، پیش‌نمایش/تست، تنظیمات تخصصی و گزینه‌های کنترل گروه‌های مستقل‌اند. در دسکتاپ، اطلاعات اتصال و تنظیمات تخصصی در ستون اصلی و پیش‌نمایش/تست و کنترل در ستون کناری هستند؛ در عرض باریک، ترتیب مشخصات، اتصال، پیش‌نمایش/تست، تنظیمات تخصصی و کنترل تک‌ستونه می‌شود. نام در موبایل یک ردیف کامل و نوع/وضعیت کنار هم‌اند. IP و پورت، نام کاربری و رمز، و چهار مختصات تشخیص در ردیف‌های مرتبط قرار دارند؛ URLها عرض کامل گروه را می‌گیرند. فقط متن ورودی آدرس/عدد LTR است و label جهت زبان فرم را حفظ می‌کند. باکس‌های هم‌ردیف با stretch بالا/پایین تراز هستند؛ قاب تست دستگاه نیز همان `AppGroupBox` را دارد تا اختلاف هندسهٔ legend ایجاد نشود. padding و فاصلهٔ گروه‌ها ۱۲ پیکسل است. جای تصویر پیش‌نمایش ارتفاع ۱۱۲ پیکسل و عرض گروه را دارد و تصویر با نسبت طبیعی داخل آن جا می‌گیرد؛ پس از شروع تست، کنترل‌های داخلی پیش‌نمایش جای دکمهٔ شروع اولیه را می‌گیرند. footer مشترک تأیید/انصراف در جای ثابت پنجره باقی است. API و رفتار ذخیره/تست تغییر نکرده‌اند.

**رفتار فعلی وب:** گرید نام، نوع، IP، پورت و وضعیت فعال‌بودن را نشان می‌دهد. ابزارهای بالای گرید به ترتیب جدید، ویرایش و حذف‌اند؛ ویرایش با انتخاب یک رکورد و دوبارکلیک نیز باز می‌شود. حذف با `ConfirmDialog` و در زمان درخواست با قفل busy انجام می‌شود. بستن پنجرهٔ دارای تغییر، تأیید کنارگذاشتن تغییرات می‌خواهد؛ لغو API ذخیره اجرا نمی‌کند.

مشخصات مشترک شامل نام، نوع، فعال/غیرفعال و کنترل خودکار است. دوربین فیلدهای آدرس، پورت، نام کاربری، رمز، RTSP URL و منبع/مختصات تشخیص دارد. برای سایر تجهیزات، نوع ارتباط و تنظیمات مرتبط شبکه یا سریال، رله، timeoutها و کنترل PC نمایش داده می‌شود؛ گزینهٔ کنترل از سرویس برای راهبند است. غیر‌فعال‌بودن تجهیز با قطع اتصال لحظه‌ای یکسان نیست.

نام و اطلاعات ارتباطی معتبر در UI الزامی‌اند؛ پورت شبکه ۱ تا ۶۵۵۳۵، IPv4 دستگاه شبکه و COM عددی بررسی می‌شوند. تنظیم غیرخالی منبع پلاکخوان نیز با parser موجود بررسی می‌شود. محدودیت‌های server در بخش ۴ آمده‌اند؛ validation UI جایگزین آن‌ها نیست.

stateها: بارگذاری فهرست، جدول خالی، خطای دریافت با refresh، ایجاد، ویرایش/dirty، ذخیره/busy، موفقیت، خطای ذخیره، تأیید حذف و خطای حذف. خطای تست زنده فقط در نشانگر بخش اتصال با Tooltip هاور/فوکوس نمایش داده می‌شود؛ خطای CRUD بازخورد عملیاتی مستقل دارد. فارسی/انگلیسی از i18next و جهت از زبان فعال گرفته می‌شوند؛ فرم در عرض باریک تک‌ستونه است.

**تست دوربین — اصلاح ۲۰۲۶/۱۱/۱۹:** یک کلیک «تست ارتباط دوربین» پیش‌نمایش مشترک را باز و اتصال WebRTC را شروع می‌کند؛ کلیک دوم داخل تصویر لازم نیست. قطع/وصل دستی و انتخاب HLS از کنترل‌های پیش‌نمایش ممکن است. بستن فرم یا تغییر فیلدها پیش‌نمایش را آزاد می‌کند. اگر RTSP URL وارد شده باشد، مقدار فعلی همان فیلد در درخواست تست ارسال می‌شود؛ در نبود آن، API دوربین ذخیره‌شده را با شناسه حل می‌کند. تست دوربین جدید بدون RTSP URL و تست تغییرات IP/پورت/credential بدون URL صریح، قرارداد مستقلی برای ارسال این فیلدها ندارند؛ این اصلاح قرارداد API را تغییر نمی‌دهد. مرجع جزئیات پخش سند ۲۴ است.

## ۳. قرارداد HTTP موجود

| عمل | method و مسیر | ورودی | نوع `Values` در پاسخ موفق | اثر UI |
|---|---|---|---|---|
| فهرست | `GET api/Parking/GetParkingEquipments?parkingId={long}` | شناسهٔ پارکینگ جاری در query | `EquipmentEntity[]`، شامل آرایهٔ خالی | جایگزینی فهرست و پاک‌کردن انتخاب |
| ایجاد/ویرایش | `POST api/Parking/SaveParkingEquipment` | یک `EquipmentEntity` در JSON body، بدون wrapper | شناسهٔ عددی مثبت `long` | بستن پنجره و دریافت دوبارهٔ فهرست |
| حذف | `GET api/Parking/DeleteEquipmentById?equipmentId={long}` | `equipmentId` در query؛ `id` صحیح نیست | `bool`؛ فقط `true` موفق است | بستن تأیید و دریافت دوبارهٔ فهرست |
| تست مستقل اتصال | `POST api/Equipment/TestConnection` | تنظیمات ارتباطی فعلی فرم؛ بدون شناسهٔ تجهیز یا درب | پاسخ مستقیم `{Status, Connected, CheckedAtUtc}`؛ بدون envelope | نمایش نتیجهٔ همان یک تست |

پاسخ عمومی CRUD از نوع زیر است؛ casing فعلی فیلدها PascalCase است:

```json
{ "ResponseResultType": 1, "Message": null, "RealMessage": null, "Values": 42 }
```

`Values` مطابق جدول، آرایه/شناسه/boolean است. `HttpResponseType` با `JsonIgnore` ارسال نمی‌شود. `ResponseResultType=1` موفق است؛ HTTP 200 به‌تنهایی موفقیت نیست. در React، `equipmentService` envelope و دادهٔ مؤثر را با Zod بررسی می‌کند: شناسهٔ صفر/منفی، حذف `false`، نتیجهٔ تجاری ناموفق یا پاسخ malformed موفق نمایش داده نمی‌شوند. خطای خام `RealMessage` به کاربر نمایش داده نمی‌شود.

### نشست، خطا و retry

- هر سه action دارای `AthunticationFilter` هستند؛ نشست نامعتبر/منقضی HTTP 401 با `ResponseResultType=11` می‌دهد. UI از cookie نشست و client مشترک استفاده می‌کند؛ توکن یا secret سرویس به درخواست جدید افزوده نمی‌شود.
- Controller برای استثناهای داخل action نیز HTTP 200 و `FailResponse` می‌سازد. خطای عمومی `ResponseResultType=2` است؛ استثناهای دامنه کد خود را دارند، مانند نام تکراری `21`. `Message` ممکن است خالی و `RealMessage` شامل جزئیات داخلی باشد.
- null در body ذخیره، طبق Repository مقدار `-1` می‌دهد؛ این نتیجه موفقیت ذخیره نیست. حذف شناسهٔ ناموجود طبق Repository `true` می‌دهد.
- در CRUD تجهیزات بررسی مجوز اختصاصی پارکینگ/ایجاد/ویرایش/حذف در این actionها و Repository مشاهده نشد؛ وجود authentication به معنی authorization اختصاصی نیست. همچنین خطای وابستگی با HTTP 409 و فهرست وابستگی‌ها در این مسیر موجود نیست.
- timeout HTTP کلاینت ۱۵ ثانیه است؛ درخواست تست با signal نیز قابل لغو است. CRUD retry خودکار ندارد؛ حذف GET نیز نباید خودکار تکرار یا prefetch شود. در خطای بارگذاری، refresh دستی و در خطای ذخیره/حذف، تلاش مجدد کاربر ممکن است. مدل خطای versioned، trace id و قرارداد idempotency موجود نیستند.

**رفتار فعلی Repository:** ایجاد Entity را اضافه و ذخیره می‌کند؛ ویرایش با Attach و فهرست مشخص propertyهای modified است. حذف با `RemoveRange` فیزیکی انجام می‌شود؛ پیش‌بررسی ارتباط به درب، audit اختصاصی و قرارداد پاسخ تعارض در این متد نیستند. محدودیت کلید خارجی/طرح SQL نصب‌شده ممکن است حذف را رد کند؛ چنین خطایی در این Controller به envelope شکست تبدیل می‌شود، نه الزاماً 409.

**تفاوت‌های مهم مدل/مصرف:** `RtspUrl` عضو `EquipmentEntity` فعلی نیست؛ ارسال آن از فرم، ماندگاری در CRUD را ثابت نمی‌کند. `DeviceManager.CreateConnection` برای اتصال سریال از `Port` استفاده می‌کند، نه `ComPort`؛ این دو مقدار نباید بدون تصمیم قرارداد جابه‌جا شوند. کنترل‌کنندهٔ چهره در درایور اتصال TCP/IP را cast می‌کند و QR آنلاین مستقیماً IP/Port می‌گیرد؛ پشتیبانی سریال برای این دو از سورس تأیید نمی‌شود.

## ۵. تست مستقل اتصال؛ یک درخواست، یک تلاش، یک پاسخ

**اصلاح صریح کاربر — ۲۰۲۶/۱۱/۱۸:** کنترل ورود و خروج فقط منبع الگوی اتصال درایورهاست. تست تجهیزات به درب، شیفت، SignalR، وضعیت کش‌شده یا ذخیرهٔ قبلی تجهیز وابسته نیست. پیاده‌سازی اولیهٔ مبتنی بر Hub درب کنار گذاشته و از UI حذف شده است.

قرارداد تنها endpoint مصرفی UI:

```http
POST api/Equipment/TestConnection
Content-Type: application/json
```

```json
{
  "ParkingId": 7,
  "DeviceType": 1,
  "ConnectionType": 1,
  "Ip": "192.0.2.10",
  "Port": 1001,
  "ComPort": null,
  "BoudRate": 9600,
  "ReadTimeOut": 3000,
  "WriteTimeOut": 3000
}
```

`ParkingId` فقط context دسترسی تجهیزات است؛ ورودی `Id` یا `DoorId` وجود ندارد. مقادیر از همین لحظهٔ فرم می‌آیند؛ تست دستگاه جدید، تغییر ذخیره‌نشده و تجهیز غیرفعال نیز ممکن است و هیچ‌کدام تجهیز را در دیتابیس ذخیره یا فعال نمی‌کنند. نمونهٔ IP بالا آدرس مستندسازی است.

پاسخ مستقیم و فاقد اطلاعات محرمانه است:

```json
{ "Status": "connected", "Connected": true, "CheckedAtUtc": "2026-11-18T08:00:00Z" }
```

| Status | معنی |
|---|---|
| `connected` | همان تلاش اتصال موفق و اتصال موقت بسته شده است |
| `disconnected` | تلاش اتصال ناموفق؛ retry خودکار انجام نشده است |
| `unsupported` | این نوع درایور تست ندارد؛ اتصال آغاز نمی‌شود |
| `invalid-config` | ورودی ارتباطی نامعتبر است |
| `timeout` | مهلت ده‌ثانیه‌ای اجرای تست به پایان رسیده است |
| `busy` | هر چهار ظرفیت تست هم‌زمان در حال استفاده‌اند؛ درخواستی در صف تکرار نمی‌شود |
| `error` | خطای درایور؛ متن خام/credential برگردانده نمی‌شود |

`Connected` فقط برای `connected` برابر true است. پاسخ HTTP عادی تست ۲۰۰ است، حتی اگر دستگاه وصل نشود یا نوع آن پشتیبانی نشود. ورودی نامعتبر HTTP 400، نشست نامعتبر 401، نداشتن مجوز 403 و پارکینگ ناموجود 404 است. UI پاسخ عادی را با Zod و سازگاری Status/Connected بررسی می‌کند؛ تایم‌اوت HTTP کلاینت ۱۵ ثانیه است. خطا یا نتیجه فقط در نشانگر عنوان و Tooltip قابل فوکوس دیده می‌شود. نمایش خطای عمومی HTTP 503 در UI همچنان پشتیبانی می‌شود، اما متد تست برای نبود تنظیم سرویس واسط چنین پاسخی تولید نمی‌کند.

**اجرا:** `EquipmentConnectionTester.TestAsync` یک probe موقت می‌سازد و فقط یک بار `DeviceManager.TestConnection` را اجرا می‌کند. این متد ساخت اتصال را با درایورهای موجود مشترک دارد، اما حلقهٔ دریافت رکورد، Start/Start2، subscription، بازکردن راهبند، پرداخت، هماهنگ‌کردن ساعت یا ذخیرهٔ اطلاعات انجام نمی‌دهد. probe در finally/Dispose آزاد می‌شود. در مسیر سریال، COM ورودی به Port موردنیاز سازندهٔ درایور نگاشت می‌شود؛ این نگاشت فقط متعلق به تست و مستقل از ذخیرهٔ CRUD است.

timeoutهای هر عملیات SDK برای تست به حداکثر ۵ ثانیه محدود می‌شوند؛ مقادیر فرم تغییر یا ذخیره نمی‌شوند. مهلت کل پاسخ ده ثانیه است. SDKهای همگام ممکن است قابل لغو فوری نباشند؛ در timeout یا قطع درخواست، worker پس از بازگشت SDK اتصال را می‌بندد و ظرفیت تا پایان cleanup آزاد نمی‌شود تا درخواست‌های جدید worker نامحدود نسازند. UI لغو و تغییر تنظیمات/خروج از فرم را با AbortController انجام می‌دهد و پاسخ دیررس را نادیده می‌گیرد.

**دسترسی مستقل:** `AthunticationFilter` نشست را کنترل می‌کند. endpoint کاربر فعال غیرراننده با `ParkingEquipment`، `ParkingEquipmentAddOrEdit` یا `DashbordManaging` و وجود پارکینگ را بررسی می‌کند؛ کاربر ویژهٔ موجود استثنای مدیر را دارد. هیچ پرس‌وجوی درب یا شیفت و هیچ مجوز `ParkingManualIO` لازم نیست.

**دو میزبان — تصمیم صریح کاربر، ۲۰۲۶/۱۱/۱۸:** متد تست در همان میزبان دریافت‌کنندهٔ API، چه IIS و چه Windows Service، مستقیماً یک اتصال موقت به دستگاه برقرار می‌کند و پس از بستن آن نتیجه را برمی‌گرداند. ارسال درخواست به سرویس جداگانه و تنظیم `EquipmentTestServiceUrl` حذف شده‌اند. این تست به `RunDeviceManagerInIis` یا فعال‌بودن reader پس‌زمینه وابسته نیست؛ تنظیم‌های مدیریت دستگاه همچنان فقط اجرای اتصال‌های دائمی پس‌زمینه را کنترل می‌کنند. مجوز و اعتبارسنجی endpoint حفظ شده‌اند. موفقیت با `connected`، عدم اتصال با `disconnected` و استثنای اجرای probe با `error` اعلام می‌شود.

## ۶. تفکیک انواع دارای اتصال و موارد بعدی

این جدول بر اساس مسیر واقعی `DeviceManager.Connect` است؛ صرف وجود enum یا تنظیم `Enable...` به معنی وجود درایور نیست.

## ۷. دسترسی و حفاظت داده

مجوزهای Windows برای ایجاد/ویرایش و حذف، `ParkingEquipmentAddOrEdit` و `ParkingEquipmentDelete` هستند. route تجهیزات از permission مدل منوی فعلی عبور می‌کند. تفکیک کامل view/manage/delete و enforce آن در CRUD سرور هنوز باید تکمیل شود؛ تست مستقل از مجوز عملیات تردد است؛ نتیجهٔ آن مجوز بازکردن راهبند یا ثبت تردد ایجاد نمی‌کند.

**یافتهٔ سورس، نیازمند اصلاح Backend:** `CameraPassword` روی Entity دارای `JsonIgnore` نیست و فهرست، Entity را مستقیم برمی‌گرداند؛ بنابراین تضمین حذف رمز از response در این قرارداد وجود ندارد. در update نیز رمز همیشه modified می‌شود؛ «عدم ارسال رمز یعنی حفظ رمز قبلی» تضمین نشده است. فرم مقدار ورودی رمز را mask می‌کند و storage ماندگار تازه‌ای برای رمز ندارد، ولی این رفتار، حفاظت response و ذخیرهٔ Backend را تأیید نمی‌کند. رمز و `RealMessage` نباید به log/Tooltip راه پیدا کنند. این تغییر سیاست ذخیرهٔ رمز Backend را تغییر نمی‌دهد.

## ۹. معیار پذیرش و شواهد

**پذیرش چیدمان نهایی:** در دسکتاپ، باکس‌های یک ردیف باید مختصات بالا/پایین مشترک و باکس‌های هر ستون لبه‌های چپ/راست مشترک داشته باشند. اندازه‌گیری مرورگر در فارسی و انگلیسی، برای فرم دوربین و راهبند در ۱۳۶۶×۷۶۸ و ۱۲۸۰×۷۲۰، تراز لبه‌ها و نبود اسکرول محتوای اضافه را تأیید کرده است؛ بازشدن پیش‌نمایش دوربین نیز در اندازهٔ دوم اسکرول اضافه نداشت. این معیار مانع اسکرول ضروری در نمایشگر کوچک‌تر، بزرگ‌نمایی مرورگر یا نمایش خطای فرم نیست. تصاویر و نتایج این بررسی در بخش «تراز لبه‌های باکس‌های تجهیزات» [سند پیشرفت](21-implementation-progress-and-regression-policy.md) ثبت شده‌اند. راهنمای درون برنامهٔ فارسی/انگلیسی، ادامهٔ کار با کنترل‌های زیر تصویر پس از شروع تست را توضیح می‌دهد.

`equipmentService.test.ts` علاوه بر قرارداد CRUD، یک POST مستقل با تنظیمات فرم و پاسخ معتبر/متناقض را می‌سنجد. `useEquipmentConnectionTest.test.tsx` نتیجهٔ مستقیم، یک فراخوانی، لغو/پاسخ دیررس، تغییر تنظیمات، مجوز و timeout را بررسی می‌کند. `EquipmentConnectionTest.test.tsx` تست بدون درب/ذخیره، جلوگیری از دوبارکلیک و جداسازی انواع فاقد پشتیبانی را پوشش می‌دهد.

آزمون سرور `Hosting/Tests/EquipmentConnectionChecks.cs` و اسکریپت `Verify-EquipmentConnection.ps1` بررسی می‌کنند: endpoint بدون نشست 401 است؛ هر تست یک اتصال و Dispose دارد؛ خطا پاک‌سازی می‌شود؛ نوع نامعتبر/فاقد درایور اتصال ندارد؛ COM درست نگاشت می‌شود؛ timeout/cancel ظرفیت را تا cleanup نگه می‌دارند. این آزمون‌ها SQL یا دستگاه واقعی را مصرف نمی‌کنند.

سناریوهای `tests/e2e/equipment-connection.spec.ts` درخواست مستقل با تنظیم ویرایش‌شده در فارسی/انگلیسی، تست دستگاه جدید پیش از ذخیره، نبود درخواست درب/ذخیره، نوع فاقد درایور، لغو/تغییر و حذف را می‌سنجند. نتیجهٔ اجرا و حدود اعتبار در [سند پیشرفت](21-implementation-progress-and-regression-policy.md) ثبت می‌شود. موفقیت fixtureها تأیید اتصال واقعی دستگاه یا برطرف‌شدن موارد باز CRUD نیست.
