# مستندات محصول و UI سیستم پارکینگ

## هدف

این مجموعه مستندات، رفتار قابل مشاهده‌ی برنامه‌ی ویندوزی سیستم پارکینگ را به زبان محصول و UI ثبت می‌کند تا مبنای طراحی و پیاده‌سازی **فقط UI** نسخه‌ی تحت وب با React قرار گیرد. پیاده‌سازی Backend در scope این کار نیست؛ هر API یا قابلیت سروریِ لازم که قرارداد تأییدشده ندارد، باید به‌صورت درخواست قابل تحویل به تیم Backend ارجاع شود.

این مستندات بر اساس ساختار پروژه و مسیرهای ناوبری موجود تهیه شده‌اند. در این مرحله تمرکز روی فرم‌ها، نقش آن‌ها، داده‌های مورد نیاز، گردش کار و قرارداد مصرف API است؛ جزئیات پیاده‌سازی قدیمی یا الگوهای فنی غیرضروری ثبت نمی‌شوند.

## ساختار برنامه

```text
Splash
  └── Login
        └── تصمیم‌گیری مسیر بر اساس دسترسی
              ├── Dashboard: مدیریت و انتخاب پارکینگ
              └── MainForm: ورود مستقیم به پارکینگ جاری
                    ├── تنظیمات پارکینگ
                    ├── کاربران و دسترسی
                    ├── اعضا و کارت‌ها
                    ├── تردد و پرداخت
                    ├── مانیتورینگ و تجهیزات
                    └── گزارش‌ها
```

## الگوی مستندسازی هر فرم

برای هر فرم یا صفحه، این موارد باید تکمیل شوند:

- هدف و نقش فرم
- مسیر دسترسی
- نقش‌ها و سطح دسترسی
- داده‌های ورودی و context مورد نیاز
- اجزای UI و جدول‌ها
- عملیات کاربر
- اعتبارسنجی‌ها و وضعیت‌های خطا
- endpointها و مدل‌های API
- خروجی و اثر عملیات در سیستم
- مسیر بازگشت یا ادامه‌ی workflow

## اصول طراحی نسخه‌ی وب

- **تصمیم محصول:** هدف، پوشش حداکثری همه قابلیت‌های برنامه Windows در UI وب است. دسته‌بندی حوزه‌ها و فرم‌ها باید قابل تشخیص و مشابه محصول Windows بماند، اما ظاهر و interaction لازم نیست کپی WinForms باشد و باید از استانداردهای وب، responsive design و دسترس‌پذیری پیروی کند.
- هر قابلیت Windows که Browser نتواند مستقیماً پیاده کند (مانند اتصال تجهیزات، چاپگر، POS یا SDK)، نباید حذف خاموش شود؛ باید یک راهکار جایگزینِ قابل استفاده برای وب و مالک مسئول آن ثبت شود، مانند API Backend، Windows Service/Agent یا workflow اپراتور.
- `MainForm` باید به layout اصلی وب با sidebar، header و محتوای صفحه تبدیل شود.
- فرم‌های فهرستی بهتر است به الگوی مشترک جدول، فیلتر، صفحه‌بندی و عملیات CRUD تبدیل شوند.
- فرم‌های عملیاتی ورود و خروج باید به‌عنوان workflow چندمرحله‌ای و حساس به وضعیت طراحی شوند.
- contextهای سراسری مانند کاربر جاری، پارکینگ جاری، درب جاری و token باید در معماری وب مستقل و شفاف باشند.
- پیام‌های موفقیت، خطا، عدم دسترسی و قطع ارتباط باید بخشی از قرارداد UI باشند.
- رفتارهای صرفاً بهینه‌سازی‌شده‌ی نسخه‌ی ویندوزی، مانند پیش‌بارگذاری داده در Splash، نباید بدون ارزیابی به نسخه‌ی وب منتقل شوند.

## نکات نیازمند تأیید در مراحل بعد

- نام فارسی دقیق همه‌ی آیتم‌های منو از روی UI نهایی
- ماتریس کامل نقش‌ها و دسترسی‌ها
- قرارداد رسمی endpointها و schema پاسخ‌ها
- قرارداد نهایی فرم عملیاتی کنترل تردد و APIهای وابسته
